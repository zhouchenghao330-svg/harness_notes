## 1. 学习目标与边界

学习用数量级和物理下界判断方案，重点阅读第 1 章 1.2～1.3。

## 2. 先用直白的话讲

先把两类“读取”分开：vLLM 启动时将模型文件从磁盘／主机内存加载到 GPU 显存，是模型加载；模型已经驻留显存后，每次前向仍要让计算单元取得本轮参与运算的权重，是执行时的权重读取。下文的 `70 GB ÷ 3.35 TB/s` 算的是后者的理想 HBM 读取时间下界，不是启动加载时间，也不是实测显存流量。

LLM 的主要有参数计算来自大量线性投影：Attention 的 Q/K/V 与输出投影，以及 FFN 中的多个大矩阵。对单个 token，一个线性层的权重通常通过“输入乘权重，再累加到输出”参与计算。因此 `2 × 参与的线性层参数数` 可以粗估主要矩阵运算量，但不能代表完整模型的精确 FLOPs。

## 4. 关键输入、输出和状态

- 线性层权重形状为 $[m,n]$ 时有 $mn$ 个参数；一个 token 的输入向量有 $m$ 个数，输出有 $n$ 个数。
- 每个输出是 $m$ 项乘积之和。单 token 需要 $mn$ 次乘法和 $n(m-1)$ 次加法，严格按这两个操作计数为 $2mn-n$，通常近似为 $2mn$ FLOPs；一次乘加（FMA）也常按 2 FLOPs 计。
- 本次处理 $t$ 个 token 时，同一权重矩阵服务于 $t$ 行输入，主要矩阵计算量约为 $2tmn$ FLOPs，权重容量仍为 $mn$ 个参数。

## 5. 公式与数量级

已讨论的教学算例：名义 $N=70\times10^9$ 参数、8 bit 权重、H100 SXM、单请求生成一个 token。简化模型令主要权重每步读取量约为 70 GB，主要矩阵计算量约为 $2N=140$ GFLOPs。使用标称 3.35 TB/s HBM 带宽和约 989.4 TFLOP/s BF16 稠密矩阵峰值：

$$
T_{\mathrm{read}}\ge\frac{70\ \mathrm{GB}}{3350\ \mathrm{GB/s}}\approx20.90\ \mathrm{ms},\qquad
T_{\mathrm{compute}}\ge\frac{140\ \mathrm{GFLOPs}}{989400\ \mathrm{GFLOP/s}}\approx0.141\ \mathrm{ms}.
$$

假设读取与计算充分重叠，简化资源下界取两者较大值，约为 20.90 ms。这里“权重读取一遍”是建模假设，不代表每一步恰好发生 70 GB 的实测 DRAM 流量。容量是否可行仍须另行检查权重、KV、量化元数据及工作区。

### 单请求 Decode 与 batch 的通用粗估

令 $N$ 为本轮参与主要线性计算的参数数量（单位：parameters），$b_W$ 为每参数存储字节数，$B$ 为本轮一起 Decode 的请求数，$\Pi$ 为对应计算精度的 FLOP/s，$\beta$ 为显存读取带宽（bytes/s）。最容易犯的单位错误是拿模型文件大小的 GB 直接乘 2 去除以 FLOP/s：**计算量使用参数数量 $N$，读取量使用权重字节数 $b_WN$。**

在“每批主要权重读一次、各请求本轮各生成一个 token、计算与读取充分重叠”的教学条件下：

$$
T_{\mathrm{compute}}\approx\frac{2NB}{\Pi},\qquad
T_{\mathrm{weight}}\approx\frac{b_WN}{\beta},\qquad
T_{\mathrm{step}}\gtrsim\max(T_{\mathrm{compute}},T_{\mathrm{weight}}).
$$

$T_{\mathrm{step}}$ 是整批产生 $B$ 个 token 的理想单步资源下界；单请求 $B=1$ 时，理想生成速度上界约为 $1/T_{\mathrm{step}}$，批内总吞吐上界约为 $B/T_{\mathrm{step}}$。**$T_{\mathrm{step}}/B$ 是每输出 token 的分摊服务时间，不是每个请求的单步等待时间。**这里还没有计入请求排队或 Prefill。

batch 增大时，计算量随 $B$ 近似线性增长，而同一批请求可复用本轮读入的权重；因此在权重读取占主导的区间，总吞吐可能明显上升，而单请求的单步时间不一定下降。计算项追上读取项后，继续增加 batch 会拉长整批时间；**在这个理想两项模型中，总吞吐趋于计算上限，而不是无限增长**。上述 H100／70B 教学条件下的形式转折点约为 $B=148$，但该点尚未计入每请求 KV 的容量与读取，不能直接当作可运行 batch 配置。

量化首先改变权重的存储字节数：70B 参数在理想的 16／8／4 bit 纯权重口径下分别约为 140／70／35 GB，参数数量不会随之改变。因此仅从 $2NB$ 出发的主要矩阵 FLOPs 不会自动减半；真正计算时间还取决于所用 kernel、Tensor Core 精度、反量化和工作区。实际量化格式也有 scale 等元数据，不能只按理想位宽判断容量和读取量。

## 9. 已确认结论

- “单 token 的主要矩阵 FLOPs 约为参与计算的线性层参数数的两倍”只适合稠密线性层粗算：嵌入查表、Attention 的上下文交互、Softmax、归一化、激活和采样不能直接套用。
- MoE 的完整参数量影响存储容量，但单 token 的矩阵计算更接近实际激活的专家参数；Prefill 处理多 token 时也不能继续只用单 token 的 $2N$。
- 本算例只是理论资源下界，未计入全部算子、KV 读写、kernel 提交、量化转换和实际利用率；翻倍峰值算力不会消除当前由读取项主导的下界。
- batch 的主要收益是让同一次权重读取服务更多 token，从而提高整机吞吐；不能把整批时间除以 $B$ 当作单请求延迟。计算项成为主导后，该简化模型的吞吐逐渐接近计算上限。
