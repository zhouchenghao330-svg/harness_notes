# 组件 04：Prefill、Decode 与请求负载

> 状态：已共同阅读。本组件建立请求形状与到达形状的基础模型；具体调度、Prefix Cache 和 KV 分配留到组件 07～08。

## 1. 学习目标与边界

组件 03 估一次模型执行 step 需要多少计算和数据读取；本组件继续问：**一个完整请求包含哪些不同形状的 step、各要执行多少次、又在什么时候与其他请求一起到达？**重点阅读第 3 章 3.1。训练、多模态与实时音频暂不展开。

不能仅用“总共多少 token”代表推理负载。至少区分已有且可复用的历史 $S$、本轮新输入 $P$、本轮输出 $G$、请求到达时刻和同时在途的其他请求。

## 2. Prefill 与 Decode：批发和逐单交付

**Prefill 像批发。**输入 token 已全部给出，同一层中许多已知位置可组成较大的矩阵；同一份权重能服务许多行输入。Prefill 建立或扩展 KV，并产生首个输出。已知位置仍受因果注意力与层间依赖约束；“可并行组织”不等于各 token 毫无依赖。

**Decode 像逐单交付。**未来 token 尚未确定，下一个输出须等待上一个输出，因此有跨生成步骤的串行依赖。小 batch 时，每轮仅给少数新 token 使用权重，复用率较低。已有 KV 避免重新计算旧 token 的大部分投影和 FFN，但新查询仍要读取历史 K/V 并追加自己的状态。

所以 Prefill 的计算强度通常比小 batch Decode 高，更容易用满矩阵计算单元；但“Prefill 必定 compute-bound、Decode 必定 memory-bound”不是定律，仍取决于模型、batch、上下文和实现。

## 3. 一次请求的运行链与 $S/P/G$

按本书口径，已恢复 $S$ 个上下文 token，本轮处理 $P$ 个新输入，最终输出 $G$ 个 token：

```text
请求到达 → 排队 / 准入
              ↓
Prefill：处理 P 个新输入，使用可复用历史 S，产生首个输出
              ↓
后续 G−1 次 Decode：逐轮使用上一轮输出，读取并扩展 KV
              ↓
最后一个输出返回 → 按服务策略回收或保留状态
```

第 $j$ 次后续 Decode 开始时（$j=0,1,\ldots,G-2$），已有上下文约为 $S+P+j$。若最后一个输出不再喂回模型，完成时已写入的 KV 位置是 $S+P+G-1$；具体引擎还可能有分页、预留和回收粒度。

$S$ 指**已恢复且可供本次继续使用的状态**。如果前缀没命中或服务不能保留它，应用层虽有旧消息，服务端仍可能重算这些输入；不能仅凭 `messages` 中存在历史，就认定 $S$ 可以免费接续。

## 4. 相同总 token 数，为什么负载仍不同

实验 3-1 固定 Qwen3-8B 和每请求总长 4224 token：

| 请求 | 新输入 $P$ | 输出 $G$ | 后续 Decode 次数 |
| --- | ---: | ---: | ---: |
| A：长输入、短输出 | 4096 | 128 | 127 |
| B：短输入、长输出 | 512 | 3712 | 3711 |

B 的后续 Decode 次数约为 A 的 $3711/127\approx29.2$ 倍。batch=8 的固定逻辑账中，总矩阵工作量约为 512.8 与 548.5 TFLOPs，差距不大；累计 Decode 权重逻辑读取量约为 1804 与 52,329 GiB，约差 29 倍。一个 token 不论在 Prefill 或 Decode，主要投影和 FFN 大体都要执行；区别在于 Prefill 的大矩阵能复用权重，长输出却要经历许多有先后依赖的 Decode 轮。

**相近 FLOPs 不等于相近性能。**上述 GiB 是整段生成的累计逻辑读取量，不是单次显存容量，也不是实测 HBM 流量。实验也没有测出完整服务时间。

batch 与 Prefill 都能提高权重复用，但不完全相同：Prefill 组织同一请求中已知的多个输入位置；Decode batch 把多个并发请求各自的当前新 token 放在一轮。若 batch 为 $B$、每条新增输入 $P$ 个 token，主要线性层可粗略面对 $BP$ 行输入。

## 5. KV：历史与长输出的隐藏成本

已有 KV 避免旧 token 的大量重算，但新查询仍要访问旧上下文。历史越长，KV 容量通常越大，每轮 Decode 的历史状态读取也可能更多；长输出不仅增加串行轮数，还使后续轮面对逐渐增长的上下文。因此请求形状至少记录 $S/P/G$，并注明 $S$ 的复用条件。具体 KV 字节数、共享与淘汰留到组件 08。

## 6. 用户时间线：TTFT、TPOT、完整时间

设请求到达 $t_a$，客户端收到首个 token 的时刻为 $t_1$，收到最后一个 token 的时刻为 $t_G$：

$$
\mathrm{TTFT}=t_1-t_a,\qquad
T_{\mathrm{request}}=t_G-t_a,\qquad
\overline{\mathrm{TPOT}}=\frac{t_G-t_1}{G-1}\quad(G>1).
$$

- **TTFT** 看多久开始回应，包含排队、准入、输入处理、首次输出和交付；reasoning 的首个内部 token 不一定是用户可见的首个有用输出。
- **TPOT** 看开始输出后的节奏，不能直接等同纯 GPU Decode 时间。
- **完整请求时间**看末 token 到达；完整 Agent 任务还包括工具、后续模型调用和验收。
- **整机吞吐**看单位时间产出；有正确性和截止时间要求时，还须看有效完成量。

只缩短排队可改善 TTFT，却未必改变输出间隔；只加快 Decode 也未必消除漫长的首响应等待。“哪个服务更快”必须先指定指标。

## 7. 到达分布：相同平均 QPS 为什么还会排队

负载还要记录请求到达时刻，以及输入长短、输出长短与到达时刻的联合分布。相同平均 QPS 可以均匀到达，也可以集中突发；过去空闲的 GPU 时间不能存起来处理未来的突发。简化队列的逐窗积压为：

$$
Q_{k+1}=\max(0,Q_k+A_k-\mu_k\Delta t),
$$

其中 $A_k$ 是窗口内新工作，$\mu_k\Delta t$ 是可处理量。长 Prompt 集中到达主要增加 Prefill 压力；长输出集中到达则使请求在多轮 Decode 中持续占用 KV、带宽和调度位置。

实验 3-2 在固定单实例配置下各回放 480 条请求：均匀混合组与“前 9:1、后 1:9”组的完整请求 p95 都约 299.4 s，TTFT p95 则约为 242.9 s 与 258.9 s；初次调度等待和抢占事件也不同。两组都出现大量积压，KV 池采样占用达到 100%。这是单次、固定顺序的受控回放，说明“总量相同不足以确定各阶段指标”，**不能**据此断言时段变化总让所有指标恶化，或把差值当稳定因果效应。

## 8. 与 Agent Harness 的连接

一次 Agent Run 往往包含多次模型请求，中间隔着工具执行。工具结果可能追加到上下文，使下一轮输入变长；是重做全部 Prefill，还是只处理新增部分，取决于服务端前缀命中、状态保留与恢复。工具等待时 KV 是否驻留也由服务策略决定，不能从应用层消息列表直接推断。

所以仅凭 Agent “最终用了多少 token”无法解释延迟。至少要逐轮记录：新增输入 $P$、可复用历史 $S$、输出 $G$、到达时刻、排队、TTFT、TPOT、KV 驻留和工具等待。组件 05 再把多轮请求放进 Agent 依赖图与关键路径。

## 10. 已确认结论与适用边界

1. 总 token 数只是工作量的一个维度；输入/输出比例决定并行组织与串行推进的比例。
2. Prefill 的权重复用与 Decode 的逐步依赖，使相似 FLOPs 可以伴随很不同的逻辑读取量。
3. KV 避免旧 token 的大量重算，但不消除对历史状态的读取；历史 $S$ 能否复用必须有具体缓存或恢复条件。
4. 到达分布、并发、KV 容量和调度策略共同决定 TTFT、TPOT、完整延迟与吞吐；均值不足以描述尾部体验。
5. 实验 3-1 是逻辑资源估算，不是实测速度；实验 3-2 是一次固定配置回放，不是生产负载或普遍性能结论。
