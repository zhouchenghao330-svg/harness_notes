# HNSW 向量索引：构建过程与规模局限

> 记录日期：2026-10-13。来源：用户提供的与 GPT 的讨论，按主题整理。作为[[15_索引与向量检索]]的算法补充；返回[[00_学习目录|学习目录]]。

本篇讨论 HNSW 向量索引怎样建立，以及它在大规模数据下的资源局限，不展开 Embedding、向量数据库和 RAG 的整体流程。

理解构建过程，先掌握三个核心问题：

1. 向量之间如何建立连接？
2. 新向量加入时，如何找到应该连接的邻居？
3. 为什么要建立多层图？

## 一、最基础的向量索引：建立邻居图

先不考虑 HNSW 的分层结构。

假设数据库里有 6 个向量。为了方便理解，把它们画在二维空间里；实际上也可能是 768 维、1536 维。每个点代表一个已有向量，空间距离可用于衡量它们的相似性。

```text
向量的空间分布（示意）：

    A                       E
        B              D
    C                       F
```

最直观的建索引思路是：**让每个向量连接一些附近的向量。**

```text
建立连接之后（示意）：

A ── B ── D ── E
 ╲   │     ╲   │
   ╲ C       ╲ F
```

索引内部可以维护类似这样的邻接关系：

```text
A → [B, C]
B → [A, C, D]
C → [A, B]
D → [B, E, F]
E → [D, F]
F → [D, E]
```

以上只用于说明连接关系，并非完整 HNSW 算法的实际输出。

**向量索引不是简单地把向量按照距离排序，而是额外建立一套可导航的连接关系。** 图中不仅有局部连接，也可以保留一些跨度较大的连接，例如 B → D，帮助搜索跨越不同区域。

## 二、新增一个向量，怎样给它建立索引？

假设现在加入一个新向量 G。

最暴力的做法是：

1. 计算 G 与全部已有向量的距离。
2. 找到距离 G 最近的几个向量。
3. 将 G 和它们连接起来。

如果每插入一个新向量，都要遍历所有已有向量，构建大型索引会很昂贵。

HNSW 的方法是：**利用已经建立的图，寻找新向量的候选邻居。**

```text
已有图：

A ── B ── D ── E
     │    │
     C    F

现在插入 G，G 的位置靠近 E。
```

构建过程可以简单理解为：

1. **选择入口节点。** 例如从 A 开始。
2. **沿着图搜索。** 比较当前节点和邻居到 G 的距离，逐渐向 G 所在区域移动，例如 A → B → D → E。
3. **收集候选邻居。** 不只保留 E，还会探索一组有希望的节点，例如 D、E、F。
4. **选择并建立连接。** 通过距离和邻居选择策略，确定 G 应该连接哪些节点，并更新相应节点的邻接关系。

最后，局部可能形成：

```text
D ── E
│  ╱ │
F ── G
```

以上是简化示意，搜索不一定沿唯一的一条路径前进。

### 邻居选择不只是取最近的 M 个点

HNSW 并不是永远只选距离最近的 M 个点。它还有邻居选择启发式策略，会考虑连接的多样性，避免所有连接都集中在同一个方向。

### 建立双向连接，并维护连接数量

建立连接一般是双向的。如果 G 连接 E，E 的邻居列表也要更新；如果 E 的连接数量超过限制，还需要进行裁剪。因此，双向添加连接后还要经过各节点的邻居维护，不能把示意图理解为最终一定严格对称的邻接表。

这样，新向量就被逐步整合进已有索引。

## 三、为什么要建立多层图？

单层图有一个潜在问题：假设数据有 1000 万条，从入口节点一步步走到目标附近，可能需要经过很多节点。

HNSW 的解决办法是分层。上层节点少，用于先定位大致区域；下降到较低层后，再进行更细的搜索。

```text
Layer 2：            D
                     │
Layer 1：      B ─── D ─── E
               │     │     │
Layer 0： A ── B ─── D ─── E
               │     │
               C     F
```

横线表示简化的层内连接；竖线只表示同一个节点在不同层出现，不是额外的层内邻居连接。实际每层都是图结构，不一定像示意中这样连接成直线。

分层规则是：

- **Layer 0，最底层：所有向量都存在。**
- Layer 1：只有一部分向量。
- Layer 2：节点更少。
- 更高层依此类推。

### 新向量应该出现在哪些层？

HNSW 使用随机层级分配机制。随机确定一个节点的最高层级，它会出现在从 Layer 0 到该最高层级的所有层中。

例如：

```text
A → Layer 0
B → Layer 0、1
C → Layer 0
D → Layer 0、1、2
E → Layer 0、1
F → Layer 0
```

这种随机分配遵循类似指数衰减的概率分布：层级越高，能进入的节点越少。

### 分层以后怎样插入 G？

1. 随机确定 G 的最高层级。
2. 从现有图的最高层入口开始，寻找 G 所在的大致区域。
3. 对于高于 G 最高层级的已有层，只进行导航，不把 G 插入这些层。
4. 一层层下降，在 G 需要加入的每一层搜索候选邻居。
5. 在各层建立连接，并维护连接数量限制。
6. 如果 G 的层级超过当前最高层，就把 G 设为新的最高层入口。

这样既能增量建立索引，也避免每次插入都从全部向量中暴力找邻居。

## 四、建索引时两个最关键的参数

| 参数 | 控制什么 | 调大后的主要影响 |
| --- | --- | --- |
| `M` | 每个节点建立连接的规模 | 图更密、内存开销更大，通常有利于召回率 |
| `efConstruction` | 构建时搜索候选邻居的广度 | 建索引更慢，但通常能建立质量更好的图 |

例如：

```text
M = 16
efConstruction = 100
```

可以粗略理解为：

- 在构建某一层的连接时，搜索过程中维护更广的候选集合，搜索宽度由 `efConstruction` 控制。
- 从候选节点中选择邻居，连接规模由 `M` 控制。
- 不是随机找 16 个节点，也不是必须比较全部向量。

`efConstruction = 100` 也不表示恰好只计算 100 次距离；它描述搜索过程中保留候选的宽度。

实际实现中，Layer 0 通常允许比上层更多的连接，例如经典 HNSW 常用 `2M` 作为底层连接上限。需要区分新节点选择邻居时的连接规模，以及已有节点更新后允许保留的连接上限。

## 五、把整个建立过程串起来

```text
              已有 HNSW 索引
                    │
                    ▼
              插入新向量 G
                    │
                    ▼
             随机决定最高层级
                    │
                    ▼
           从现有最高层入口搜索
                    │
                    ▼
              逐层向下导航
                    │
                    ▼
          在需要插入的层寻找候选邻居
                    │
                    ▼
           根据策略选择邻居节点
                    │
                    ▼
            建立双向连接并裁剪
                    │
                    ▼
       必要时更新最高层级和入口节点
                    │
                    ▼
               索引更新完成
```

**HNSW 构建索引的本质，就是把向量组织成一个分层的邻居图。新向量加入时，利用已有图快速寻找候选邻居，再建立连接，而不是每次都与所有向量进行比较。**

HNSW 是增量构建的，但不意味着一次插入就能得到全局最优的邻居图。插入顺序、候选搜索广度和邻居选择策略都会影响最终索引质量。

## 六、为什么流行，以及它的规模局限

HNSW 是主流的 ANN（Approximate Nearest Neighbor，近似最近邻）索引算法之一。讨论中提到，Qdrant、pgvector、Milvus、Elasticsearch 等都支持 HNSW。

**HNSW 流行，是因为它在查询速度、召回率和工程易用性之间取得了很好的平衡，不代表它在任意超大规模下性能都最好。**

### 为什么经常选择 HNSW？

1. **查询速度快。** 利用分层图导航，不必遍历所有向量。数据量增加时，搜索开销通常增长得比较缓慢。
2. **召回率高。** 通过调整查询时的搜索参数 `efSearch`，通常能实现很高的召回率，同时保持较低的查询延迟。增大搜索宽度通常也会增加查询开销。
3. **支持增量插入。** 新增向量可以直接加入已有图，不必每次都重新构建整个索引。

这里的两个搜索宽度参数作用在不同阶段：

| 参数 | 所在阶段 | 主要取舍 |
| --- | --- | --- |
| `efConstruction` | 建立索引、插入节点时 | 构建开销与图的质量 |
| `efSearch` | 查询已有索引时 | 查询开销与召回率 |

### 内存成本是明显限制

假设存储 **1 亿个向量，每个向量 768 维，使用 float32，每维 4 字节**。

仅原始向量数据的容量为：

```text
100,000,000 × 768 × 4 字节
= 307,200,000,000 字节
= 307.2 GB（十进制）
```

**307.2 GB 还没有计算 HNSW 图连接、节点管理及其他元数据。** 它是未压缩原始向量的容量，不是完整索引的总内存需求。

因此，HNSW 虽然搜索很快，大规模数据下的内存成本仍会成为重要限制。索引和数据怎样存得下，以及建索引所需的时间与资源，都需要一起考虑。

### 与其他主流向量索引的区别

| 索引算法 | 核心思想 | 主要特点 |
| --- | --- | --- |
| HNSW | 构建分层邻居图 | 查询快、召回率高，但比较占内存 |
| IVF | 将向量聚类分桶 | 搜索时只访问部分桶，减少搜索范围 |
| IVF-PQ | 分桶 + 向量压缩 | 大幅节省内存，但存在精度损失 |
| DiskANN | 利用图索引与 SSD | 适合内存放不下的大规模向量集合 |

讨论中的规模例子用于帮助理解：

- **百万、千万级向量：** HNSW 经常是很好的默认选择。
- **亿级向量：** HNSW 依然能用，但可能需要分片、量化以及足够的内存。
- **十亿级甚至更大：** DiskANN、IVF-PQ 等方案的存储成本优势可能更明显。

这些不是严格的算法适用边界，也不能仅凭向量数量选索引。真实选择还取决于向量维度、硬件、召回率目标、查询吞吐量等因素。

### 搜索效率与资源效率要分开看

一个容易形成的直觉是：

> 向量越多，HNSW 的分层优势就越明显，所以它应该更适合超大规模数据。

这个推理只对了一半。分层结构确实有助于保持较好的搜索效率，但还要区分：

| 概念 | 关注的问题 |
| --- | --- |
| 搜索效率 | 找到近邻需要多少次距离计算、多少时间 |
| 资源效率 | 获得这样的搜索速度需要多少内存、存储及建索引成本 |

HNSW 在搜索效率上通常很优秀，但资源效率不一定占优势。

当内存比较充足，而且特别重视低延迟、高召回率时，HNSW 是成熟且常用的默认选择。真正海量的数据场景，还必须考虑怎样让索引和数据以可接受的成本存得下。这也是向量数据库会提供多种索引算法的原因。
