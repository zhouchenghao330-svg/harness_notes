# 多样化上下文压缩（用人话理解）

> 这几种东西都在解决同一个问题：对话越来越长，模型每次都要带上很多旧内容。它们的区别不在于“能不能总结”，而在于什么时候动手、谁来决定，以及旧内容还在不在。
>
> 日期：2026-08-26
>
> 关联：[[04_context_and_prompt]]、[[07_compaction_and_branching]]

## 先给一个最简单的结论

| 方案 | 用人话说 |
| --- | --- |
| pai-acp | 给 Agent 一把剪刀，让它自己决定删哪一段、以后要不要找回来 |
| pi-smart-compact | 系统发现上下文快满了，就提前准备一份经过检查的总结，再交给 Pi 正常压缩 |
| pi-context | 不急着删旧对话，而是在旧历史树上开一条“带交接说明的新路” |
| pi-press | 趁 Agent 还在工作时，后台偷偷把总结准备好；下一次请求先用这份总结，最后再正式落盘 |
| Hypa | 还没进对话之前，先把 shell、编译、git 这些很长的工具输出滤干净 |

所以，前四个主要处理“对话历史”，Hypa 主要处理“工具输出”。Hypa 和其他方案不是竞争关系，通常可以一起用。

## 先说缓存：为什么改历史会有代价

模型服务商会缓存请求前面那一大段内容。如果我们把已经发过的旧对话换成摘要，那么被换掉的位置后面通常就要重新缓存。

但如果只是把这一次新产生的工具输出变短，之前的对话没有被改写，前面的缓存一般还能继续用。

这就是为什么 Hypa 对缓存更友好；而各种会话压缩方案，哪怕摘要本身做得很好，真正替换旧历史时仍然会产生一次缓存断点。

## 1. pai-acp：给 Agent 一把剪刀

参考：

- [Pi Discussion #7414](https://github.com/earendil-works/pi/discussions/7414)
- [pai-acp](https://www.npmjs.com/package/pai-acp)

它给 Agent 几个上下文工具：

- compress：把一段旧消息压成摘要；
- decompress：需要时把它展开；
- search_context：先在压缩内容里搜索，不必整段展开；
- acp_status：看看现在的上下文是什么状态。

简单说，模型自己判断“现在该不该整理”，然后告诉工具要整理哪一段。下一次请求发送给模型时，pai-acp 会按照这个决定重新拼一遍消息。

它的优点是很灵活：模型可以只压掉已经完成的工作，也可以临时找回旧内容。缺点也很直接：模型每次压缩、解压，都会改变它看到的历史。频繁来回改写，缓存就会频繁失效，而且摘要好不好完全取决于 Agent 有没有做对。

一句话：Agent 自己拿剪刀，灵活，但容易剪得太勤。

## 2. pi-smart-compact：系统先准备，Pi 再正式压缩

参考：

- [README](https://github.com/alpertarhan/pi-smart-compact/blob/main/README.md)
- [ARCHITECTURE.md](https://github.com/alpertarhan/pi-smart-compact/blob/main/ARCHITECTURE.md)

它不是让 Agent 在当前这一步突然改消息，而是让系统盯着上下文使用量。在比较合适的时候，系统先做一份候选总结：

1. 先挑出可以压掉的旧内容，保留最近正在做的事情；
2. 把文件、错误、决定、未完成事项等重要信息提取出来；
3. 让模型整理成一份交接说明；
4. 再检查文件名、错误和任务状态有没有丢；
5. 只有 Pi 真正进入正常 compaction 流程时，才把这份总结提交进去。

Agent 也可以提出 smart_compact 请求，但它只是“请系统准备”，不会在当前 turn 中途直接改掉正在使用的上下文。

它比 pai-acp 稳，因为压缩有时机、有收益门槛，也有失败回退；但它仍然是正式替换旧历史，所以替换点后面的主对话缓存还是会重新建立。

一句话：像一个谨慎的整理员，先整理和检查，等安全时再换掉旧记录。

## 3. pi-context：不删旧树，开一条带摘要的新路

参考：

- [README](https://github.com/ttttmr/pi-context)
- [context-management Skill](https://github.com/ttttmr/pi-context/blob/main/skills/context-management/SKILL.md)
- [src/index.ts](https://github.com/ttttmr/pi-context/blob/main/src/index.ts)

Pi 本身会把会话保存成一棵历史树。pi-context 借助这个特性，让 Agent 做三件事：

- 给某个节点做 checkpoint，标记“这里是一个阶段”；
- 查看时间线，知道自己现在在哪条历史路上；
- 从某个旧节点写一份 summary，然后开一条新的分支继续工作。

例如原来是：

~~~text
A → B → C → D → E
                     Summary → 继续做下一阶段
~~~

D、E 没有被物理删除，旧分支还在。新的活动分支从 C 接上摘要继续走。

它的好处是历史保留得很完整，也可以从不同阶段重新开始；如果摘要边界选得好，边界之前的缓存还有机会继续用。它的风险是摘要和切点由 Agent 自己决定。Agent 如果切得太早，或者交接说明漏了关键信息，下一阶段就会接不上。它也只管理对话历史，不会回滚文件、进程或浏览器状态。

一句话：不是把旧笔记撕掉，而是从某一页开始写一本带交接说明的新笔记。

## 4. pi-press：趁还没到极限，后台先把总结做好

参考：

- [jsDelivr 包页面](https://www.jsdelivr.com/package/npm/@sunnyx11/pi-press)
- [设计说明](https://github.com/sunnyx11/pi-press/blob/main/docs/DESIGN.md)
- [运行代码](https://github.com/sunnyx11/pi-press/blob/main/src/extension-runtime.ts)

pi-press 发现上下文大约到了阈值（默认约 80%）时，不马上打断 Agent，而是在后台准备一份 Pi 原生格式的压缩总结。

等下一次要请求模型时，如果总结已经准备好了，它会临时把模型看到的内容变成：

~~~text
压缩总结 + 最近还没有压缩的新消息
~~~

Pi 内部那份原始记录此时还没有被改掉。等 Agent 这一轮真正结束后，再由 Pi 正式写入 compaction entry，并尽量复用刚才准备好的总结。

这解决的是两个实际问题：

- 不要等到上下文快爆了才临时总结；
- 不要为了压缩而打断当前工作。

但它不是“完全不影响缓存”。第一次把模型视图切成“总结 + 尾部”时，切换位置后面的缓存仍可能失效；如果后台又生成了新总结，也会再出现一次断点。它主要优化的是等待时间和硬限制风险，不是专门让缓存永远不变。

一句话：先在后台写好小抄，必要时先给模型看小抄，事后再把小抄正式放进档案。

## 5. Hypa：先把工具输出变短，再让它进上下文

参考：

- [Hypa 项目](https://github.com/Hypabolic/Hypa)
- [压缩流程](https://github.com/Hypabolic/Hypa/blob/main/docs/architecture/compression-pipeline.md)
- [Pi 接入](https://github.com/Hypabolic/Hypa/blob/main/packages/pi-hypa/README.md)

Hypa 主要不管聊天历史。它管的是 Agent 经常调用的命令：

- git status、git diff；
- 编译和测试；
- docker、kubectl；
- npm、TypeScript 等。

例如一次编译产生几千行输出，Hypa 会先把它整理成错误、警告、文件路径、行号和退出码等有用内容，再把短版本交给 Agent。必要时，完整输出会另存为本地文件，方便之后查看。

它默认使用确定性的规则，不靠另一个模型重新总结，所以行为比较稳定，也不会回头改写已经存在的对话。当前的 Pi 插件主要是改写 bash/tool 调用和压缩 tool result，并不是 Pi 会话级的 context_compact，也没有借用 Pi Session Tree 来切分聊天历史。

这使它对缓存特别友好：旧对话不动，只是新进来的工具消息变短了。

一句话：像水管口的滤网，先拦住工具输出里的噪声,不让它把整桶脏水倒进上下文。

## 放在一起看

~~~text
工具输出进来之前
    ↓
Hypa：先把命令输出滤短
    ↓
正常 Agent 对话
    ↓
上下文变长后，选择一种会话级方案：
    ├─ pai-acp：Agent 自己剪
    ├─ pi-smart-compact：系统检查后正式压
    ├─ pi-context：从历史树开新分支
    └─ pi-press：后台先准备，之后再正式压
~~~

如果要做自己的 Harness，我会这样分工：

- Hypa 负责工具输出，尽量让噪声不要进来；
- 会话级压缩只选一个真正的“负责人”；
- 想保留历史和阶段切换，就借鉴 pi-context；
- 想要更稳的摘要和失败回退，就借鉴 pi-smart-compact；
- 最怕上下文突然爆掉、又不想打断当前工作，就借鉴 pi-press；
- 想把决定权交给 Agent，再考虑 pai-acp，但要接受缓存和摘要质量的波动。

最重要的一点：

> 不要让多个方案同时改写同一份活动上下文。工具输出压缩可以叠加，但会话级压缩最好只有一个主人。
