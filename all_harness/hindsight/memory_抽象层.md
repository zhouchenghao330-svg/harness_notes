# Memory 抽象层

> 目的：从 Hindsight 的具体实现中提炼出能跨项目使用的 Memory 思考框架，帮助理解和设计记忆系统。整理日期：2026-10-05。
>
> 来源：用户提供的讨论、已共同阅读的 [[02_retain_pipeline|Retain 拆解]]，以及本地源码的边界核对。通用框架是设计解释【Inferred】，Hindsight 对照处标注【Code-verified】。第 6 节补充用户认可的写入路径设计框架；TencentDB 金字塔仅作为用户提供的比较案例，尚未在本页核对其源码。Recall、Reflect 和归纳维护仍须按 [[01_components|组件地图]] 继续共同阅读；本页不改变它们的阅读状态。

## 1. 先抓住一个问题

**Memory 管的是：当前上下文放不下、或者当前运行结束以后，哪些信息仍要留下，以什么方式留下，以后如何找到，信息变化以后如何处理。**【Inferred，通用理解】

可以把它理解为“让过去的信息持续可用的一套规则”。长期保存是基础，还需要知道谁能使用、来源是什么、何时适用，以及新证据来了怎么办。

与熟悉的 Harness 对照：

| 侧重点 | 用人话描述 |
| --- | --- |
| Harness | 当前任务怎么运行，模型看到什么、能做什么，以及下一步如何继续 |
| Memory | 过去哪些信息以后仍可使用，怎么找回，以及怎样处理变化 |

这是侧重点的区分。Harness 也会处理持久化与恢复，Memory 也会参与当前上下文选择；两者通过读写接口协作，职责会交叉。【Inferred】

```text
当前任务 / Harness
    |
    +-- 产生新信息 --> Memory 写入 --> 可持续使用的信息
    |                                      |
    +<-- 放入当前上下文 <-- Memory 查找 <-----+
                                           |
                                  归纳 / 修正 / 清理
                                           |
                                           v
                                  更新后的信息与关系
```

不需要先掌握数据库、向量索引和图算法的所有实现，才能建立这个框架。先说清这些职责，再决定实现需要多复杂；具体机制仍要检查，确认它是否兑现了这些职责。【Inferred】

## 2. 看任何 Memory 系统都先问五件事

### 2.1 留下什么

英文讨论中叫 Admission，可以先理解成“决定哪些信息值得保留”。

输入一句话、一次工具结果或一份文档，系统要决定全留、只留重点，还是不留。这个决定可能由调用方、固定规则或模型做出；有的系统默认全收，选择发生在以后读取时。【Inferred】

例如“今天聊了天气”和“用户对某种食物过敏”，是否同样保存，取决于记忆的用途。这里的“值得”是任务策略，不是数据天然具有的属性。

Hindsight 的 concise 抽取 Prompt 要求选择值得长期记住的重要事实；chunks、verbatim 等模式采用不同保留策略。它说明了模型抽取参与信息筛选，不代表所有模式都用同一套价值判断。【Code-verified】

### 2.2 留成什么

英文讨论中叫 Representation，可以理解成“用什么形式表达保留下来的信息”。

可以保留原文、事件、简短事实、用户偏好、归纳结论，或它们的组合。还要保留足够的来源和时间，才能解释、修正或者重新检查一条记忆。【Inferred】

Hindsight 里需要分清几种角色：

| 对象 | 作用 |
| --- | --- |
| 来源 document / chunk | 保存或标识原始材料，使事实有来源可追溯 |
| fact | 系统使用的一条事实或经历记录 |
| observation / mental model | 对已有材料形成的上层归纳内容，两者的组织与触发方式不同 |
| embedding / links | 帮助查找或连接信息的索引与访问线索 |
| entity ID / fact ID / document ID | 稳定引用对象、建立关联和定位更新范围 |

这些对象与角色在已核对的本地代码中存在；上层归纳的完整生命周期待组件 09 展开。【Code-verified】

同一份信息可以同时具有正文、来源、身份和查找线索。向量和 ID 的用途分别是检索与引用，不能直接当作事实正文或已经验证的知识。

### 2.3 怎样判断是不是以前的那个对象

英文讨论中叫 Identity，可以理解成“名字变了以后，还能不能认出同一个人、文档或对象”。

例如 Alice 和 Alice Chen 是否同一个人？一份重新提交的文档是否是旧文档的新版本？这些问题决定系统是否共享身份、复用内容或建立关联。【Inferred】

Hindsight 的实体解析利用名称检查、共现和时间等信号，决定是否复用实体 ID；文档更新使用 bank 与 document_id 确定更新范围。【Code-verified】

需要区分三个判断：

- 同一个实体：两条信息说的是不是同一个人或对象。
- 相同或相近内容：两段信息是否重复、接近。
- 同一事实是否仍适用：信息是否已经过时、被修正或出现冲突。

实体 ID 匹配成功，不会自动解决后两个问题。Alice 先在 Acme、后来在 Beta 工作，也可能是同一个人在不同时间的两条有效记录。【Inferred，设计例子】

### 2.4 以后靠什么找回来

英文讨论中叫 Access，可以理解成“当前任务给出什么线索，能从过去的信息里找到什么”。

线索可以是语义、关键词、实体、日期、来源、标签或已有关系。找到候选之后，还要决定保留多少、要不要回到原文，以及哪些内容最终交给模型。【Inferred】

Hindsight 的 Retain 已经在为未来查找做准备：增强向量输入、解析实体、建立语义、时间和因果链接。事实正文与 Embedding 输入可以不同；四类关系各自判断，没有统一加权建边总分。【Code-verified】

哪些线索在 Recall 中实际使用，如何融合、重排、控制数量与 token 预算，仍待组件 04 共同阅读。写入时建了索引或关系，不等于当前查询必然会用到它。

### 2.5 信息变化以后怎么办

英文讨论中叫 Evolution，可以理解成“新信息来了，旧记录和旧结论要怎样处理”。

需要决定追加历史、修改当前记录、保留多个版本、标记冲突、删除过期内容，或者重新生成依赖旧信息的归纳。【Inferred】

Hindsight 的 Delta Retain 对同一文档做按块编号的哈希比较：未变块复用，修改和删除的块清理旧事实及受影响的关系，新块重新处理；受影响的观察和图维护也需要相应处理。【Code-verified】

长期状态可以演化，但不要求每个系统都覆盖旧记录。一个系统也可以保留只追加的事件历史，再从历史维护当前视图；具体策略要看时间语义、来源和使用目标。【Inferred】

## 3. 把 Retain 的操作放回这些问题

Retain 可以理解成“把输入整理成系统以后能维护和使用的信息”的写入路径。【Inferred】

| 已拆解的操作 | 在解决什么问题 |
| --- | --- |
| 抽取模式、Prompt、事实选择 | 留下什么，以及留下多细的内容 |
| 切块、事实记录、日期与来源关联 | 留成什么，以及以后怎样回查来源 |
| 实体名称解析和稳定 ID | 怎样与已有对象保持身份连续 |
| 向量输入增强、Embedding、各类关系 | 未来有哪些查找与关联线索 |
| 文档身份、块哈希、增量替换与清理 | 哪些旧内容仍保留，哪些需要更新 |

操作与源码行为见 [[02_retain_pipeline]]；把操作归入五个问题是设计解释【Inferred】，分类允许交叉，不要求每个操作只属于一个格子。

原讨论中的“Memory Compiler”可以保留为理解用的比喻：输入经过整理，形成系统可维护的内容、身份和查找线索。它不意味着每种 Memory 都必须做 LLM 抽取、实体消歧或图构建。

“Commit Path”也可以用于理解写入职责，但不能据此认为整次 Retain 是一个数据库原子提交。Hindsight 的流式写入可以分批提交，部分语义链接在事实提交之后补建。【Code-verified】

一个很轻量的实现也可以回答五个问题：选择用户偏好，写进带来源和日期的 Markdown，按固定位置或关键词读取，偏好变化时更新相关段落。向量、图和后台归纳是在具体规模及使用需求下选择的实现手段。【Inferred，设计例子】

## 4. 写入 查找 推理 维护分别是什么

### 4.1 Hindsight 中的职责对照

| 路径 | 人话 | 当前确认范围 |
| --- | --- | --- |
| Retain | 把新内容变成能保留和使用的记忆 | 既定写入清单已共同阅读，见 Retain 笔记 |
| Recall | 按当前问题查找记忆并返回结果 | 已确认入口；完整检索与结果预算待组件 04 |
| Reflect | 模型使用检索工具收集证据，形成回答 | 已核对基本职责；Agent Loop 与工具细节待组件 05 至 07 |
| Consolidation / 心智模型刷新 / 维护 | 归纳已有信息、刷新上层内容或维护关联 | 已核对职责边界；完整流程待组件 09、10 |

Retain、Recall、Reflect 的主入口及 Reflect 的只读工具职责已从本地源码核对。【Code-verified】这张表不把“确认职责”标记为“组件已经共同读完”。

### 4.2 修正原讨论中容易混淆的说法

**Reflect 与 Consolidation 要分开。** 当前 Hindsight 的 Reflect 使用只读检索工具生成回答，不把回答自动写回长期事实。Consolidation 才负责创建或更新 observations。心智模型刷新流程可以调用 Reflect 得到内容，再由刷新流程保存到心智模型，因此推理结果是否持久化取决于调用它的流程。【Code-verified】

```text
问题 -> Recall / 检索工具 -> 已有证据 -> Reflect -> 回答

新事实 + 已有观察 -> Consolidation -> 创建 / 更新观察

心智模型刷新任务 -> 调用 Reflect -> 保存刷新后的心智模型
```

**Memory 与 RAG 的边界有重叠。** 检索增强回答关注把找到的材料用于生成；Memory 的设计还可以关注过去的经历、身份、适用时间以及长期变化。RAG 系统同样可以更新索引、保留版本和管理权限，不能凭“能更新”或“用了图”就断定属于哪一类。比较时要看它实际负责什么。【Inferred】

**抽象可以少，实现仍要查。** 五个问题帮助组织理解；具体项目的失败、恢复、删除、冲突或后台更新路径，仍按 [[00_拆解共识#1.4 Runtime 内容的完整性和模块完成标准|完整性规则]] 主动检查。抽象页不替代 Runtime 操作清单。

## 5. 后续怎样继续寻找抽象

### 5.1 先看职责和输入输出

可以先用三个简单接口来思考系统，暂时不决定技术栈：【Inferred，设计辅助，并非 Hindsight 的正式 API 定义】

| 职责 | 输入要说明什么 | 输出要说明什么 |
| --- | --- | --- |
| 写入 | 内容、用途、归属范围、来源和日期 | 留下哪些内容，得到哪些稳定引用 |
| 查找 | 当前问题、可见范围、时间条件和内容预算 | 找到什么，有哪些来源，以及如何供当前模型使用 |
| 修正或清理 | 新证据、要更新或删除的范围 | 哪些记录变化，哪些依赖结论和关联需要重做 |

这三个职责可以在一个文件或模块里实现，也可以由多个服务协作。先把输入输出和规则说清楚，才能判断拆分是否有必要。

### 5.2 继续阅读时追问这五件事

1. **时间**：日期表示发生、提及还是写入？新旧记录是否可能同时有效？
2. **来源与可信程度**：这是原始记录、模型抽取还是推断？能否回查证据，发现错误后怎样修正？
3. **使用范围**：这是谁的记忆，哪些任务能读取，修改或删除的边界在哪里？
4. **上下文预算**：找到很多材料以后，哪些真正进入模型请求，为什么选择它们？
5. **变化传播**：原始内容改变以后，事实、索引、关系和上层归纳是否同步处理？

这些是后续核对问题，不表示每个机制都已经确认存在。按当前组件地图，下一步读 03 记忆表示与持久化，再读 04 Recall；届时用实际代码修正和补充本页，不因新建抽象页跳过其他 Runtime 内容。

## 6. 从「写入 / 召回」继续展开设计空间

### 6.1 用户已经有的抽象，以及现在需要补的层次

用户已有的第一层理解是：Memory 提供写入和召回两大方向。继续展开写入时，采集时机、切分、事实粒度、实体、时间、索引、关系和更新等不同问题同时出现，需要一个能跨项目比较的框架。【用户讨论 + Inferred】

~~~text
Memory
+-- 写入：过去的信息怎样成为可持续使用的记忆？
+-- 召回：当前任务怎样找到并使用这些记忆？
~~~

这里的“两层”按两大方向理解，不表示先后层级。归纳、修正、清理可以继续展开为状态维护职责，不能因为顶层只有读写就遗漏它们。

第 2 节的五个问题提供总视角；本节进一步把“写入”内部需要作出的设计选择展开。目标不是继续寻找一句万能定义，而是明确不同项目在哪些选择上相同、在哪些选择上不同。【Inferred】

### 6.2 两个组织方向：向上归纳，以及补充坐标和关系

用户熟悉的 TencentDB 案例可画成：

~~~text
文档 / 对话 -> Fact -> Scene -> User Profile
~~~

这是用户提供的组织模型，尚未在本页核对具体项目版本或源码。它可用于理解“由具体记录形成更高层描述”的方向；不同层具体如何生成、是否保留细节，仍取决于实际实现。【用户描述，待项目核对】

Hindsight 已共同阅读的 Retain 则主要表现为：

~~~text
文档 / 对话 -> 来源片段 -> Fact
                            |
                            +-- 时间与来源
                            +-- 实体身份与关联
                            +-- 向量和关键词等查找线索
                            +-- 语义、时间、因果等关系
~~~

Retain 在事实层补充身份、时间、来源及访问线索；后续 Consolidation 还会形成 Observation，另有 Mental Model 对象。因此不能把 Hindsight 整体理解成“到 Fact 就结束”。【Code-verified：沿用已核对的职责边界，完整上层生命周期仍待组件 09】

比较时可以使用两个独立方向：【Inferred】

| 方向 | 问题 | 例子 |
| --- | --- | --- |
| 向上归纳 | 多条具体信息能否形成更高层描述？ | 场景总结、人物画像、观察 |
| 补充坐标和关系 | 一条信息能否有明确身份、时间、来源和关联？ | 实体 ID、日期、来源引用、检索线索、链接 |

一个系统可以同时做两件事。它们用于描述关注点，不是互斥的项目分类。

### 6.3 三个边界：什么时候送入、怎样切块、怎样形成记忆单位

~~~text
持续发生的对话 / 经历
          |
          v
采集边界：什么时候送入？每次送多少上下文？
          |
          v
一次写入收到的文档 / 对话窗口
          |
          v
切块边界：这份输入怎样分成可处理的片段？
          |
          v
Chunks
          |
          v
记忆单位边界：哪些内容值得独立保存，拆得多细？
          |
          v
Facts / 其他 Memory Units
~~~

这是三种不同的设计决定。【Inferred】

| 边界 | 人话 | 教学例子 |
| --- | --- | --- |
| 采集 Capture | 什么时候把什么范围的信息交给 Memory？ | 每 10 轮调用一次；会话结束写入；重要事件立即写入 |
| 切块 Segmentation | 收到的这一批输入怎样分段处理？ | 10 轮对话切成 3 个块 |
| 记忆单位 Unitization | 每个块产生哪些独立记忆？ | 3 个块分别产生 4、2、5 条事实 |

这些数字只是教学假设，不是 Hindsight 的默认行为。

采集策略需要在调用方或集成层检查。Retain 内部的切块只回答“收到内容以后怎样处理”，不能据此推断 Agent 每轮、定时或在会话结束调用 Retain。【Inferred：职责区分】

例如“工资少一点无所谓”可能依赖前面的换工作讨论。逐句送入和按完整对话窗口送入，会给抽取提供不同的上下文，也会影响延迟、成本和什么时候能召回这段信息。原始消息、滚动窗口、预先总结及异步采集是不同策略，需要按实际调用链确认。【Inferred】

“切块”也不等于“截断丢弃”。要分别问：内容只是被分批处理，还是有内容被永久舍弃？如果使用重叠窗口，重复输入怎样避免造成重复记忆？重叠与去重是否存在，必须检查具体实现。【Inferred，后续比较问题】

### 6.4 Fact 是系统定义的记忆单位

原始输入：

> 我毕业后来到南京，在一家 AI 公司做 Agent。我喜欢这个方向，但是通勤有点远。

系统可以把它拆成多条信息，也可以保留一条较完整的职业状态记录。两种方式会影响以后独立检索、修改、关联和回查来源的粒度。【Inferred，教学例子】

**Fact 可以理解为：系统选择作为独立保存、检索、更新或关联单位的一段信息。** 它不是客观世界天然固定的最小单位，也不意味着内容已经被验证为真实。抽取出的声明可能错误、不完整或带有推断；真实性与证据还需要另外处理。【Inferred】

一个记忆单位可能需要这些信息：

~~~text
Memory Unit
+-- 内容：记住了什么
+-- 身份与类型：这是哪个对象，属于什么记录
+-- 时间与适用条件：何时发生、被提及，何时仍有效
+-- 来源与关系：来自哪里，涉及谁，和什么有关
+-- 检索及维护信息：怎样找回，发生变化怎样处理
~~~

实体、时间、来源、关系可以看成记忆的“坐标”：它们决定如何区分、解释、检索和修正信息，不应因为被称作 metadata 就默认可有可无。但并非每种系统或每条记录都必须具有全部字段；必要性取决于用途，未知信息也不能强行填成确定值。【Inferred】

### 6.5 同一条记忆可以有不同表示

| 表示 | 人话 | 可能的形式 |
| --- | --- | --- |
| 内容表示 | 系统究竟记住了什么 | 事实正文、结构化事件、偏好记录 |
| 检索表示 | 用什么去找它 | 增强后的向量输入、关键词、索引 |
| 展示表示 | 最后给人或模型看什么 | 正文加日期、来源引用，或整理后的片段 |
| 关系表示 | 它怎样连接其他对象 | 实体关联、来源引用、事实链接 |

这是职责上的区分，不要求物理保存四份副本；内容与展示可以相同，某些表示也可在读取时生成。【Inferred】

Hindsight 已读的例子是：事实正文与 Embedding 输入可以不同，向量输入会补充日期和实体名。因此“保存的语义内容”和“用于查找的表示”不必相同。具体处理见 [[02_retain_pipeline]] 第 10 项。【Code-verified】

### 6.6 写入路径的八个设计问题

下图是比较框架，不是每个项目必须依次执行的流水线。操作可以合并、交错、跳过或放在后台；例如身份解析与关系建立可能交叉，更新也可能同时触发重新抽取和索引维护。【Inferred】

~~~text
原始经历
   |
   v
输入边界
  1. Capture：何时送入，送多大范围？
  2. Segmentation：收到的内容怎么切？
   |
   v
记忆单位
  3. Extraction / Unitization：留什么，独立单位有多细？
  4. Enrichment：补什么时间、实体、类型和来源？
   |
   v
身份与访问
  5. Identity：和以前哪个人、文档或记忆是同一个？
  6. Representation / Indexing：以后靠什么找回？
   |
   v
关系与变化
  7. Linking：和已有记忆建立什么关系？
  8. Commit / Evolution：新增、合并、替换、删除或保留历史？
~~~

第 5 项还要区分实体身份、文档身份和记忆重复判断；一种匹配成功不能替代另一种。第 8 项表示写入及变化策略，不承诺整批写入是原子事务。

以后比较不同 Memory 项目时，可以按四组提问，每组两个问题：

| 比较组 | 要问的两个问题 |
| --- | --- |
| 输入 | 它什么时候写？一次提供多少上下文？ |
| 单位与组织 | 最基本的 Memory Unit 是什么，带哪些坐标？有没有更高层归纳？ |
| 身份与变化 | 怎样认出同一人、对象或重复内容？怎样处理更新、冲突和历史？ |
| 访问与依赖 | 为 Recall 建了哪些访问路径？底层内容变化后，这些路径与上层归纳怎样同步？ |

这套框架可以把不同架构放在同一张比较表中，不需要先假定大家都必须使用 Fact / Scene / Profile，或者向量、实体和图。组件笔记仍负责说明具体实现；本节只记录经讨论认可的抽象问题，不改变主线程的组件阅读和写入进度。
