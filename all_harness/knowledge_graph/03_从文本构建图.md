## 第一组 从文本片段到候选记录

### 模型这一轮看得到什么

教学假设：“张三在甲公司担任工程师。甲公司开发了产品乙。”

```text
片段编号：chunk-001
文本：张三在甲公司担任工程师。甲公司开发了产品乙。
来源文件：公司介绍.txt
```

普通文档首次抽取按片段处理。请求主要包含抽取规则、实体类型指引、输出模板、可选章节标题路径及当前文本；该路径没有先读取整个现有图，再把全图交给模型理解。【Code-verified】

如果片段1介绍张三，片段2只剩“他负责产品乙的测试”，片段2的首次请求不默认包含片段1的正文或抽取结果。缺少指代依据时，不能可靠认定他就是张三。重叠或额外上下文可能改善情况，但不能默认一定存在。

切分不只影响长度，也影响事实能否被完整理解。

### 程序构造任务

提示词要求识别明确、有意义的实体，输出名称、类型和描述；识别直接、明确的关系，输出端点、关键词和描述，并遵守格式与记录数量限制。【Code-verified】

类型指引提供 `Person`、`Organization`、`Event` 等类别。章节标题路径作为可选背景帮助理解，但提示词要求从正文抽取，不把标题词直接当作正文事实。【Code-verified】

建模选择通过类型指引、字段与规则影响模型产出。模型负责语义判断，任务边界由程序与配置提供。

### 模型输出形式

项目支持分隔符文本与 JSON 两种抽取模式，由配置决定。【Code-verified】

| 模式 | 形式 |
| --- | --- |
| 分隔符文本 | 每行一条记录，字段按标记分隔 |
| JSON | 对象内包含实体列表和关系列表 |

以下为教学示意，没有实际调用模型：

```text
entity<|#|>张三<|#|>Person<|#|>张三在甲公司担任工程师。
entity<|#|>甲公司<|#|>Organization<|#|>甲公司开发了产品乙。
entity<|#|>产品乙<|#|>Artifact<|#|>产品乙由甲公司开发。
relation<|#|>张三<|#|>甲公司<|#|>任职<|#|>张三在甲公司担任工程师。
relation<|#|>甲公司<|#|>产品乙<|#|>开发<|#|>甲公司开发了产品乙。
<|COMPLETE|>
```

实体行包含记录种类、名称、类型、描述；关系行包含记录种类、两个端点、关键词、描述。`<|#|>` 是字段分隔符，`<|COMPLETE|>` 是文本模式结束标记。【Code-verified】

结束标记只说明模型按协议声明本轮结束，不证明没有漏抽。第一次抽取使用抽取角色模型；有效缓存命中时可能直接取得以前的模型结果，详细机制在第二组展开。

### 程序解析与来源附加

模型输出仍是文字，程序将其转换成数据记录，进行名称清理、类型规范化和基础格式检查，附加片段编号、文件路径与处理时间。【Code-verified】

```text
名称：张三
类型：person
描述：张三在甲公司担任工程师。
来源片段：chunk-001
来源文件：公司介绍.txt
处理时间：系统时间信息
```

| 信息 | 来源 |
| --- | --- |
| 名称、类型、描述 | 模型输出 |
| 名称清理、类型小写等规范化 | 程序处理 |
| 片段编号、文件路径、处理时间 | 程序附加 |

检查包含名称、描述是否为空，以及类型的基础合法性。文本解析器尝试修复部分分隔符与换行问题，JSON 路径也有容错解析。详细修复与拒绝行为在第三组展开。【Code-verified】

本阶段返回候选，尚未在这里完成图构建：

```text
当前片段 → 模型输出 → 解析与规范化 → 实体、关系候选
```

候选还会进入补抽、可选检查及后续合并。模型回答结束、解析成功和图构建完成是不同状态。

## 用户设计 缺失上下文报告与定向补齐

本节以下内容是用户提出的设计及共同讨论，不是 LightRAG 当前已经实现的上下文扩张流程。

用户认为抽取提示词可以借用，并提出：模型发现不能消解指代时输出特殊内容；程序检测后扩张输入上下文，同时保留本次任务状态，只补齐“他是谁”，避免对新增材料重复全量抽取。

### 提示词与解析协议配套

抽取提示词、类型指引、字段和解析规则可以作为自建抽取器的起点。增加“需要上下文”状态时，不能只加入一句特殊文本；程序需要识别该状态、取得补充材料、发起定向请求并更新对应候选。

### 首次输出明确候选与待解决项

只看到“他负责产品乙的测试”时，可以报告：

```text
待解决项：第1项
原句：他负责产品乙的测试。
未确定指代：他
缺少信息：负责测试的人员是谁
状态：需要上下文
```

某项人物关系未确定，不意味着必须丢弃当前片段中所有其他明确信息。待解决项作为任务记录保存，不急着把“他”写成真实人物节点。

### 扩大判断材料 保持任务目标

程序取回有依据的上下文，仍只处理原待解决项。例如：

```text
原句：他负责产品乙的测试。
新增上下文：张三是产品乙项目的测试工程师。
待解决问题：“他”指谁？

只处理该问题，不重新抽取新增段落中的全部实体与关系。
```

补充段落可作为候选判断依据，但这句话本身不自动证明指代唯一，需要检查上下文是否足够；有多个可能人物时仍保留未确定。

### 明确保留状态与结果更新

保留模型上下文，需要程序把上一轮请求与结果，或整理后的候选和待解决问题，再传给模型；不能假定独立 API 请求之间自行保留记忆。

成功确定时，模型可以仅返回待解决项编号、指代对象和依据，再由程序补齐原候选。这样的设计仍需稳定识别待解决项与程序去重，不能仅依靠模型不重复的指令。

### 两处来源与未确定状态

“负责测试”可能来自原句，“此人是张三”的依据可能来自补充段落。后续核实需要能回看两处；不能把模型上一轮的猜测当成新增证据。

扩张后仍不能唯一确定时继续保留未确定，不强行选择人物。

## 与 LightRAG 补抽的初步对照

以下为第一组讨论中的对照，当前实现的具体补抽行为见第二组。

| 环节 | LightRAG 普通补抽 | 用户方案 |
| --- | --- | --- |
| 上一轮信息 | 传入首次请求与回答历史 | 保留历史或明确任务状态 |
| 再次目标 | 找遗漏、纠正候选，避免重复正确内容 | 只解决指定未确定项 |
| 新材料 | 当前流程不自动扩张邻近正文 | 根据缺失状态补上下文 |
| 触发 | 配置允许时补抽，受输入预算约束 | 根据需要上下文状态触发 |

LightRAG 补抽提示词要求不重复已经正确、完整的内容，调用也传入上一轮历史；当前没有上述特殊状态驱动的扩张流程。【Code-verified】

第一组讨论曾预告：同一键的首次与补抽候选按描述长度选取，更长的补抽描述才替换；这不是新描述更正确的证明。具体组合和条件见第二组。

## 第二组 补抽 限制 截断与缓存

### 补抽是对同一份材料再检查一次

假设首次抽取漏掉产品乙与开发关系，只得到张三、甲公司及任职关系。程序将首次请求与回答组成历史，再要求模型补充遗漏、纠正需要修复的内容，不重复已经正确、完整的结果。【Code-verified】

补抽可以增加产品乙与开发关系，并引用首次已抽出的甲公司，无须再完整输出该实体。JSON 模式没有需补充内容时，提示词要求返回空实体与关系列表。【Code-verified】

普通补抽没有自动加入邻近正文。它是在已有材料上检查遗漏，不能保证解决证据原本缺失的指代问题。这与用户按需扩张上下文、只处理指定未确定项的方案不同。

### 什么时候进入补抽

**开启后通常每个正常处理的片段都考虑补抽，不先判断首轮是否遗漏。** 当前普通路径的触发条件如下：【Code-verified】

```text
首次抽取并解析
       ↓
补抽配置是否大于0？
  ├─ 否：不补抽
  └─ 是：在输入预算检查启用时估算长度
             ├─ 超预算：跳过并记录警告
             └─ 允许：追加一次补抽
```

默认 `MAX_GLEANING` 为1。当前实现检查配置是否大于0，然后追加一次；设成更大的正数也不在这段代码里循环补抽多次。首次结果完整时仍可进入补抽，由模型返回无新增内容。异常、取消或超出预算会影响这条正常路径。

教学假设：10个片段均正常处理，补抽开启且预算允许，则产生10次首次请求与10次补抽请求。它们是20次逻辑请求；有缓存命中时，实际模型调用次数会减少。

### 首次与补抽候选怎样组合

| 补抽候选 | 程序处理 |
| --- | --- |
| 新实体名或新关系键 | 加入候选 |
| 与已有候选键相同，补抽描述更长 | 替换为补抽候选列表 |
| 键相同，补抽描述更短或同长 | 保留首次候选 |

实体按名称键比较，关系按该阶段的端点元组键比较；代码取两份候选列表第一项的描述长度，决定保留哪组。【Code-verified】

例如“张三在甲公司任职”可能被更长的“张三在甲公司担任工程师”替换。但简短正确的纠正结果也可能无法替换冗长错误的原结果。长度是启发式，不是事实正确性的证明。

这是同一片段的两轮候选组合，不是第②节中多个片段共同更新一条图边的合并。

### 输出数量限制

默认提示词要求每次响应实体与关系合计最多100条，其中实体最多40条；数值可配置。这不是整个文档或图的上限。【Code-verified】

首次抽取要求关系两端都在本次选出的实体中；补抽允许引用首轮已正确输出的实体。实体选择因此影响关系覆盖。

数量限制是提示词要求，不等于此处程序证明模型严格遵守。高密度片段可能只输出模型认为重要的内容；正常结束也不证明已穷尽可抽取事实。

### 补抽输入预算与输出截断

补抽请求包含系统规则、首轮输入与回答、补抽指令，首轮回答越长，下一次输入也越大。

有 tokenizer 且提前检查启用时，程序估算补抽输入；默认预算为20480 tokens，超过就记录警告并跳过补抽，不在这里自动拆分请求或扩张正文。预算设为0或缺少 tokenizer 时，不进行这项提前检查；不代表模型或服务没有上下文限制。【Code-verified】

输出截断则是模型输出额度耗尽、尚未完成。对被标记为截断的回答：【Code-verified】

- 抽取阶段报告知识可能不完整，并汇总截断信息。
- 尝试解析已有输出；完整有效的记录仍可能进入候选。
- 缓存写入路径跳过这份截断回答，避免反复复用残缺结果。
- 若截断后没有可用正文，共享调用路径报错。

这只针对被识别和标记的截断响应，不能把所有漏抽都归因为输出额度。主动选择、语义遗漏和格式问题仍需分别检查。

### 缓存保存请求与模型回答

**缓存将一次请求的标识与回答保存下来，匹配的请求可以复用该回答，减少重复生成的时间与费用。** 它不是事实正确性认证。

教学示例：

```text
第一次：
  请求：从“张三在甲公司担任工程师”中抽取实体和关系。
  模型回答：张三、甲公司、任职关系。
  保存：请求标识 → 回答。

再次进入相同抽取请求：
  查缓存 → 找到回答 → 返回给解析程序。
```

保存的是模型回答文字。命中后仍要解析、附加当前来源并执行后续处理，不能视为图构建整体已经完成。

### 失败重试的例子

```text
首次处理：
  片段1 → 回答成功，缓存已保存
  片段2 → 回答成功，缓存已保存
  片段3 → 调用失败

重试时，若请求匹配且缓存仍可用：
  片段1 → 读取缓存回答
  片段2 → 读取缓存回答
  片段3 → 再调用模型
```

前两个片段不必再次生成。这个例子依赖缓存实际保存并保留、重试请求匹配等条件，不保证所有失败后都能命中。

### 首次与补抽分别缓存

首次请求与补抽请求包含不同的提示词与历史，因此通常对应不同缓存项。重试时两项都可能分别命中，不代表每个片段固定产生两次真实模型调用。【Code-verified】

当前请求标识考虑用户提示词、系统提示词、历史、输出格式及模型/服务标识。改变抽取提示词或新增上下文会影响请求标识；仅原文相同不保证命中。【Code-verified】

旧回答若漏掉时间或有错误，复用后仍可能保留问题。重新执行流程不保证重新调用模型，缓存命中也不提供新增证据。

### 缓存引用与写入限制

抽取缓存需要通过所属片段的缓存引用找到。程序先记录引用，再写缓存内容；无法记录引用时跳过缓存写入并报告，结果仍返回，后续可能需要重新计算。【Code-verified】

持久化、删除和失败恢复的完整契约在维护章节继续，不把这项来源要求当成跨存储事务保证。

### 重复上传与缓存的区别

用户认可缓存在文档可能多次上传时的复用价值。需区分两个阶段：【Code-verified】

| 机制 | 处理什么 |
| --- | --- |
| 文档去重 | 在入队阶段过滤已有文档或相同内容的重复上传，可能不进入抽取 |
| 抽取缓存 | 请求实际再次进入模型调用路径时，复用匹配的回答 |

当前入队代码检查已有文档ID及内容哈希等。重复上传不必然再次调用模型，也不必然是缓存起作用。失败后手动重试等实际重走抽取的情形，是理解缓存用途的直接例子。

### 第二组概念流程

```text
首次抽取或读取缓存
        ↓
解析首次候选
        ↓
补抽启用且预算允许？
   ├─ 否：保留首次候选
   └─ 是：带首轮历史补抽或读取对应缓存
               ↓
       新键加入；同键按描述长度选择
        ↓
交给后续质量检查与合并
```

上图是概念正常路径。异常、取消、截断及缓存写入降级等条件仍分别按上述边界处理。

## 第三组 抽取质量检查与处理

**可解析、忠实于来源、覆盖所需内容，是需要分别检查的性质。** 发现问题与处理问题也不同；发现后可能拒绝、重新抽取、补充上下文或交由人工确认，不保证自动修好。

### 用同一段原文区分问题

教学原文：“2023年，张三在甲公司担任工程师。甲公司开发了产品乙。”

| 抽取结果 | 问题 |
| --- | --- |
| 无法解析的 JSON | 表达格式损坏 |
| 张三开发了产品乙 | 缺少原文依据 |
| 记录任职但未保留2023年 | 时间限制丢失 |
| 只记录任职，未保留开发关系 | 漏掉需要保留的内容 |

不同问题需要不同检查，不能用一次格式校验代替。

### 程序默认处理的格式与字段问题

当前 LightRAG 处理文本字段数量、分隔符和记录种类，检查实体名称、类型与描述，以及关系端点、描述的基础有效性。空端点与自环关系会被跳过，名称与类型被清理规范化，过长名称可能被截短。【Code-verified】

文本解析器尝试修复部分分隔符、换行和关系行误用实体前缀的问题；JSON 解析尝试恢复带围栏、说明或轻微损坏的对象。修复这些格式不等于核实语义。【Code-verified】

JSON 为空或不可恢复时，当前解析器记录警告并返回空候选；无效条目也可能被跳过，不一定让整个处理失败。因此零候选可能是没有合适信息，也可能是解析问题，数量本身不能说明原因。【Code-verified】

### 逐项检查来源支持

```text
候选：张三开发产品乙。
问题：原文哪段支持这项完整陈述？
```

张三与产品乙的名字都出现在原文，不代表两者之间的开发关系成立。需要检查人物、组织、作用方向、否定、时间条件，以及可能、计划等语气是否被忠实保留。

例如不能因张三在甲公司任职、甲公司开发产品，就补出张三开发产品；也不能把“未参与”变成“参与”，或把2023年的状态直接当作当前状态。

这里检查是否忠实表达来源，不等于确认来源在现实中真实。原文自身也可能出错。

### 从原文反查遗漏

查错从输出出发，寻找原文支持；查漏从原文出发，寻找结果中的对应项。

```text
检查输出：这条陈述有什么原文依据？
检查覆盖：原文这项应保留信息在结果哪里？
```

本例应核对任职关系及2023年限制，以及甲公司开发产品乙的关系。只反复验证已有任职关系正确，可能一直看不到开发关系缺失。

检查遗漏之前，需要先约定抽取范围，不要求每个词都成为节点。无错误与无遗漏分别检查；相同输出数量也不代表相同质量。

### 可采用的检查方法

以下是可设计的方法，不是项目默认全部执行的步骤。

| 方法 | 作用 | 局限 |
| --- | --- | --- |
| 程序规则 | 空字段、不允许的类别、部分异常值 | 难以全面判断语义 |
| 模型复核 | 对照原文找无依据陈述、遗漏和条件丢失 | 仍可能判断错误 |
| 人工对照样本 | 整理关键事实与预期，检查输出 | 需要阅读与标注 |
| 截断和警告信号 | 提醒可能不完整 | 信号正常不证明无遗漏 |

评估抽取器可选取代表性文本，先人工整理应保留的信息，再分别检查输出中受支持的比例、应保留信息的找回程度。不能只凭一段漂亮输出认定整体可靠。完整实践与评估仍留在第⑧节。

### 可选质量检查接口

`kg_extraction_validator` 在首次、补抽与候选组合之后、图合并之前被调用。它接收片段编号、正文、实体候选和关系候选，返回处理后的实体与关系候选。默认 `None` 不进行该额外检查。【Code-verified】

```text
首次与补抽候选组合
         ↓
可选检查：正文 + 实体候选 + 关系候选
         ↓
处理后的候选
         ↓
后续处理与合并
```

检查逻辑由调用方提供，可采用程序规则或调用模型，支持同步、异步。函数报错或返回结构不符合约定，会使片段处理失败，不会静默忽略。【Code-verified】

接口收到抽取所见的正文，内部解析标记已清理，不包含作为背景提供的章节标题路径。应按这个证据范围设计规则。【Code-verified】

文档示例检查规范化后的名称是否出现在规范化正文中，只能过滤部分异常名称。别名、缩写与指代消解可能让合法名称不直接出现在当前正文；名称出现也不能证明关系正确，规则更不能证明无遗漏。

### 删除实体时也要检查关系端点

```text
原候选：
  实体：张三、甲公司
  关系：张三任职于甲公司

只删除张三后：
  实体：甲公司
  关系：张三任职于甲公司
```

后续合并可能按残留的关系端点补建类型为 `UNKNOWN` 的张三节点。因此若意图拒绝该名称，需同时过滤实体和关系端点，核心接口不自动完成该过滤。【Code-verified】

某一片段的拒绝也不自动成为全篇拒绝，其他片段仍可能保留该名称。需要根据规则的预期范围保持一致。

该接口处理模型候选；程序根据多模态元数据补建的节点与关联在之后处理。其具体行为留到第四组，不能把第三组视为这一部分已经完成。

## 共同讨论 抽取器在构图中的位置

用户认为本组为前面的抽取做兜底，包括抽错、抽漏时怎样检查、修复，并提出从比较健全的实体与关系抽取器切入构建知识图谱。

共同确认：在从非结构化文档构图的路线中，抽取是最关键环节之一，决定哪些原文信息以何种含义进入系统。存储和检索不会自动恢复未抽到的内容，错误陈述也可能被后续反复使用。

补充边界：发现错误不等于自动修复；LightRAG 默认只处理部分格式问题，完整语义检查与修复策略还需设计。抽取也不是唯一关键环节；忠实抽出的两个同名人物若被错误合并，图仍会出错，身份、时间、来源和冲突处理也须保证质量。

建议的工程切入方式是先约定任务与表示，用少量代表性文档建立可检查的抽取器，尽早接通身份判断、合并、存储与查询，再根据结果迭代。不是先无限完善抽取器、等其完整才查看后续需求。

```text
任务问题 → 需要保留的结构 → 小规模抽取器
                                 ↓
                  身份判断、合并、存储与查询
                                 ↓
                    检查结果，改进抽取与建模
```

这是一项适用于本学习路线的设计讨论。来自数据库、业务记录或人工录入的图谱不一定需要模型文本抽取；不能把当前路线当作所有图谱的必经过程。
