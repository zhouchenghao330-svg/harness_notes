# 图的建模

> 第②节。三组约定入门内容及岗位建模、关系合并、列表与事件节点补充均已共同阅读、确认理解并写入。本轮清单已完成，不表示穷尽图建模方法。首次记录：2026-10-13；更新日期：2026-10-14。返回 [[all_harness/knowledge_graph/00_学习目录|学习目录]]。

**建模是在决定系统用什么结构表达信息，以便之后按任务需要查找、连接和维护。** 业务决定需要哪些表达能力，原文证据决定具体能够写入哪些陈述。

## 第一组 从问题出发决定节点和属性

### 岗位既可以是属性，也可以是节点

教学假设：“张三在甲公司担任工程师。”

如果主要需要知道员工在哪家公司工作、担任什么岗位，可以把岗位附在任职关系上：

```text
[张三] ──任职于──→ [甲公司]
          岗位：工程师
```

加入“李四在乙公司担任工程师”，可以建立另一条带有相同岗位值的任职记录。程序仍然可以筛选岗位值为工程师的记录，找出张三和李四。

**某个信息需要被查询，不意味着它一定要成为节点。属性也可以被查询和建立索引。**

如果要建立职业知识库，记录人员的职业，以及职业要求、技能、课程等关联，把工程师作为独立职业对象会更方便：

```text
[张三] ──从事职业──→ [工程师] ←──从事职业── [李四]
                         │
                         └── 可以继续连接职业要求、课程等信息
```

新增的要求或课程仍需要实际资料支持。设计出可连接的位置，不等于已经有了对应事实。

| 表示方式 | 工程师怎样存在 | 更方便处理的任务 |
| --- | --- | --- |
| 属性 | 每条任职记录里的岗位值 | 保存、筛选具体岗位 |
| 节点 | 独立的职业对象 | 连接人员、技能、课程和职业分类 |

节点的价值在于让对象可以独立识别、描述、连接和维护。共享一个职业节点，也方便统一管理这个职业的相关信息。

### 抽象概念也可以成为实体

实体可以是人、公司和产品，也可以是职业、技能、理论等抽象对象。是否成为节点，不取决于能否看见或触摸，而取决于它是否值得独立记录并与其他对象建立关系。

不能因此把文本里的所有概念都抽出。应围绕系统要回答的问题，判断哪些对象需要独立表示。

### 表示复杂度与后续使用

只为显示姓名时，把姓名作为属性通常足够；额外建立字符串节点未必提供有用的能力。反过来，若公司、岗位和技能全塞进人物描述，内容仍然存在，但按这些条件准确操作时还需要解析文字。

决定是否拆出节点或独立字段，需要检查它是否会参与核心查询、是否需要连接其他对象，以及是否需要独立维护。

### Schema 是表达结构的约定

开始录入大量资料前，可以先约定对象类型、关系和需要保存的信息。例如：

```text
对象类型：人、公司、产品

关系：
  人 ──任职于──→ 公司
  公司 ──开发──→ 产品

附加信息：
  任职关系可以记录岗位
  每项陈述需要保留来源
```

这类结构规则通常称为 Schema。它帮助不同资料使用一致的表示，减少同一含义被写成很多种结构所带来的查询负担。

规则需要服务任务并可随需求修订。例如遇到在大学任教的人员，可能需要把公司类型扩展为更一般的组织类型。规则本身不保证录入内容真实。

### LightRAG 的表示选择

将抽取交给模型，仍然需要表达规则；规则会进入提示词、类型指引、输出格式和程序处理逻辑。

当前 LightRAG 普通文档路径提供实体类型指引，用名称、类型和描述表示实体，用关键词与描述表达关系。它没有默认为所有领域生成岗位、学历、产品型号等专用字段。【Code-verified】

这样可以接收不同领域的文本，但需要按专用字段严格查询时，不能假定对应结构已经自动建立。“容易承载丰富文本”与“可以按明确字段准确操作”是需要分别检查的能力。

## 岗位建模的共同讨论

用户对节点与属性选择的理解：

> 按照我的理解 并不是一定要成为节点 对每个员工的属性附加值 也可以增加岗位这个字段 记录他们的实际岗位
> 但是如果需要作为职业要求和培训课程 节点会更加合适

用户进一步提出：

```text
张三 --(目标岗位)--> 工程师
```

主判断正确，补充确认了以下两个边界。

### 当前岗位与目标岗位表达不同陈述

“目标岗位”表达张三希望成为工程师或把工程师设为目标，不能仅凭“张三在甲公司担任工程师”得到该关系。后一句支持实际任职。

如果另有原文说“张三目前担任技术员，希望转岗成为工程师”，则可以分别保存：

```text
[张三] ──当前岗位──→ [技术员]
[张三] ──目标岗位──→ [工程师]
```

同样的节点，关系含义不同，就会表达不同陈述。节点或属性的选择属于表示设计；当前岗位或目标岗位的选择还涉及是否忠实于来源。

把实际岗位简化为“张三—担任岗位—工程师”，也要意识到公司信息尚未表达完整。将人员、公司、岗位与具体任职经历一起表示的例子，见第三组的独立任职记录。

### 岗位属性应附在适当对象上

系统只记录单一当前岗位时，可以将岗位作为员工属性。若要记录不同公司、不同时期的岗位，应考虑放在对应任职记录中，避免相互覆盖。

## 第二组 关系含义 方向与 LightRAG 的表示

### 同一对实体可以有不同联系

教学假设：“张三在甲公司任职。张三投资了甲公司。”

```text
[张三] ──任职于──→ [甲公司]
[张三] ──投资──→   [甲公司]
```

端点相同不代表陈述相同。只知道两个实体相连，还需要知道它们具体有什么联系。

### 语义方向与查找方向

“甲公司投资乙公司”不等于“乙公司投资甲公司”。投资、收购等陈述需要区分两端角色，不能任意交换。

合作联系可以具有对称含义：“甲与乙合作”和“乙与甲合作”表达同一项联系。但这不说明合作中的责任和收益相同。

```text
有语义方向：甲公司 ──投资──→ 乙公司
对称联系：  甲公司 ──合作──  乙公司
```

从张三查任职公司，或从甲公司查任职人员，都是使用同一项任职信息。能从两端查找，不代表关系含义对称。

### 有向与无向存储

| 存储方式 | 图结构保存的连接 |
| --- | --- |
| 有向边 | 区分起点和终点，A 到 B 与 B 到 A 是不同方向 |
| 无向边 | 保存 A 与 B 相连，交换两端仍是同一条连接 |

系统还可以在边上保存类型和文字描述。底层使用无向边时，有方向的陈述可以留在描述里，但不能仅靠连线确定谁作用于谁。

LightRAG 的图存储契约按无向关系处理，默认 NetworkX 后端使用 `nx.Graph()`。普通文档合并按排序后的实体对分组，交换端点进入同一组。【Code-verified】

```text
[张三] ────────── [甲公司]
         关键词：任职
         描述：张三在甲公司任职。
```

此前教学图中的箭头表达语义，不代表 LightRAG 内部有一条对应的有向、独立关系边。无向连接更不代表“甲公司也任职于张三”。

### 同一对实体的多种联系如何共存

一种设计可以分别保存任职和投资两条独立关系。LightRAG 普通文档路径则把同一对实体的候选关系集中到一条边上，合并关键词和描述。【Code-verified】

```text
[张三] ────────── [甲公司]
         关键词：任职、投资
         描述：张三在甲公司任职，并投资了甲公司。
```

上面是教学示意，实际描述可能是多段拼接或模型摘要。多种联系仍可在文字中分别表达，但不是按关系类型分别保存的独立边。

检索“张三与甲公司的相关信息”可以使用这份材料。若要求只操作投资关系、让任职独立保留，就不能假定已有单独的投资边，需要进一步区分描述中的陈述或采用其他结构。

## 补充 同一对实体的具体合并流程

用户追问多种关系如何合并。本补充沿普通文档写入路径说明；并不把实体合并、改名或所有手工写入路径等同于这一流程。

### 输入示例

假设模型从三个片段得到以下候选：

| 来源 | 两个实体 | 关键词 | 描述 |
| --- | --- | --- | --- |
| 片段1 | 张三、甲公司 | 任职 | 张三在甲公司担任工程师。 |
| 片段2 | 张三、甲公司 | 投资 | 张三投资了甲公司。 |
| 片段3 | 甲公司、张三 | 任职 | 张三在甲公司担任工程师。 |

### 按实体对分组并读取已有边

程序排序两端名称后分组。三条记录进入同一组，关系关键词不参与分组；不是先让模型判断任职与投资是否同义。若已有边，会读取旧关键词、描述与来源加入合并。【Code-verified】

### 关键词取并集

任职、投资、任职合并后保留任职和投资。该步骤由程序完成，删除相同关键词，不自动进行同义词合并。任职与工作可能同时保留。【Code-verified】

### 描述按文字去重

片段1与片段3的描述相同，只保留一份描述；旧描述与新描述也会一起去重，防止重新处理文档时不断追加相同文字。【Code-verified】

比较的是清理后的字符串，不是语义相似度。例如“张三在甲公司任职”和“张三是甲公司的员工”不会仅凭含义接近，在此阶段自动合成一条。【Code-verified】

### 直接拼接或调用模型摘要

并非每次合并都调用模型。当前代码默认行为如下，参数可以配置：【Code-verified】

| 描述情况 | 处理 |
| --- | --- |
| 只有一条描述 | 清理后直接保留 |
| 多条描述，数量少于8条且总长度少于1200 tokens | 使用分隔符拼接 |
| 达到摘要条件 | 调用模型整合 |
| 输入规模很大 | 按上下文预算分组摘要，再继续整合 |

8条指去重后的描述片段数量，不是关系种类或来源数量。摘要输入预算默认12000 tokens，输出建议长度默认600 tokens；这些是代码默认值，不代表已检查当前运行实例的有效配置。

示例只有两条短描述，通常直接保存为：

```text
张三在甲公司担任工程师。
<SEP>
张三投资了甲公司。
```

达到摘要条件时，抽取角色模型被要求整合重要信息，可能生成“张三在甲公司担任工程师，同时也是甲公司的投资者”。这是教学示意，不是实际模型调用结果。【Code-verified：调用角色与提示词；示例输出为教学假设】

之后再有新信息，参与合并的可能是旧摘要加新描述，不保证边上仍保存原先每条描述的独立形式。

### 来源分开合并

片段1与片段3虽然描述重复，来源编号仍可以同时保留。删除重复文字，不等于删除支持它的来源。【Code-verified】

```text
描述：任职描述、投资描述
来源：片段1、片段2、片段3
```

边上保存的是整个实体对的来源集合，不能直接当成任职与投资分别精确绑定来源的逐条事实账本。核实某个说法仍可能需要回读原文。

### 更新边和关系向量记录

程序将合并后的信息更新到一条关系边，并更新其对应的关系向量记录。【Code-verified】

```text
同一实体对的候选记录 + 已有边
                ↓
关键词取并集、描述按文字去重、来源合并去重
                ↓
描述较少：拼接；达到条件：模型摘要
                ↓
更新一条关系边和对应向量记录
```

这张图表达概念流程，不是跨存储事务或全部写入时序的保证。来源限额会在描述合并前影响本次可参与合并的候选；具体限制如下。

### 冲突与来源限额

**合并不保证自动解决矛盾。** “张三仍在甲公司任职”和“张三已离开甲公司”，可能被直接并排保存。摘要提示词要求模型处理冲突、保留不确定性，但这不是可靠的事实核验机制。【Code-verified】

默认每条关系在边上保留的来源编号上限为200，策略 `KEEP` 优先保留较早来源。达到上限后，一些新来源的描述会被过滤；若没有候选剩下，满足跳过条件时直接返回旧边。因而不能假定每条新陈述都会进入边描述。【Code-verified】

另有 `relation_chunks` 来源跟踪存储记录完整片段列表，它与图边上受限的来源列表不同。跟踪中存在来源，也不能自动证明该来源的每项陈述已经完整进入边描述。【Code-verified】

## 第三组 时间 适用条件与事件表示

### 时间需要说明它描述什么

教学假设：

> 2022年1月至2023年12月，张三在甲公司担任工程师。
> 2024年1月至2024年6月，张三在甲公司担任产品经理。

只保存张三与甲公司的任职连接，会丢掉岗位和时间。将两个岗位与两个时间范围分别列出，也没有明确保留哪个岗位对应哪个时期。

假设2026年才导入这份资料：

| 时间 | 描述什么 |
| --- | --- |
| 2022年1月至2023年12月 | 张三担任工程师的时期 |
| 2024年1月至2024年6月 | 张三担任产品经理的时期 |
| 2026年导入 | 系统何时收到资料 |

**记录时间描述系统处理，事件或状态的时间描述现实经历。** 数值可能恰好相同，但含义不能等同。较新的记录也可能记载较早的事情，不能按导入时间推断当前任职状态。

时间值还需要明确语义。“2024年7月”可能是入职时间、离职时间或资料发布时间。一次入职是某时发生的事情；一段任职则是持续状态，可以有开始与结束时间。

**没有结束时间，不等于已经证明持续到今天。** 资料只说张三于2024年7月加入乙公司，不能据此排除后来的离职。回答当前状态仍需要检查资料覆盖范围和后续信息。

### 条件限定陈述的适用范围

教学假设：“在产品乙项目中，张三临时代任负责人，直到李四返回。”

只保存张三担任负责人，丢掉了项目范围、临时性质和结束条件，可能被错误扩大成一直担任负责人或负责整个公司。

```text
人员：张三
职责：负责人
适用范围：产品乙项目
性质：临时代任
结束条件：李四返回
```

结束条件不一定能立即转成日期。原文没有说李四何时返回，就不能自行补出结束日。

时间与条件都限定陈述在哪个范围内成立。删掉限制，可能改变原句含义。

### 将每段经历独立表示

简单情形可以给一条独立任职关系附加岗位和时间属性。如果同一个人在同一家公司经历不同岗位或多次任职，应分别保留各段信息，避免互相覆盖或混配。

一种通用设计是把每段经历作为独立对象：

```text
[任职记录1]
    ├─ 任职人员 → [张三]
    ├─ 任职组织 → [甲公司]
    ├─ 岗位     → [工程师]
    ├─ 开始时间：2022年1月
    └─ 结束时间：2023年12月

[任职记录2]
    ├─ 任职人员 → [张三]
    ├─ 任职组织 → [甲公司]
    ├─ 岗位     → [产品经理]
    ├─ 开始时间：2024年1月
    └─ 结束时间：2024年6月
```

每条记录将人员、公司、岗位和时间绑定。查询2023年的岗位，可以先找到覆盖该时期的记录，再读取岗位。

这些是通用建模示例，箭头表示语义；不是 LightRAG 默认自动生成的任职记录结构。

### 分开的列表与结构化记录列表

用户指出下面的表示无法确认对应关系：

```text
岗位：a、b
时间：c、d
```

不能确定是a对应c、b对应d，还是另一种配对。仅依赖列表顺序也容易在更新时出错。

问题不在于列表必然容量小，而是这两个独立列表没有保留显式对应关系。改成完整记录列表即可表达配对，并继续增加公司、来源等字段：

```text
任职经历：
  - 岗位：a，时间：c
  - 岗位：b，时间：d
```

结构化记录列表也能承载丰富信息。把经历作为图节点，则进一步方便它与人员、公司、岗位等对象连接。选择哪种表示仍要结合查询和维护需求。

### 一次事件与一段经历

一次入职事件与持续任职经历分别表达不同内容：

| 表示 | 可以记录的信息 |
| --- | --- |
| 入职事件 | 谁加入哪个组织，何时发生 |
| 任职经历 | 谁在何组织担任何岗位，持续哪个时期 |

两者可以关联，但不能完全互相替代。知道一次入职发生，不代表已知道随后全部岗位变化。

经历或事件成为节点，可以继续连接参与者、项目、地点与来源，将信息围绕同一次事情或同一段经历组织。不要求每条简单陈述都增加事件节点；是否需要取决于多次发生、时间条件和参与对象等需求。

### 事件节点将信息绑定到同一次事情

教学假设：“甲公司组织了产品乙发布会。张三在会上讲解产品，李四负责现场演示。”

```text
[甲公司] ──组织──→ [产品乙发布会]
                         └──发布的产品──→ [产品乙]

[张三] ──参与──→ [产品乙发布会]
        行为：讲解产品

[李四] ──参与──→ [产品乙发布会]
        行为：现场演示
```

这里的事件节点表示这一次发布会，是组织者、参与者、行为和产品共同关联的对象。如果两人还参加另一次发布会，建立不同事件对象可以分别保留任务，避免混淆。

**参与事件不自动说明做了什么。** 原文只说张三参加，就只能记录参与，不能补出讲解职责。行为、角色与职责都需要依据。

**事件成为节点不保证描述已经完整。** 它提供组织信息的结构，实际保留多少取决于原文、抽取和建模。没有地点资料，不能因为有事件节点就补出地点。

### LightRAG 时间字段的实际含义

已核对普通文档抽取与关系合并路径：【Code-verified】

| 字段 | 当前路径中的含义 |
| --- | --- |
| 抽取记录的 `timestamp` | 模型调用完成时间；命中缓存时使用缓存记录的时间 |
| 合并后图边的 `created_at` | 本次关系合并写入过程中取的系统当前时间 |

这些值不是从原文抽取的入职、离职或有效时间。此路径的 `created_at` 也不应直接理解成永久不变的首次创建时间。

普通关系抽取字段没有默认要求独立输出有效开始、有效结束和适用条件。这些信息可能留在自然语言描述中；后续合并或摘要仍需保留它们。存在系统时间字段，不代表原文时间已经结构化。【Code-verified】

默认类型指引包含 `Event`，模型可以抽出事件实体。但允许事件成为实体，不等于自动形成完整经历结构；需要检查是否识别了同一次事件，以及参与者、行为和时间是否被正确关联。【Code-verified：类型指引与输出字段；结构完整性是本组的检查要求】
