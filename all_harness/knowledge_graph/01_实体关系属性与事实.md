# 实体 关系 属性与事实

> 第①节。约定的基本概念、表示的信息损失，以及 LightRAG 模型与程序分工补充已共同阅读并获得理解确认与写入授权。记录日期：2026-10-13。返回 [[all_harness/knowledge_graph/00_学习目录|学习目录]]。

**把文本变成知识图谱，是把谈论的对象、对象之间的联系，以及相关信息明确地表示出来。** 表示方式决定系统以后还能知道什么；画出连接不等于证明所有沿连接想出的结论。

## 从两句话开始

教学假设：

> 张三在甲公司担任工程师。甲公司开发了产品乙。

```text
[张三] ──在……工作──→ [甲公司] ──开发──→ [产品乙]
```

这里的箭头表达句子的语义方向，不代表 LightRAG 底层把它保存成有向边。语义方向与项目的无向图存储在第②节进一步讨论。

## 实体与类型

实体是需要独立识别、记录和谈论的对象，通常以节点表示。

| 实体 | 类型的通用示意 |
| --- | --- |
| 张三 | 人 |
| 甲公司 | 组织 |
| 产品乙 | 产品 |

“张三”是具体对象，“人”是它所属的类型。类型和具体实体不能混淆。算法、事件和概念也可以作为实体；是否需要独立表示，要结合后续任务判断。

上述类型是概念示意，不等于 LightRAG 的默认类别名称。例如默认类型指引包含 `Artifact`，不能假定一定有一个名叫 `Product` 的类别。

## 关系与三元组

关系表达两个实体之间的联系，通常用边表示。只知道两个节点相连，还不能知道它们是任职、投资或其他关系。

```text
主体 ──关系──→ 客体

张三 ──任职于──→ 甲公司
甲公司 ──开发──→ 产品乙
```

“张三、任职于、甲公司”三个部分构成一个简单三元组。三元组可以表达一项简单陈述，但实际系统可能需要额外保存时间、条件和来源。

## 属性可以描述实体或关系

属性是附在实体或关系上的信息。实体可以带有名称和类型；任职关系可以带有岗位和开始时间。

```text
张三 ──任职于──→ 甲公司
        岗位：工程师
```

岗位与具体任职经历有关。若以后出现“张三在乙公司担任产品经理”，只在张三节点上放一个岗位字段，就容易混淆他在不同公司的职位。

信息放在哪里会影响后续理解。原文没有提供的时间不能自行补出；把岗位独立成关系属性是一种通用设计，并非 LightRAG 普通抽取路径默认生成的字段。

## 事实陈述与表示方式

| 概念 | 本例中的含义 |
| --- | --- |
| 实体 | 张三、甲公司、产品乙这些对象 |
| 关系 | 任职、开发这些联系 |
| 属性 | 对象或联系的类型、岗位、时间等信息 |
| 事实陈述 | “张三在甲公司担任工程师”这一项具体说法 |

“任职于”只是关系名称；确定谁任职于哪里，才形成一项具体陈述。

**写进图里不等于已证明真实。** 原文可能有误，模型也可能抽错。系统实际保存的是从某个来源获得的陈述，需要另外检查来源与抽取质量。

```text
记录了什么：张三在甲公司担任工程师。
根据什么记录：文档A中的某段文字。
```

来源如何支持维护和修订，在第⑦节继续讨论。

## 沿图查找与推断的区别

问题：“张三任职的公司开发了什么产品？”

```text
找到张三
   ↓ 沿任职关系查找
找到甲公司
   ↓ 沿开发关系查找
找到产品乙
```

连续经过两条关系，可以称为两跳查找。但现有信息不能证明“张三参与开发了产品乙”。他可能负责其他项目。

**图上存在路径，只说明这些对象能沿已有关系连接起来；路径两端之间的新陈述仍需要依据。**

## 表示保留和丢失了什么

最初的简图保留了三个对象与两项联系，却没有显示岗位和来源。若系统只保存这张简图，相关信息就会丢失；若关系附有描述和来源引用，则能保留更多内容。

因此，构图时要检查哪些信息被明确表示、哪些只留在文字里，以及哪些被丢掉。检索成功不能自动恢复表示时已经丢失的信息。

## LightRAG 中模型与程序的分工

本节只确认普通文档自动抽取路径的基本分工，不代表第③节完整抽取流程已经共同读完。【Code-verified】

| 内容 | 模型负责 | 程序负责 |
| --- | --- | --- |
| 实体抽取 | 判断哪些对象值得提取，给出名称 | 清理名称、检查输出格式 |
| 实体信息 | 从文本生成实体描述 | 附加来源片段、文件路径等信息 |
| 实体类型 | 根据提供的类型指引选择类别 | 清理类型；合并时按规则选取类型 |
| 实体关系 | 找出关联实体，生成关系关键词和描述 | 解析、检查、合并并写入图 |

程序把文本、类型指引和输出要求放入提示词，模型返回实体与关系候选。程序随后将候选转换为记录，附加来源并进行合并。

```text
程序提供文本、类型指引和输出要求
                 ↓
模型提出实体、类型、描述和关系
                 ↓
程序解析、清理、附加来源、合并
                 ↓
必要时让模型整理描述
                 ↓
程序保存图和相关索引
```

### 类型体系与具体分类

默认类型指引包括 `Person`、`Organization`、`Location`、`Event`、`Concept` 等，并提示无法归类时使用 `Other`。类型指引可以配置；某个实体属于哪一类，主要由模型判断。【Code-verified】

提示词约束不等于程序强制枚举。当前类型处理会检查空值、特定不合法字符、保留名称等，并去空格、转小写；它没有逐项检查类型是否属于默认类别列表。【Code-verified】

合并同一实体时，程序根据本次参与合并的候选类型，加上已有节点类型的出现次数选择一个类型。这不是对所有历史来源重新投票，也不是另一次模型分类。【Code-verified】

### 实体信息与独立字段

普通抽取主要以名称、类型和自然语言描述表达实体。岗位、学历等信息可能保留在描述中，不会默认全部生成独立属性字段。多个片段的描述会经过程序去重、组合；满足一定长度或数量条件时，会再调用模型整理摘要。【Code-verified】

关系也保存关键词与自然语言描述。例如“张三在甲公司担任工程师”可能作为完整关系描述保存，不能假定岗位已成为独立字段。【Code-verified】

来源片段编号、文件路径与处理时间信息由程序附加。处理时间不等于原文所描述事件的发生时间。【Code-verified】

### 基础检查与事实正确性

格式齐全的错误关系仍可能通过基础处理。例如把任职误抽成投资，并不一定能由格式检查发现。项目提供可选的抽取质量检查接口，具体检查逻辑由调用方提供；不能把它视为默认启用的事实验证机制。【Code-verified】

### 范围例外

调用方可以通过 `ainsert_custom_kg()` 直接提供已经构建好的实体和关系；多模态路径也有程序根据附加元数据补建节点与关联的操作。因此不能把项目的每个节点和每条边都归因于模型生成。【Code-verified】这些路径的完整行为留到后续对应章节。
