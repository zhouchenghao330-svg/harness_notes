# Hermes Agent 02.5：Agent Loop Repair

> 状态：已按当前 checkout 的代码完成第一版阅读。本文专门记录“模型响应没有形成一个可接受的正常 turn”时，Hermes 如何修复、重试、继续、降级、清理和收尾。
>
> 研究日期：2026-08-28

## 1. 先给结论：Hermes 不是只有一个 retry

Hermes 的恢复不是简单的：

~~~text
失败 → 再问一次模型
~~~

它实际上在修复不同层次的东西：

~~~text
模型 / Provider 层
  ├─ 连接断了、超时、SSE 没有结束
  ├─ HTTP 401 / 429 / 5xx
  ├─ context overflow / payload too large
  └─ Provider 不接受某个 reasoning / tool / compaction 字段

响应 / 语义层
  ├─ 只有 reasoning，没有可见正文
  ├─ reasoning scratchpad 没闭合
  ├─ 输出长度截断
  ├─ 模型说要调用工具，但结构化 tool_calls 为空
  └─ 模型说“我接下来会做”，但没有真的行动

协议 / 历史层
  ├─ assistant(tool_calls) 缺 tool result
  ├─ 孤儿 tool result
  ├─ 连续 user / assistant 消息
  ├─ 重试脚手架污染 transcript
  └─ 已经展示的回答没有落到 SessionDB

用户体验 / 生命周期层
  ├─ 已经流出的 partial text 不能重复拼接
  ├─ retry 期间要告诉用户正在 reconnect / continue
  ├─ stop gate 可能要求再做一次验证
  └─ 清理资源失败不能吞掉已经得到的答案
~~~

所以，本文说的“恢复”可能是在恢复：

| 恢复对象 | 具体恢复什么 |
| --- | --- |
| Provider request | 重新建 client、换 credential、换 provider、重发请求 |
| Model continuation | 让模型从未完成的输出继续，或重新给它一个明确 nudge |
| Tool protocol | 补齐 tool result、移除错误调用、修复 role alternation |
| Transcript | 丢掉临时 retry 行，保留真正的 assistant/tool 历史 |
| UI stream | 避免 partial 文本重复，发出 reconnect/continue 状态 |
| Turn lifecycle | 继续同一个 `run_conversation`，或以 partial/failed 结果安全结束 |

## 2. 三份状态：不要把“模型看到的”和“用户看到的”混为一谈

Hermes 同时维护三种视图：

~~~text
                 ┌────────────────────────┐
                 │ canonical messages     │
                 │ 规范历史 / 持久化事实   │
                 └──────────┬─────────────┘
                            │ clone + project
                            ▼
                 ┌────────────────────────┐
                 │ api_messages           │
                 │ 本次请求的可变副本       │
                 └──────────┬─────────────┘
                            │ transport format
                            ▼
                 ┌────────────────────────┐
                 │ provider wire payload  │
                 │ 真正发给模型的字段       │
                 └────────────────────────┘

stream deltas / reasoning callbacks ─────→ UI
canonical append + SessionDB flush ─────→ durable transcript
~~~

这解释了许多看似矛盾的行为：

- UI 可以已经显示了一段 reasoning，但它未必已经作为一条完整 assistant message 写入 SessionDB；
- Hermes 可以为了 Anthropic 重试而从 `api_messages` 删除 `reasoning_details`，但不应删除 canonical history 中的原始记录；
- 一个 synthetic user nudge 可以进入下一次模型请求，但在 finalization 时被移除，不成为用户未来 `/resume` 的真实历史。

      │       │                 │          │
      │   native replayable   plain/坏掉   │
      │       │                 │          │
      │   continuation       丢弃坏响应     │

                                             │

                                  有结构化 tool_calls？

把你给的图单独翻译成 Hermes 语义，就是：

~~~text
                    模型异常停止
                         │
              response / finish_reason 先判断
                         │
          ┌──────────────┴──────────────┐
          │                             │
      没有可用 reasoning               有 reasoning
          │                             │
   empty / partial /              reasoning 是否“可重放”？
   provider retry                  /                 \
                                  是                   否
                                  │                    │
                       是 native provider state？    丢弃本次坏响应
                         /             \
                       是               否
                       │                 │
                continuation replay   nudge / fresh retry
~~~

注意：这里“reasoning 合法”不是说模型的思考内容在语义上正确，而是说它满足当前 Provider 的协议要求，仍然有可用的 replay carrier、签名或完整消息结构。

## 4. 两个 retry 层次

### 4.1 API request retry：同一个外层调用槽位再发请求

`conversation_loop.py` 在每个外层 API call slot 内有一个 `while retry_count < max_retries`���它处理的是 Provider 层问题：

~~~text
构造 api_kwargs
      │
      ▼
发起一次 Provider request
      │
      ├─ 成功且响应可解析 → 离开 inner retry
      └─ 失败
           ├─ 识别错误类型
           ├─ 只做一次性的局部修复？
           ├─ 重建 client / refresh credential？
           ├─ compress / fallback？
           └─ backoff 后重新 request
~~~

这一层通常不把一条假的 user 消息写进对话。它尽量用相同的 canonical messages 重建 request copy，只改变 transport、Provider 字段或请求参数。

### 4.2 Turn continuation：外层 Loop 继续下一次模型调用

有些响应“HTTP 成功了”，但没有构成可接受的最终回答，例如 reasoning-only、空响应、模型声称要用工具但没有发 tool call。这时不是 inner API error，而是：

~~~text
本次 response 已经返回
      │
      ▼
需要给模型追加 interim / nudge
      │
      ▼
messages 形成下一次合法输入
      │
      ▼
outer loop continue
~~~

这两层不要混淆：

| 情况 | 主要循环 | 典型处理 |
| --- | --- | --- |
| 连接断开、HTTP 429、签名 400 | inner retry | 重连、退避、刷新、换 provider、改 wire |
| reasoning-only、post-tool empty | outer loop continuation | prefill、user nudge、bounded continue |
| `finish_reason=length` | outer loop 的截断分支 | 保存 fragment，追加 continuation nudge，重新调用 |

## 5. 你最关心的 reasoning 状态：到底能不能 replay？

### 5.1 “完整 reasoning”不等于“可以安全 replay”

Hermes 内部会保存 `reasoning`、`reasoning_content`、`reasoning_details`，某些 Responses Provider 还会保存 `codex_reasoning_items` 和 `codex_message_items`。它们的性质不同：

~~~text
普通 reasoning / reasoning_content
  = 轨迹、显示和部分 Provider 的 echo 字段
  = 不是通用的“继续生成句柄”

Provider-native replay state
  = Codex Responses 的 reasoning/message items
  = 可能包含加密内容、item id、phase 等
  = Provider 认可时才能原样 replay

Anthropic thinking block
  = 需要合法的 block 形状和签名
  = 上游改写、压缩、合并后可能失效
~~~

因此，判断条件不是“有没有字符串”，而是：

| 响应状态 | 能否 replay | Hermes 的方向 |
| --- | --- | --- |
| Codex 的完整 `codex_reasoning_items` / `codex_message_items` | 通常可以，前提是 Provider 仍接受 | 保留 interim carrier，继续 Responses 请求 |
| 普通结构化 `reasoning`，没有 native carrier | 不能假定可以 | 可能作为 API echo 或轨迹保存，但不能伪造 native replay |
| 已闭合的 inline `<think>...</think>` | 只能按普通 content/Provider policy 处理 | 先判定是否有可见正文，必要时走 prefill/empty retry |
| 未闭合的 reasoning scratchpad | 不可可信 replay | 不把坏消息加入历史，fresh retry |
| 加密 reasoning 被 Provider 拒绝 | 当前 carrier 已失效 | 禁用 replay、清理 cached items、重试一次 |
| Anthropic thinking signature 失效 | 原签名不能继续使用 | 仅从 `api_messages` 去掉 `reasoning_details`，重试 |

### 5.2 Hermes 并不会默认“关闭 thinking 再伪造它的思考”

你的推理里有一部分很接近，但不能概括成统一规则：

~~~text
完整 reasoning
  ≠ 自动关闭 thinking
  ≠ 自动把 reasoning 当成模型已经完成的隐藏前缀
~~~

Hermes 的具体行为取决于响应和 Provider：

1. **Codex Responses `finish_reason=incomplete`**：如果响应带有可重放的原生 item，就保留这些 item，下一次请求继续；如果没有任何可重放 item，单纯把同一请求再发一次可能是 byte-identical，所以追加一个 user-role continuation nudge，让下一次请求发生真实变化。
2. **普通 Chat Completions reasoning-only**：Hermes 先尝试 thinking-only prefill，最多两次；但发送前仍会经过 Provider-specific 的 thinking-only 清洗。对不接受孤立 thinking block 的 Provider，`drop_thinking_only_and_merge_users()` 会在 API 副本中丢掉 reasoning-only assistant，并合并被它隔开的 user 消息。canonical transcript 仍保留原始 reasoning。
3. **严格 Provider 的 reasoning echo**：DeepSeek/Kimi/MiMo 需要 `reasoning_content` echo 时，Hermes 会补齐或保留；Mistral、Cerebras、Groq 等拒绝该字段时，会把它从请求中去掉。这个是协议适配，不是把 reasoning 当成可继续生成的 prompt。
4. **签名或加密 replay 被拒绝**：Hermes 不会继续硬塞坏 carrier，而是在 API copy 上降级；Codex invalid encrypted content 会关闭本 session 的 reasoning replay，Anthropic invalid signature 会去掉 `reasoning_details` 后只重试一次。

所以更准确的说法是：**Hermes 只在 Provider 明确支持且状态仍合法时 replay；普通 reasoning 没有通用 replay 语义，不能靠“伪造 thinking”保证继续。**

## 6. Thinking-only：模型只输出 reasoning，没有正文

这是你描述的最常见形状：模型调用成功，UI 可能收到了 reasoning，但 `content` 在去掉 think block 后为空。

### 6.1 代码里的判定

`run_agent.py:_has_content_after_think_block()` 会去掉 `<REASONING_SCRATCHPAD>`、`<think>`、`<reasoning>` 等内部标记，只看剩下是否有非空可见文本。

~~~text
assistant_message
  ├─ content = "<think>我正在分析...</think>"
  ├─ reasoning = "..."
  └─ tool_calls = []
          │
          ▼
strip_think_blocks(content)
          │
          ▼
可见正文为空
~~~

### 6.2 实际恢复阶梯

~~~text
no-tool response
      │
      ▼
可见正文为空？
      │
      ├─ stream 已经流出可见文本
      │       └─ 使用已交付 partial text，避免重复调用
      │
      ├─ 上一个 housekeeping tool round 已有真实回答
      │       └─ 直接复用之前的回答，不注入假的工具说明
      │
      ├─ tool result 刚刚回来，且当前为空
      │       └─ 一次 post-tool empty nudge
      │
      ├─ 有 structured / inline reasoning，prefill 次数 < 2
      │       └─ append 临时 assistant(incomplete)，outer loop continue
      │
      ├─ 仍然是 empty / reasoning-only
      │       └─ bounded empty retry + backoff
      │
      ├─ empty retry 用完，存在 fallback provider
      │       └─ 切换 fallback，重建请求再试
      │
      └─ 全部耗尽
              └─ 保存 `(empty)` sentinel，返回失败/partial 结果
~~~

当前默认的几个上限是不同计数器，不是一个总的“retry 3 次”：

- thinking-only prefill：最多 2 次；
- empty-content retry：通常最多 3 次，但高成本/确定性空响应会缩短或跳过；
- fallback：沿配置的 fallback chain 尝试；
- 最终 reasoning-only：持久化的 transcript 保留 `(empty)` sentinel，用户端可以收到明确说明，而不是把内部 reasoning 静默当成正常答案。

### 6.3 prefill 到底是什么？

prefill 是一个**外层继续控制标记**，不是“强行让 UI 回滚并把整段思考伪造回去”：

~~~text
本次 assistant：reasoning-only
      │
      ▼
构造 interim assistant message
  ├─ finish_reason = incomplete
  └─ _thinking_prefill = True
      │
      ▼
放入 live messages
      │
      ▼
下一轮 build api_messages
      │
      ├─ 某些 Provider：可保留合法 reasoning / native state
      └─ 某些 Provider：send-time sanitizer 丢掉孤立 thinking-only turn
      │
      ▼
下一次模型请求
~~~

这就是为什么不能把 Hermes 的实现粗略描述为“把完整 thinking 塞进去并关闭 thinking，让模型直接写正文”。真实行为是：先把它作为 interim 候选挂在 live history 上，再由当�� Provider 的消息协议决定哪些字段能发出去。

## 7. Reasoning 被截断：和 reasoning-only 不是一回事

### 7.1 非闭合 scratchpad：丢弃本次响应，重新请求

如果 content 里出现打开的 `<REASONING_SCRATCHPAD>` 却没有闭合标签，Hermes 把它视为输出 token 在 reasoning 中途耗尽：

~~~text
response.content = "<REASONING_SCRATCHPAD>还在分析……"
                              ↑ 没有闭合
                                      │
                                      ▼
                         不 append 到 messages
                                      │
                         fresh API retry（最多 2 次）
                                      │
                         仍失败 → partial / failed result
~~~

这里没有“继续 replay 当前半截 reasoning”，因为半截 block 的协议边界和语义边界都不可靠。代码在 `agent/conversation_loop.py:6867-6895` 明确选择不把 broken message 写入历史。

### 7.2 普通输出长度截断：保存 fragment，追加 continuation

对于 `finish_reason="length"` 或流在中途断掉但已经交付了文本，Hermes 走另一条路径：

~~~text
第一段 response（可见文本 fragment）
      │
      ▼
assistant interim + _length_continuation_fragment
      │
      ▼
user-role continuation nudge
      │
      ▼
重新请求，适当增大 output token cap
      │
      ▼
继续得到 fragment
      │
      └──────────────┐
                     ▼
             join_truncated_parts()
                     │
                     ▼
             最终拼接后的回答
~~~

此路径最多尝试 4 次。未回答的 fragment/nudge 在失败时会被清除，避免下一轮永久重复截断；已经交付的 partial text 也不会再次被 stream 一遍。

### 7.3 “thinking 用完全部 output budget”

如果模型有明确 reasoning tag，但 visible content 为空，且 `finish_reason=length`，Hermes 会区分“普通输出被截断”和“所有 token 都被 thinking 吃掉”：后者直接给出 Thinking Budget Exhausted 的可读错误，建议降低 reasoning effort 或提高 `max_tokens`，不浪费多次 continuation 去重复同一个预算问题。

## 8. Codex Responses 的 native incomplete continuation

Codex Responses 是一个独立的恢复形状：

~~~text
finish_reason == "incomplete"
          │
          ▼
提取 interim assistant
  ├─ visible content
  ├─ reasoning
  ├─ codex_reasoning_items
  └─ codex_message_items
          │
          ├─ 有内容或 native replay item
          │      └─ append / 更新 interim，继续
          │
          └─ 没有任何可 replay 的 item
                 └─ 若 role 合法，追加 user continuation nudge
~~~

几个细节很关键：

- 连续 incomplete assistant 的去重只比较用户可见的 content/reasoning，不比较每次会漂移的 opaque encrypted item；否则同样的可见文本会形成 message storm。
- 如果新响应没有重新发出 native compaction checkpoint，旧 checkpoint 需要 merge，而不是被覆盖掉。
- 如果只有普通 reasoning 文本，没有 content、`codex_reasoning_items` 或 `codex_message_items`，bare retry 可能产生完全相同的请求；这时才追加 `_CODEX_INCOMPLETE_NUDGE`。
- 这个 nudge 使用 `role=user`，且只在最后一条是 assistant 时追加。若直接接在 user 或 tool 后面，会破坏严格 role alternation。
- 连续 3 次仍 incomplete 后，返回 partial/failed 结果，不无限循环。

代码证据：`agent/conversation_loop.py:6900-7040`。

## 9. Stream 中途断掉：用户已经看到一部分怎么办？

### 9.1 只流出了 reasoning，没有可见正文

这种情况下 UI 可能已经打开 reasoning box，但 canonical transcript 还没有一个正常 final assistant。Hermes 会把它当成 reasoning-only 或 partial stream，继续走上面的 prefill/empty/retry 阶梯。

### 9.2 已经流出了可见文本

如果 `_current_streamed_assistant_text` 中已经有可见文本，no-tool 分支优先采用这段 partial stream：

~~~text
stream delta: “答案已经写到一半……”
          │
          ├─ provider 结束异常
          ▼
检查 current_streamed_assistant_text
          │
          ▼
使用已交付文本作为 recovery final
          │
          └─ 不再让 retry 重新输出同一段，避免用户看到重复文本
~~~

### 9.3 正在生成 tool call 时断掉

如果 stream 在 tool-call 参数中途断掉，Hermes 不会执行一个半截 JSON。它会返回带 `PARTIAL_STREAM_STUB_ID` / `finish_reason="length"` 的内部 stub，记录被丢掉的工具名，再走截断工具调用的 retry/continuation 路径。

如果完全没有可见文本的空 stub，连空 assistant 行也不应写入历史；只追加合法的 continuation 方向，避免严格 Provider 下一次因为空 assistant content 返回 400。

## 10. nudge 是什么？为什么是 user，不是 system？

### 10.1 nudge 的定义

nudge 是 Hermes 为了让**同一个 Agent 运行继续**而构造的一条内部提示。它常常长这样：

~~~text
role = "user"
content = "[System: You returned no visible answer. Continue ...]"
~~~

内容里出现 `[System: ...]` 只是让模型把它当作高优先级运行提示；消息的实际 role 仍然是 `user`。它不是修改 system prompt，也不是给用户发了一条新的真实消息。

### 10.2 为什么不能直接 append 一个 system message？

Hermes 要同时守住：

- system prompt 的稳定缓存前缀；
- Provider 的消息 role 约束；
- 不能在中途重新构造一个变化的 system prompt；
- 不能让 synthetic recovery text 污染未来 `/resume`。

所以 nudge 采用：

~~~text
真实 assistant / tool 历史
          ↓
必要时补一个 role=assistant 的 interim placeholder
          ↓
role=user 的 nudge
          ↓
下一次模型调用
~~~

例如 post-tool empty 的顺序是：

~~~text
tool(result)
  ↓
assistant(content="(empty)", _empty_recovery_synthetic=True)
  ↓
user(content=_EMPTY_TOOL_RESPONSE_NUDGE,
     _empty_recovery_synthetic=True)
~~~

因为 `tool → user` 在很多 Provider 中不合法，所以必须先放一个 assistant placeholder。两条消息都带 private flag，成功恢复后不会进入 durable transcript；finalization 还会清掉尾部 scaffold。

### 10.3 Hermes 当前主要 nudge 类型

| nudge / continuation | 触发条件 | 上限/特点 |
| --- | --- | --- |
| thinking prefill | reasoning-only，没有可见正文 | interim assistant，最多 2 次 |
| post-tool empty | tool result 后模型返回空 | 通常每个成功工具轮次允许再触发一次 |
| Codex incomplete | Responses `incomplete` 且没有可 replay item | 最多 3 次；只在 role 合法时追加 |
| length continuation | 输出长度截断或 stream stub | 最多 4 次；保存并拼接 fragment |
| dropped tool-call | `finish_reason=tool_calls` 但 `tool_calls=[]` | 最多 3 次；要求模型真正发结构化调用 |
| intent/stall | “Let me now… / I will now…” 说完就停 | 最多 2 次；要求立即行动 |
| verify-on-stop | 编辑了可验证文件但没有新鲜通过证据 | 默认 opt-in，最多 2 次 |
| pre_verify | 注册了 pre_verify hook，且编辑了文件 | 由 hook 的上限决定 |
| Kanban terminal | worker 没有 `kanban_complete` / `kanban_block` | 受 worker stop guard 限制 |

所有这些都在 live loop 中增加下一次模型输入，但不是用户真实输入；成功或结束时由对应 cleanup 逻辑去除。

## 11. 为什么没有 tool call 仍然不一定结束？——Stop Gates

“没有 tool call”只说明这一次归一化响应没有进入 Tool Executor。它不自动等于“整个 run 可以结束”。Hermes 在 finalization chokepoint 继续做停止前检查：

~~~text
没有结构化 tool_calls
          │
          ▼
得到 final_response
          │
          ├─ trailing continue-intent？
          │       └─ assistant interim + user nudge，继续
          │
          ├─ finish_reason=tool_calls 但数组为空？
          │       └─ dropped-toolcall nudge，继续
          │
          ├─ verify_on_stop gate 命中？
          │       └─ 保留候选，要求运行验证，继续
          │
          ├─ pre_verify hook 命中？
          │       └─ 执行插件定义的继续提示，继续
          │
          ├─ Kanban worker 缺终止工具？
          │       └─ 要求 kanban_complete / kanban_block，继续
          │
          └─ 都没有命中
                  └─ 真正 append final + finalize
~~~

### 11.1 intent / stall guard

如果模型只给一个很短的未来时态答复，例如：

~~~text
“I will now inspect the repository.”
“Let me now run the tests.”
“Next, I will write the report.”
~~~

但它没有 tool call，Hermes 可以把它视为“宣布了动作但没有执行”。`trailing_continue_intent()` 只看短文本的尾部，避免普通长答案中间出现 “I will” 就误触发。历史 Codex ack guard 还会要求 workspace/action markers，或在用户显式开启 all-mode 后对所有 API mode 生效。

它的恢复仍复用同一条 bounded continuation path：

~~~text
assistant(interim, finish_reason="incomplete")
  ↓
user(_CODEX_ACK_CONTINUATION_NUDGE)
  ↓
下一次模型调用
~~~

### 11.2 dropped tool call guard

这是专门处理：模型/Provider 的终止原因说“tool_calls”，但解析结果中没有任何结构化 call：

~~~text
finish_reason = "tool_calls"
tool_calls = []
content / reasoning = “我现在会执行……”
          │
          ▼
不把 narration 当成工具已经执行
          │
          ▼
保存临时 assistant + user dropped-toolcall nudge
          │
          ▼
要求模型重新发真正的 tool_calls
~~~

这个 guard **不会**拦截所有 `finish_reason="stop"` 的普通文本。也就是说，如果 Provider 把“模型想调用工具但调用被藏在 reasoning 里”伪装成一个干净的 `stop` 响应，Hermes 没有通用方法证明它是工具调用；它最多由 intent/stall guard 或 verify gate 在特定条件下补救。这是实现边界，不应把 Hermes 描述成能读取自然语言中的隐式工具调用。

## 12. verify-on-stop：这里的“gate”具体校验什么？

这是另一个“没有 tool call 仍可能继续”的来源。它不是每个普通对话都默认触发，当前实现是配置/环境控制的 opt-in：

~~~text
final response candidate
       │
       ▼
本轮是否编辑了可验证的文件？
       │ 否
       └──────────────→ 不触发
       │ 是
       ▼
是否有最新 verification snapshot？
       │
       ├─ status == passed → 放行结束
       └─ 未通过 / 未验证
              │
              ▼
生成 verify-on-stop nudge
  ├─ 改动路径
  ├─ 当前 verification status
  ├─ 检测到的 test/lint/build/verify command
  └─ 要求运行、读取失败并修复
              │
              ▼
把真实候选答案先作为 interim 展示/持久化
加入 synthetic user nudge
              │
              ▼
继续同一 outer loop
~~~

具体校验包括：

- `_turn_file_mutation_paths` 是否有本轮改动；
- 文档、README、Markdown、skill 等纯 prose 路径会被过滤，因为它们通常没有可运行行为需要验证；
- verification snapshot 是否记录 `passed`；
- 是否有项目自己的 test/lint/build 命令；没有时可能要求 `hermes verify --json` 或临时验证脚本；
- `attempts` 是否达到上限，默认最多 2 次。

它校验的是“工作区有没有新鲜、可观察的验证证据”，不是让另一个模型凭感觉判断答案正确。`verify_on_stop` 的默认值是关闭；`auto` 才根据 CLI/TUI/Desktop 与 messaging surface 做差异化判断。

### 12.1 为什么候选答案会先显示，又继续调用？

这是为了用户体验和恢复安全：

~~~text
模型给出候选 final
      │
      ├─ 先作为真实 assistant interim 发给 UI / SessionDB
      ├─ final_response 暂时清空，表示“还没有最终结束”
      └─ synthetic user verify nudge 驱动下一次调用
~~~

如果后续验证成功，新的响应会替代模型 replay 视图中的 provisional candidate；如果预算耗尽，finalizer 可以使用显式保存的 pending candidate，而不是再胡乱发一次模型请求。synthetic nudge 本身会从 durable transcript 去掉，真实候选不会因为它是 interim 就丢失。

## 13. Provider / Transport 层的恢复机制

### 13.1 Stream、timeout、SSE 断开

流式调用有独立的 inner retry 和 stale-stream watchdog：

~~~text
stream 开始
  ↓
持续接收 chunks？
  ├─ 是 → touch activity，继续
  └─ 否
       ├─ timeout / connection / SSE parse error？
       │       └─ 关闭当前 request client，fresh connection retry
       ├─ 长时间没有真实 chunk？
       │       └─ kill stale stream，标记 reconnect，重新请求
       └─ 已在 tool-call 参数中途？
               └─ 不执行半截调用，返回 partial-stream stub
~~~

`agent/stream_diag.py:214-270` 会给 UI 一个短状态，例如 `stream drop ... reconnecting, retry N/M`，同时把 provider、HTTP status、bytes、chunks、elapsed 等细节写到日志。成功的 partial text 会被 reset/fence，防止旧 stream 的 token 和新 stream 交叉写入。

### 13.2 HTTP 错误、credential 和 fallback

错误先经过 `FailoverReason` 分类，而不是看到一个 429 就用同一种办法：

~~~text
API error
  ↓
classify_api_error()
  ├─ transient transport → retry / rebuilt client
  ├─ 401/403 auth → refresh token / rotate credential
  ├─ 429 / billing → retry once or rotate / fallback
  ├─ upstream rate limit → 不污染用户 credential，走 fallback
  ├─ context overflow / 413 → compression / smaller context
  ├─ content policy → 不盲目重试同一请求，必要时 fallback/terminal
  └─ permanent format / model error → 针对 wire 做一次修复或结束
~~~

credential pool 的行为也有边界：

- 429 通常先给当前 credential 一次机会，连续失败才 rotation；已标记 exhausted 的 credential 会直接换；
- billing exhaustion 直接 rotation；
- auth failure 先 refresh 失败项的 token，再考虑 rotation；
- upstream aggregator 限流不应该把健康的用户 key 标记成 exhausted；
- 同一个 OAuth entry 的 refresh 次数有上限，避免“refresh 成功但每次仍 401”形成永循环；
- fallback 切换后会重算 context window、reasoning config、prompt-cache layout 和 provider-specific reasoning echo。

### 13.3 Context overflow 和 output cap

输入过大与输出上限过小是两类不同问题：

~~~text
request 太大 / context overflow / 413
  └─ 若允许自动压缩：compress → 重新组 request → retry
  └─ 若 compression.enabled=false：不要偷偷压缩，给用户 /compress、/new 或换大窗口模型的建议

max_tokens / output cap 错误
  └─ 调整 max output tokens → retry

finish_reason=length
  └─ 走 fragment continuation（见第 7 节），不是简单的 HTTP retry
~~~

压缩是少数可以改变上下文前缀的正式机制；一般 recovery 不应通过重建 system prompt 或随意改历史来“修缓存”。

### 13.4 Provider 特定的 wire 修复

Hermes 还有一些“错误明确指向某个请求字段”的一次性修复：

| 错误形状 | 修复动作 | 为什么只改请求视图 |
| --- | --- | --- |
| Anthropic thinking signature invalid | 从 `api_messages` 去掉 `reasoning_details` 后重试一次 | canonical history 仍保留原始轨迹 |
| Codex `invalid_encrypted_content` | 禁用本 session reasoning replay，清理 cached items，重试一次 | 失效的是 provider carrier，不是用户文本 |
| Provider 拒绝 `context_management` | 关闭 native compaction，让本地 compression 接管 | 不能持续发送已知不支持的字段 |
| llama.cpp grammar 拒绝 tool schema 的 `pattern` / `format` | 去掉这些 schema keyword 后重试一次 | 云端 Provider 仍可保留原 schema |
| strict Provider 拒绝 `reasoning_content` | strip；DeepSeek/Kimi/MiMo 需要时则 pad/echo | 由当前 Provider 决定字段，不复制旧 Provider 形状 |
| image / multimodal tool payload 过大或不支持 | 缩小图片或降级多模态 tool content | 尽量保留文本和工具语义 |

这些分支由 `TurnRetryState` 的 one-shot flags 防止同一种错误无限重复：

~~~text
TurnRetryState（每个 outer API call slot 新建）
  ├─ provider auth refresh attempted
  ├─ thinking signature attempted
  ├─ invalid encrypted reasoning attempted
  ├─ native compaction rejection attempted
  ├─ image / multimodal repair attempted
  ├─ grammar repair attempted
  ├─ primary transport recovery attempted
  └─ restart_with_* signals
~~~

## 14. Transcript / protocol 修复：到底恢复什么历史？

### 14.1 补齐未回答的 tool call

如果异常发生在 assistant tool-call 已经 append 之后，但某些工具还没有结果，outer exception handler 会为每个缺失的 `tool_call_id` 补一个 error tool result：

~~~text
assistant(tool_calls=[A, B])
tool(A)
异常
  ↓
补 tool(B, content="Error executing tool: ...")
~~~

这样下次 Provider 至少收到结构完整的 call/result pairing，而不是一个永远等待 B 的半截 turn。

中断/取消路径也会给未执行调用补 `[Tool execution cancelled ...]` result。这个动作不是声称工具真的执行过，而是把“没有执行”作为合法的观察结果写入协议。

### 14.2 `repair_message_sequence`

每次发请求前还有角色序列防线，主要修三类问题：

~~~text
1. assistant → assistant（不是 Codex native interim）
   → 合并 content / tool_calls，或用后一个 verification candidate 替换前一个

2. 没有对应 assistant tool_call 的 stray tool
   → 丢弃孤儿结果

3. user → user
   → 用换行合并，避免丢掉任何用户输入
~~~

它**不会**无条件删除所有“assistant(tool_calls)+tool”后接 user 的形状，因为那可能是用户在上一个工具轮完成后主动 redirect 的合法对话。真正被 retry scaffolding 破坏的 tail，由专门的 scaffolding stripper 做 flag-gated rewind。

### 14.3 清掉 retry scaffolding

恢复消息常带这些私有标记：

~~~text
_thinking_prefill
_empty_recovery_synthetic
_empty_terminal_sentinel
_dropped_toolcall_nudge
_length_continuation_fragment
_length_continuation_nudge
_verification_stop_synthetic
_pre_verify_synthetic
_kanban_stop_synthetic
~~~

它们的原则是：

- 为了下一次模型请求暂时存在；
- 成功恢复后不应污染未来模型上下文；
- 真实 assistant 候选可以保留，只有 synthetic nudge 被删除；
- 如果尾部是 empty scaffold，且它前面挂着未完成 tool result，恢复函数会 rewind 掉 tool-result + assistant(tool_calls) 尾巴，避免下一次真实 user 直接接在孤儿 tool 后面。

### 14.4 持久化的恢复顺序

~~~text
assistant(tool_calls)
  ↓ flush before side effects
tool result A
  ↓ flush after each result
tool result B
  ↓ flush
assistant(final candidate)
  ↓ flush before leaving loop
finalize_turn()
  ├─ remove private scaffolding
  ├─ close interrupted tool sequence if needed
  ├─ save trajectory
  ├─ cleanup VM/browser
  └─ persist SessionDB / JSON log
~~~

SessionDB 使用 message marker 做幂等 flush，避免 turn-finalizer、错误出口和 shutdown 出口重复写同一条消息。持久化失败时，Loop 会停止继续发送一个只有内存存在的副作用 turn，并在结果/日志中保留失败原因。

### 14.5 Hermes 做不到 exactly-once

如果网络在一个外部工具已经执行成功之后、Hermes 收到结果之前断掉，Hermes 可能只知道“结果丢了”，不知道远端副作用是否已经发生：

~~~text
Hermes 发起 write / deploy / send
          │
          ▼
外部系统已经执行
          │
          ✕ 回包丢失
          │
          ▼
Hermes 只能补协议结果 / 重试模型
~~~

它可以避免执行半截 tool call、补齐协议和记录取消，但不能在没有外部幂等 key/查询能力时证明副作用恰好执行一次。这个边界必须和“消息历史恢复成功”分开。

## 15. 用户在 UI 上会看到什么？

### 15.1 thinking 已经显示，然后重试，会不会很奇怪？

有可能看到“reasoning box 暂停 → 状态提示 → 新一段 reasoning 又开始”，但它通常仍属于同一个逻辑 turn：

~~~text
第一条 stream
  ├─ reasoning.delta → UI reasoning box
  └─ 没有 final / stream drop
          │
          ▼
内部 retry / continuation
  ├─ status: reconnecting / asking it to continue
  └─ 第二条 stream 的 reasoning.delta
          │
          ▼
最终 message.complete / final response
~~~

CLI 会在 reasoning token 到来时打开 dim reasoning box，在 visible content 到来时关闭它；stream boundary 会 flush/reset。TUI gateway 也把 `thinking.delta` / `reasoning.delta` 作为事件交给同一个 turn controller。已经发给用户的 token 通常不能被 UI 回滚，所以 Hermes 的策略是避免重复发送可见正文，而不是假装第一段从未发生。

### 15.2 哪些状态会立即显示，哪些会缓冲？

- reasoning/content delta：可实时显示，取决于 surface 的 `show_reasoning` 和 callback；
- stream drop/reconnect：有明确的 status/heartbeat 和日志诊断；
- 普通 empty retry：很多状态先进入 status buffer，成功后清掉，避免用户看到一串最终不会发生的失败噪音；
- Codex incomplete：会发 wait notice，因为每次 continuation 可能等很久；
- verify-on-stop：真实候选可以作为 interim 显示，但内部 nudge 通常不作为用户聊天气泡展示；
- `message.complete`：在最终候选通过 gate 或以明确 partial/failed 结果收尾后才发。

因此，用户看到的不是“把 reasoning 删除后重新渲染一遍”的严格事务 UI，而是一个带 status/stream continuity 的 best-effort 实时投影。Hermes 能保持同一个 turn 的语义，但无法撤回已经显示的模型 token。

## 17. 最容易误解的五件事

### 17.1 “thinking 里出现工具调用文字”不等于工具真的调用了

模型输出的自然语言、reasoning 字段和结构化 `tool_calls` 是三种不同事实。Hermes 只有在解析对象里看到 `tool_calls` 才执行工具；dropped-toolcall guard 只能处理它有明确 `finish_reason=tool_calls` 但数组为空的情况。

### 17.2 “有完整 thinking”不等于可以把它伪造成 replay 前缀

普通 reasoning 文本没有通用的 continuation handle。只有 Provider-native replay item、合法签名或当前 Provider 要求的 echo 字段，才可能被安全重放。

### 17.3 nudge 不是 system prompt 改写

nudge 可能写 `[System: ...]`，实际却是 role=user；它是为保持 role alternation 和 Prompt Cache 而设计的内部继续消息。

### 17.4 stop gate 不是“另一个模型来审判答案”

verify-on-stop 主要看工作区是否有改动、有没有新鲜验证 snapshot、有没有可运行的验证命令。它不是默认对所有自然语言答案做语义裁判。

### 17.5 恢复历史成功不等于外部副作用 exactly-once

Hermes 可以修 transcript 和 tool pairing，但不能仅靠本地消息知道一个超时的远程写操作到底有没有发生。

## 19. 一句话总结

Hermes 的高价值之处，不是“模型坏了就再问一次”，而是把异常响应拆成多个可判断的状态：

~~~text
能不能解析？
有没有结构化工具调用？
有没有可见正文？
reasoning 是普通轨迹还是 native replay state？
是否破坏了 role / tool pairing？
是否已经给用户流出 partial text？
是否满足验证 / worker stop gate？
~~~

然后在每一层选择最小的恢复动作：重建 request、继续生成、追加 nudge、切 fallback、修消息协议、清理临时历史，或者在有明确原因时安全结束。这样既尽量不让一次坏响应杀死整个 Agent turn，也不把模型从未真正产生的工具调用、答案或 thinking 伪造进历史。
