# Notes 与 History：跨窗口如何找回工作状态

> 状态：记录本轮关于 History 检索、Notes 组织和 Thread Hint 的讨论，并对本地源码做局部核对。**这不是 Codex 的完整拆解，也不把未公开的服务端实现当作已知事实。**

核对范围：本地 Codex 仓库 `/Users/zhouchenghao/python_file/codex`，版本 `c0e88f3c04219aaa032aaf4b20a8c3284cc81449`。先看跨窗口主流程：[[all_harness/codex/Token Budget：同一任务如何跨上下文窗口继续|Token Budget：同一任务如何跨上下文窗口继续]]。

## 1. 核心问题：历史还在，不等于能找回

切换上下文窗口后，旧对话不再全部直接摆在模型眼前。若想找回某次用户要求、工具结果或测试失败，就需要一个定位入口。把全部历史简单拼成一长段文本，虽然可以保存原文，却很难精确回答“上一窗口的哪条记录包含那次测试结果”。

这里要区分两层：

1. **定位结构**：至少能按 Agent、窗口、条目、顺序、角色或工具等线索缩小范围，并用稳定标识读取具体条目。
2. **记录内容**：保留当时的消息或工具输出，供模型回看和核对。内容本身不一定要事先转成严格的业务 Schema。

这是根据检索需求整理的设计理解，**不是公开源码证明的服务端数据库结构**。当前源码展示了工具接口和客户端适配；服务端到底怎样存储、建立索引、处理事务，尚不能从这些文件确认。

## 2. History 的公开检索接口

| 操作 | 能做什么 |
| --- | --- |
| `list_windows` | 列出历史上下文窗口及条目数量 |
| `list_items` | 按窗口、消息角色、工具名称等条件列出条目 |
| `read_item` | 已知窗口 ID 和条目 ID 时读取内容，可限制读取的字符范围 |
| `search_contents` | 按**区分大小写的字面子字符串**搜索内容 |

这给出两条找回路径：**知道 ID，就直接读取；不知道 ID，就先列出或搜索，再读取。** History 的工具描述也说明，新增记录在列表和搜索中可能延迟数秒出现。公开接口没有显示语义向量检索，也不要求每条历史先经过模型总结后才能读取。

真正难的是“不知道该搜什么”。例如旧记录写的是“工具超时后重复执行可能产生副作用”，新窗口只想到搜“幂等性”，字面搜索可能没有命中。**数据仍在**与**模型能够有效召回**是两回事。

## 3. Notes 是怎样的笔记空间

Notes 对模型表现为跨上下文窗口存在的**虚拟文件空间**，不是工作区里的真实文件。公开接口提供五种操作：

| 操作 | 能做什么 |
| --- | --- |
| `list_files_by_prefix` | 按路径前缀列出笔记 |
| `read_file` | 读取全文或指定行范围 |
| `search_contents` | 按字面子字符串搜索笔记内容 |
| `append_to_file` | 向笔记末尾追加文本 |
| `write_file` | 创建文件或替换整个文件 |

工具没有规定笔记必须写成 JSON、YAML 或某套固定目录。模型可以自行组织简短检查点，例如任务目标、已完成的工作、关键决定、未解决的问题、下一步，以及对应的窗口 ID 和条目 ID。这样笔记既是**工作进度记录**，也可以充当指向 History 原文的**语义路标**。

这一点在模型配置的 Token Budget 指引里写得更明确：对于可能跨窗口的任务，执行过程中逐步维护简洁检查点；记录仍在处理的用户要求和重要动作的历史引用；重置后先读检查点，缺细节再查 History。它是给模型的工作要求，**不等于运行时已经验证笔记完整、准确，或强制模型在新窗口读取了它**。

### 已能核对的文件行为

- 相对路径归属当前 Agent 的 Notes 空间；工具说明也允许使用绝对虚拟路径寻址其他 Agent。模型配置又要求写入限制在当前线程，因此跨 Agent 实际授权边界仍需服务端证据，不能只由路径说明推断。
- 成功写入后，直接读取应能看到新内容；文件列表和内容搜索是最终一致的，可能稍后才出现。
- 单个文件上限为 **1,000,000 UTF-8 字节**。写入与追加被标记为不支持并行工具调用，但这不能证明跨请求或跨 Agent 的写冲突已全部解决。
- 这些 Notes 属于同一执行轨迹的跨窗口工作笔记；它们与 [[all_harness/codex/长期 Memory：两阶段记忆管线|跨 Session 的长期 Memory]] 不是同一种机制。

## 4. 纠正：固定恢复说明与 Thread Hint 是两份东西

前面曾把“服务端返回 Thread Hint”进一步说成“服务端根据 Notes 动态生成 Hint”。**这一步推断没有公开源码支持，应当收回。**从客户端能确认的是请求、接收和注入过程，不能确认服务端究竟返回固定文字、笔记索引、动态摘要，还是组合内容。

| 内容 | 来源与作用 | 已知边界 |
| --- | --- | --- |
| 固定的窗口恢复说明（`guidance_message`） | 随模型配置提供的 Token Budget 指引，说明如何维护 Notes、如何用 History 恢复 | 对给定配置基本固定；它与 Thread Hint 分开组织 |
| 窗口信息 | 运行时组装 Agent 名称、首个/当前/上一窗口 ID | ID 随窗口变化；上一窗口 ID 可提示发生过重置 |
| 可选的 Thread Hint | 客户端向后端请求文本，收到非空且合规的内容后放入窗口上下文 | 上限为 **4,000 字节**；可能为空或请求失败；生成规则未公开 |

前面提出的“有一段固定文字提醒新窗口怎样使用 Notes 和 History”确实对应源码中的恢复说明。它的名称不是 Thread Hint。Thread Hint 是另一段可选文本，不能先验认定为“服务端根据 Notes 写的任务摘要”。

可以把新窗口的恢复入口理解为：

```text
固定恢复说明 + 当前窗口标识 + 可选 Thread Hint
                       ↓
              模型读取相关 Notes
                       ↓
       必要时凭 ID 或搜索回看 History 原文
```

这只是工作流程示意，不表示每次都会得到 Hint，也不表示读取 Notes 和 History 已由运行时强制完成。

## 5. 这套设计留下的可靠性问题

Notes 能帮助模型保存“我做到哪里了”，History 能提供“当时实际发生了什么”。但两者都不能独自回答**正在执行的工具调用究竟完成没有、下一步该不该重试**等运行时状态问题。讨论中提出的通用设计分层是：运行时检查点保存可验证的执行状态；Notes 保存语义判断和计划；History 保存原始轨迹。这是进一步的架构建议，**不是声称当前 Codex 已按这三层实现了完整恢复协议**。

后续值得验证：

- 上一窗口没有及时写 Notes，或漏写关键用户限制时，新窗口能否找到原文？
- Notes 写了历史引用，但列表与搜索尚未更新时，会怎样恢复？
- 只靠字面搜索，术语不同却指向同一事件时，召回率如何？
- 新窗口没有主动读取 Notes，或者 Hint 缺席时，未完成 Turn 的语义状态是否会丢失？
- 多次写入、跨 Agent 寻址与后端失败时，如何处理冲突和恢复？

因此，这套机制要分别验证两件事：**运行流程能否继续**，以及**模型能否准确找回并理解先前状态**。详见主笔记中的同一 Turn 续跑与消息保留边界。
