# Codex 长期 Memory：两阶段记忆管线

> 状态：前期资料记录。Codex 的系统拆解与本模块的共同阅读都尚未开始；这份笔记保留本次提供的思路及有限源码核对，后续需要沿实际代码逐项讲解。

本文记录跨 Session 可能复用的长期记忆设计。材料来自用户提供的文章第 10 页摘要；本次参考本地仓库 `/Users/zhouchenghao/python_file/codex`，版本 `c0e88f3c04219aaa032aaf4b20a8c3284cc81449`，阅读了 Memory README 和部分代码。这里是入口概览，不代表已经完整核对所有分支或运行表现。

## 1. 先看整体

```text
历史 Session 的执行轨迹（Rollout）
                 ↓
Phase 1：逐会话提取
  筛选合适的 Rollout，提取原始记忆和该会话摘要
  将结果存入状态数据库
                 ↓
Phase 2：全局整合
  按条件选择第一阶段结果，整理文件工作区
  根据变化让整合 Agent 更新长期记忆
                 ↓
记忆目录中的摘要、索引、会话摘要与相关资源
```

**第一阶段关注一条会话产生了什么可复用信息；第二阶段关注如何把多个会话的信息组织成整体。** 这不是每次用户提问都同步扫描所有历史：README 及启动代码说明，符合条件的根 Session 启动时会在后台执行该管线；临时 Session、子 Agent Session、功能未启用或状态库不可用等情况会跳过。具体触发与配置边界留待系统拆解。

## 2. Phase 1：逐会话提取

系统从状态数据库中选择符合条件的历史会话，例如在配置的时间范围内、已空闲足够久、没有被其他工作者领取的会话。它将轨迹中需要处理的内容交给模型，得到：

- `raw_memory`：该会话中提取的较详细记忆。
- `rollout_summary`：较精简的会话摘要。
- 可选的 `rollout_slug`：用于摘要文件等场景的标识。

代码说明生成字段会做敏感信息清理，成功结果保存为数据库中的阶段一输出。一次提取也可能成功但没有值得保留的内容。

工程上，多个会话的提取可以并发执行，但有并发上限；任务在数据库中领取并带租约，避免多个工作者同时处理同一项；失败后记录重试时间和剩余次数，避免立即反复重试。这里的协调机制用于减少重复工作，不能据此断言任何故障下都绝不会重复执行。

## 3. Phase 2：选择并整合

第二阶段领取一个全局整合任务，并协调对共享记忆工作区的访问。它从阶段一结果中选取有限数量的候选：源码按使用次数优先、再按最近使用或来源更新时间等排序，并过滤超过配置的未使用时间窗口的结果。没有使用记录时，当前查询使用来源更新时间作为判断依据，避免刚产生的记忆直接因未使用而被排除。

接下来，系统同步合并后的 `raw_memories.md` 与选中会话的 `rollout_summaries/`，并清理不再选中的部分文件。工作区与上次成功的 Git 基线比较，生成用于整合的 Diff；变化可以包含新增、修改和删除。

```text
阶段一输出 → 筛选候选 → 同步记忆文件 → 对比上次成功基线
                                                ↓
                                 有变化或需要修复产物
                                                ↓
                              内部整合 Agent 更新记忆
```

如果工作区没有变化且已有产物通过检查，可以直接结束本次整合，不必每次都启动整合 Agent。Agent 成功后会更新基线并记录任务结果；失败、租约与重试有对应的协调机制。

整合后的记忆工作区可能包含 `memory_summary.md`、`MEMORY.md`、`rollout_summaries/`、`skills/` 等。它们各自保存什么、读取时如何查找以及不同版本的差异，留待共同阅读，不把目录名本身当作完整实现说明。

## 4. 整合 Agent 的执行边界

当前源码把整合工作作为内部任务，关闭继续递归委派的协作功能，也关闭部分与该任务无关的能力。权限配置需要分情况看：

- 父会话使用 Codex 管理的沙箱时，代码为整合 Agent 配置记忆目录写入范围，并关闭网络访问。
- 父会话明确关闭 Codex 管理的沙箱，或使用外部权限配置时，代码保留相应的父权限配置。此时能否联网、能写哪里取决于实际运行环境，不能一概认定一定被 Codex 沙箱禁止。

因此，“整合 Agent 不能递归委派”是本次看到的明确配置；“一定不能联网且只能写记忆目录”需要限定到相应沙箱分支。

## 5. 关于遗忘，以及与上下文压缩的区别

候选记忆可能因长时间未使用等原因不再进入当前整合集合，相关记忆文件也可能随整合被清理或调整。这是**记忆集合的筛选与更新**；不能由此推断原始 Rollout 一定被删除，也不能据此断言所有相关内容都会被立即彻底清除。

长期 Memory 和当前会话的上下文管理有不同目标：

| 机制 | 主要关注 |
| --- | --- |
| 长期 Memory | 跨 Session 保存以后可能复用的经验与线索 |
| Token Budget / Context Compaction | 当前任务的上下文预算、历史压缩和后续继续执行 |

两者可能配合使用，但不能把长期记忆构建直接等同于当前会话的压缩，也不能把记忆文件当成原始会话的完整替代品。

## 6. 以后共同拆解时需要核对

- Session 如何被选中、领取，什么情况下跳过、重试或无输出。
- 一条 Rollout 如何变成模型输入、阶段一输出和数据库记录。
- 第二阶段的候选筛选、同步、Diff、Agent 更新及成功/失败恢复。
- 记忆文件如何进入后续任务，usage 信息何时更新。
- 不同权限配置、Memory 版本和清理策略下的实际边界。

以上是待研究方向，不是完整操作清单，也不代表本模块已经开始共同阅读。
