# Token Budget：同一任务如何跨上下文窗口继续

> 状态：本篇所述的主流程、同一 Turn 跨窗口和旧消息保留边界，已在对话中共同讨论，用户明确表示理解并授权写入。它是 Codex 的**一个局部专题**，不表示 Token Budget 所有分支或 Codex Harness 的系统拆解已经完成。

核对范围：本地 Codex 仓库 `/Users/zhouchenghao/python_file/codex`，版本 `c0e88f3c04219aaa032aaf4b20a8c3284cc81449`。以下区分源码中实际做的事、需要模型自己做的事，以及仍需验证的可靠性问题。文章中的示意材料只帮助提出问题；本篇实现结论以这一版源码和随仓库的测试为依据。

## 1. 先建立一幅运行画面

假设用户要求 Codex 修复一个错误。它已经读文件、改代码、调用测试工具，但尚未完成。此时模型直接能看到的对话快装不下了。

```text
同一会话、同一个未完成的 Turn

旧窗口：用户任务 → 读文件 → 修改 → 测试反馈 → 继续工作
                                         │
                                         └─ 当前这一步结束后发现需要换窗口
                                                     ↓
                                          重建模型可见的上下文
                                                     ↓
新窗口：当前指令与环境 + 简短恢复提示 + 可用工具
                                                     ↓
                              模型按需读笔记、查旧历史、继续工作
```

这里有三个不同层次：

| 层次 | 换窗口时怎样变化 |
| --- | --- |
| Session / Thread | 持久会话仍在，工作目录中的文件和执行环境不会因换窗口而清空 |
| Turn | 当前用户任务可以继续处于运行状态，不要求用户重新发送任务 |
| Context Window | 下一次模型请求中直接可见的旧对话被替换，新窗口重新组装必要上下文 |

因此“同一任务跨多个窗口”说的是**运行流程可以跨越**。模型是否准确理解旧任务，则取决于新窗口里有哪些恢复线索，以及它是否正确使用。

## 2. 什么时候提醒，什么时候切换

Codex 会记录当前窗口的 Token 使用情况。检查主要发生在一次模型回复及相关工具处理结束后的边界，也会在新 Turn 发送模型请求前检查；它不是在模型生成每个字时随时打断。

临近设定的提醒点时，系统可以向模型追加一次“窗口快用完，请保存重要进度”的提示。同一窗口里，这类提醒有防止重复发送的状态。若配置了额外的保存缓冲，达到基础预算时还可以再给出明确的保存提示，留出一段继续行动的空间。具体阈值和提示是否启用取决于配置与模型信息。

模型也可以主动要求开始新窗口。需要继续执行且触发了换窗条件时，运行时会切换；达到缓冲上限或完整窗口上限时，也会强制走切换路径。这里要区分：

- **接近上限的提醒**：给模型机会整理进度，不等于笔记已经写好。
- **主动要求换窗**：模型提出请求，运行时在处理边界执行。
- **自动换窗**：运行时根据预算，在需要下一步模型请求时建立新窗口。

如果模型已经给出最终答复、当前 Turn 不需要继续，主流程不会为了“在本 Turn 继续”而强行开启另一次模型请求。后续新 Turn 仍可能在开始前遇到预算检查。

## 3. 同一个 Turn 中途换窗，程序怎样接着走

考虑一个更具体的例子：

```text
用户：修复这个错误并运行测试
  ↓
模型：调用测试工具
  ↓
工具：返回失败结果
  ↓
运行时：处理完这一步，发现窗口需要切换
  ↓
运行时：替换模型可见的旧对话，生成新窗口
  ↓
仍在同一个 Turn：发出下一次模型请求
  ↓
模型：继续查资料、改代码或回答
```

程序没有把这次换窗当作任务完成：成功切换后，执行循环回到下一步。随仓库的测试覆盖了**同一个 Turn 自动换窗后继续模型请求和工具调用**的场景。这解释了为什么用户无需重新提交任务。

但要把两种“继续”分开：

1. **流程上的继续**：运行时保留当前 Turn，切换后进入下一步。这一点有明确代码路径和测试。
2. **语义上的继续**：模型知道原任务、已做的工作和下一步。这需要足够的恢复信息，不能只靠“Turn 还在”保证。

切换是在步骤之间进行，不会凭空恢复刚被新窗口移走的普通工具结果。若笔记里没有记录必要结论，而模型也没有去查 History，新窗口仍可能失去关键线索。换窗本身发生错误或被中止时，当前 Turn 也可能结束；“同一个 Turn 能跨窗口”不等于“任何情况下都绝不会中断”。

## 4. 新窗口实际得到什么

这一模式下的切换不调用模型把全部旧对话总结成一篇短文。运行时会为下一次模型请求重新组装当前指令、环境信息和可用工具，并给窗口新的身份标识。工作目录、已写入的文件和其他外部执行状态不会因模型对话换窗而清空。

模型配置中另有一段相对固定的**窗口恢复说明**，指导模型维护 Notes，并在窗口重置后读取检查点、按需查询 History。运行时还会组装当前及上一窗口的 ID。它们与下面这段可选的 Thread Hint 是不同内容。

启用了相应的笔记与历史能力时，系统还会尝试向后端获取一段简短的 Thread Hint，放入新窗口。当前核对的原生路径对这段提示设置了 **4,000 字节**的上限；这是字节，不是 Token。请求失败、内容为空或不合要求时，该提示可能缺席，运行时仍可继续组装新窗口。**公开客户端源码没有说明 Hint 如何生成，不能断言它由 Notes 动态生成，或必定包含任务进度。**

笔记与历史工具是否出现也有条件。当前核对的原生扩展需要相应配置、支持的提供方和认证路径。不能把“Token Budget 已启用”直接推断为“所有部署都有可用的 Notes 与 History”。源码中还存在通过其他工具提供提示的兼容路径；两条路径的具体限制不应混用。

## 5. Notes、History 和 Thread Hint 各负责什么

| 内容 | 它提供什么 | 它不能保证什么 |
| --- | --- | --- |
| 固定的窗口恢复说明与窗口 ID | 说明如何使用 Notes / History，并标识当前及上一窗口 | 不保证模型已按说明读取、核对笔记 |
| Thread Hint | 后端可选返回的新窗口短文本 | 不能保证有内容，更不能确认其生成方式或完整性 |
| Notes | 模型主动写入的工作笔记，可在同一会话的窗口之间读取 | 不能保证模型一直维护、写得准确或切换后一定读取 |
| History | 已保存的旧执行记录，可按窗口、条目查找 | 不会自动全部进入新窗口，也不能恢复原先已被截断的内容 |

例如，模型可以在旧窗口写下：测试失败，详细结果在上一个窗口的某条记录中；新窗口先读笔记，再根据引用去 History 找具体输出。这样笔记可以只保存索引和行动计划，不必复制大量工具正文。

但这条恢复链路有两个前提：模型先写下必要线索，换窗后再主动读取。当前实现没有一项通用的强制检查，确认“切换前有效笔记已经写好、切换后任务状态已经读回并核对”。历史列表与搜索也可能有短暂延迟；实际可查到什么还受原始输出截断、保存与服务状态影响。

这些 Notes 服务于**同一会话跨窗口继续工作**。[[all_harness/codex/长期 Memory：两阶段记忆管线|长期 Memory]]面向跨 Session 的经验积累，职责不同。

关于 History 的具体检索接口、Notes 的文件行为，以及固定恢复说明和 Thread Hint 的区别，另见 [[all_harness/codex/Notes 与 History：跨窗口如何找回工作状态|Notes 与 History：跨窗口如何找回工作状态]]。

## 6. 最近几轮消息会不会保留？

**当前这条 Token Budget 换窗路径没有“默认保留最近 N 轮对话”的规则。** 新窗口以新组装的上下文替换旧的模型可见历史。测试明确检查：旧用户消息、旧助手消息不会因为是“最近一轮”就自动留在下一次模型请求里；同一 Turn 的原始用户话语和刚得到的普通工具结果，也可能不再直接可见。

可以按配置保留的少数内容是特定种类，而非按时间选取的最近几轮。例如，某些客户端提供的指令，以及明确标记的特定客户端工具结果，可以在限制范围内带入新窗口。这不等于保留一般聊天消息或所有工具输出。新的用户输入若发生在换窗之后，会按正常流程加入新窗口。

因此，若用户原话中的精确限制对未完成任务仍重要，需要确保它进入可靠的任务状态、笔记或可找回的历史，而不能假定“刚刚说过”就一定仍在模型眼前。

## 7. 实现保证与可靠性边界

目前可以确认的运行时行为：

- 统计预算，在配置条件下提醒或切换。
- 成功切换后重建模型可见的必要上下文；会话和执行环境继续存在。
- 在同一 Turn 有后续工作时，切换后继续执行循环。
- 提供有条件的笔记、历史查询和短提示入口。

不能直接当成已保证的事情：

- 模型在整个工作过程中始终维护完整笔记。
- 换窗前自动验收一份有效的任务检查点。
- 换窗后强制读取笔记并确认恢复了原任务。
- 旧用户消息、助手消息或工具结果按“最近几轮”自动保留。
- 恢复提示失败时，运行时一定阻止模型继续。

所以，这套机制把“让 Turn 跨窗口继续运行”和“让模型准确找回任务状态”分成了两个问题。前者在主流程中有明确支持；后者需要笔记质量、历史可用性和模型恢复行为共同成立。要做更强的可靠性保证，仍需研究有效检查点、恢复后核验和失败处理等机制，不能仅凭当前实现声称已经解决。
