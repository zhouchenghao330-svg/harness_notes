# Harness 拆解共识

> 本文件是 all_harness 的总规则。研究任何新的 Harness 前，Agent 必须先阅读本文件。
>
> 2026-11-03 修订：源码研究保持覆盖责任，对话改为工程问题驱动、设计决策优先；研究进度与用户学习进度分别记录。

## 0. 研究目标

本项目不做完整产品架构导览，也不复述项目作者的宣传语。

目标是从代码中拆出 Agent Runtime，也就是：

- 模型如何被调用
- 一次 Agent Run 如何循环执行
- 上下文如何构造
- 工具如何注册、选择、执行和返回结果
- 状态、历史、记忆和压缩如何工作
- Agent 如何继续、停止、重试、取消或等待人工控制
- 这些部件之间如何协作

研究的最终目的，是理解目标 Harness 遇到的工程问题、采用的解决方案、相对简单实现的收益与代价，提取可跨项目复用的设计原则，并在有事实依据时与 AI-Human 等自研 Runtime 建立对照。

最终形成的 Agent Harness Pattern Library 应是“工程问题—方案—取舍—适用条件—源码证据”的知识库。不能把掌握全部内部实现、能够维护目标项目，作为高于学习可复用设计的目标。某项设计暂时不用于 AI-Human，也可以因其揭示了新的工程问题而值得学习。

## 1. 研究边界

### 1.1 纳入范围

不要只按目录名判断是否属于 Agent 部分。

只要代码会影响下列任一项，就纳入研究：

- 模型输入或输出
- System Prompt、工具描述或上下文
- Agent Loop 和 Run 生命周期
- 工具调用、工具执行或工具结果
- Session、History、State、Memory
- Compaction、Summarization、Checkpoint、Replay
- Stop、Retry、Cancel、Approval、Permission
- 事件流、流式输出和最终回复
- Provider、模型协议和响应格式适配

### 1.2 排除范围

通常排除：

- 与 Agent 行为无关的前端页面布局
- 普通登录、计费、管理后台和 CRUD
- 与 Agent Runtime 无关的部署、监控和基础设施
- 不改变模型输入输出和执行状态的通用业务逻辑

### 1.3 边界判断原则

业务代码不能一律排除。

如果业务代码实现了 Agent 工具、权限策略、结果格式化、领域上下文注入或工作流决策，就要纳入它影响 Agent 行为的那一部分。

判断标准是：

> 这段代码是否会改变 Agent 下一步看到什么、能做什么、是否继续运行，或者最终输出什么？

如果会，就属于 Harness 的行为边界。

### 1.4 源码研究完整性与用户学习进度分离

研究必须有覆盖责任，讲解必须有优先级。用户不自行阅读源码，不意味着必须逐项学习全部实现；Agent 不能把自己的源码核对清单变成用户的必修课程表。

#### A. 源码研究轨道

Agent 负责发现并沿调用链检查 Runtime 行为：核心执行链、条件分支、后台操作、状态变化、异常与恢复、并发和扩展路径。名称像工程优化的行为也按实际影响纳入，例如实体解析、向量输入加工、事实链接、增量块复用、缓存和去重。不能因为它不进入当前对话就从研究范围删除。

先建立组件的操作与风险清单，再分阶段核对。研究发现的新操作补入清单，影响核心判断或优先级时主动说明。完整性责任不要求在第一次讲解前穷尽全仓库，也不允许用局部阅读冒充整组件覆盖。

分别记录覆盖程度与证据状态：覆盖程度使用“尚未研究 / 部分核对 / 当前声明范围已核对”；结论依据区分“代码确认 / 仅文档描述 / 推断 / 待验证”。一条行为已确认，不等于组件全部研究完成；推断与未验证内容不能记为代码事实。证据细则见第 3 节第七步。

发现遗漏时，补充行为、工程影响、源码位置及研究状态。若它推翻已讲结论或揭示重要风险，主动修正并补讲；若只是低优先级实现，不自动扩展成新的必修章节。用户运行项目或提供 trace 是验证补充，不能替代 Agent 的研究责任。

#### B. 用户学习轨道

按具体工程影响、设计价值与当前学习目标为主题分级，并简述分级理由：

| 优先级 | 判断依据 | 默认讲解深度 |
| --- | --- | --- |
| P0：核心设计 | 影响执行正确性、可靠性、关键模型行为，或具有明显迁移价值 | 深入讲清问题、简单基线、方案、取舍与关键异常 |
| P1：架构机制 | 对组织、扩展、隔离或生命周期有价值，但不需要掌握全部内部实现 | 讲清真实需求、设计思想、收益、代价和适用条件，按需下钻 |
| P2：实现细节 | 特定框架的表达语法、内部包装或当前迁移价值较低的细节 | 自行研究、记录，并在主题收尾简要说明作用；默认不逐项授课 |

不能按目录、技术领域或复杂程度静态分级。一个底层检查若防止错误执行、状态污染或恢复失败，仍可能是 P0；配置、事件和生命周期也不能一律降为 P2。暂时看不出用途的机制，先给真实需求或明确标注的假设场景，再判断深度，不直接称为无用。

学习状态独立使用“待学习 / 已讲解、理解未确认 / 已理解当前深度 / 需要换方式重讲 / 已记录、未展开”。用户明确暂缓时另行注明。学习状态和写入状态分开：笔记已写入、Agent 已检查源码，均不代表用户已经理解；用户说没看进去时，恢复为需重讲。

索引以工程问题或机制为单位，不要求每个辅助函数都建学习条目。用户可以随时提高深度，或明确要求某组件所有操作逐项共同阅读。

#### C. 完成与继续的规则

每个核心主题结束时简要说明：最值得记住的设计思想、目标项目特有的实现方式，以及已记录但未展开的相关机制。用户认可，表示当前主题在当前深度达到学习目标，不表示全部源码操作都已共同学习。

模块收尾分别报告：源码覆盖情况、已共同理解的核心设计、已记录未展开的机制、待验证问题。允许“当前学习目标已达成，源码研究仍有待办”并继续下一个高价值主题；P2 细节不作为继续主线的阻塞条件。待验证问题若会影响核心判断，必须限定或暂缓该判断，不能用分级掩盖风险。

既不能把未共同学习标成已共同学习，也不能把未展开混同于未研究。保留清单和证据，使以后可以返回深入，而不要求用户先学完所有实现才能推进。

### 1.5 讲解方式：工程问题驱动，设计决策优先

默认用户已经掌握此前共同拆解并确认的 Harness 内容。先看相关组件索引，必要时读已有笔记，建立知识基线。没有读过目标项目源码，不等于没有 Agent 工程经验；通用 ReAct、工具调用、上下文与恢复机制若无实质差异，简要定位即可，重点讲目标项目的不同选择。

每轮优先讲透一个核心设计决策，默认沿下面顺序组织；简单主题可以合并表达，不必机械写成六段。

| 顺序 | 优先回答的问题 |
| --- | --- |
| 工程问题 | 要解决什么真实困难？没有该机制时，可能出现什么 Bug、失败或能力缺口？假设案例明确标注 |
| 简单基线 | 普通实现可以怎么做？用户已知的 Pi、Hermes 或典型 Runtime 可作什么对照？ |
| 目标方案 | 目标 Harness 实际怎样处理？先用具体动作、输入输出、状态变化或简图说明，再引入必要名称 |
| 设计取舍 | 相比基线增加了什么能力，又增加了什么复杂度？什么规模或需求下才值得承担？ |
| 迁移与对照 | 对 AI-Human 或其他 Runtime 可直接借鉴、可简化借鉴、暂不需要，还是仍待评估？能提取什么更简单的原则？ |
| 源码证据 | 哪些关键结论由实际代码支撑？完整调用链与特殊分支保留在研究笔记，不必全部进入对话 |

解释复杂机制必须能回答“如果不用它，会失去什么”，但不能默认复杂方案优于简单方案。区分代码证明的行为、文档明确记录的理由和根据设计推测的动机；不能凭机制存在就声称作者必然出于某种考虑。

AI-Human 对照只能使用已确认的当前事实。没有检查过的具体实现不能假设存在某个缺陷或已经满足某种需求；改用明确的假设场景，或标为待评估。不强行要求每个机制立即迁移，允许学习面向未来需求的设计原则。

讲解还必须遵守：

- 先典型路径，再影响结论的重要异常；其余分支按优先级记录。源码多一个机制，不自动新增一个必修小节。
- 用人话解释职责和工程影响，保持技术深度；陌生函数、变量、类型或缩写先解释是什么、做什么，再给名称，不能把源码名当作解释本身。
- 用连续例子、简图和小表格建立对照，控制同时出现的概念；不为证明研究充分而罗列函数、字段和配置，也不复述用户已掌握的基础。
- 用户反馈抽象、看不进去或不懂时，先检查工程问题与对照基线是否建立；换场景重新解释，不只是缩短句子、换成更简单的词或继续补实现细节。

### 1.6 先建立整体认识，再局部深入

正式深入组件前，先提供全局认知地图：核心责任有哪些、一次完整运行怎样发生、最有特点的架构决策是什么、哪些属于通用 Agent 问题而哪些属于框架组织方式，以及哪些方向最值得先研究。

架构图应帮助识别目标项目的责任划分、数据与控制关系和关键差异；对已有 Agent 经验的用户，只画通用“模型—工具—模型”流程不算建立该项目的架构认识。

先沿 Agent 执行主线形成完整理解，再围绕高价值设计下钻。涉及 Cordis 等通用框架时，先交代它承担的责任、解决的问题、代价及与 Runtime 的关系；其配置语法、内部调度与生命周期实现按实际价值展开，不能成为进入主线前的无限前置课程。

## 2. Agent-centric 核心模型

研究重点是下面这条运行链：

用户输入
  ↓
入口 / Session / Run
  ↓
Context Builder
  ├─ System Prompt
  ├─ Conversation History
  ├─ Tool Definitions
  ├─ Runtime State
  └─ Retrieved Context
  ↓
Model Adapter
  ↓
模型文本或 Tool Call
  ├─ 最终文本 → 输出 / 事件流
  └─ Tool Call → Tool Router → Tool Executor
                         ↓
                    Observation
                         ↓
              State / History / Memory
                         ↓
              Continue / Stop / Retry / Compact

以下能力通常作为横切关注点单独记录：

- Permission / Human Approval
- Cancel / Timeout / Error Recovery
- Persistence / Checkpoint / Replay
- Logging / Tracing / Event Streaming
- Provider / Model Configuration

## 3. 固定研究流程

以下是源码研究与建立地图的顺序，不是用户必须逐目录学完的授课顺序。研究分阶段推进，对话按第 1.4—1.6 节围绕高价值设计组织；不得以此流程要求用户先掌握整个底层框架。

### 第一步：粗扫项目

粗扫的目的只有一个：定位 Agent Runtime。

不要先总结整个项目，也不要先画包含前端、后端、数据库和部署的产品架构图。

需要找到：

- CLI、TUI、API 或其他 Agent 入口
- Session、Run 或 Task 的创建位置
- 主 Agent Loop
- LLM 请求入口
- Tool 注册和执行入口
- Prompt / Context 组装入口
- History、Memory、Compaction 和 Persistence 入口

### 第二步：划定 Agent Runtime 边界

建立一份 Scope 记录，明确：

- 纳入哪些目录、模块、类和函数
- 排除哪些产品层代码
- 哪些边界目前仍不确定
- 哪些业务代码只保留其 Agent 行为相关部分

### 第三步：追踪一次完整运行

优先追踪一条真实调用链：

用户输入
→ 创建 Run
→ 组装上下文
→ 调用模型
→ 返回文本或 Tool Call
→ 执行工具
→ 写入结果
→ 继续或停止
→ 持久化和输出

记录每一步的：

- 入口函数
- 关键数据结构
- 输入和输出
- 状态变化
- 失败、重试、取消和停止条件

### 第四步：绘制 Agent 架构图

只绘制 Agent-centric architecture。

架构图必须表达：

- 主要组件
- 数据流
- 控制流
- 循环位置
- 状态写入位置
- 横切能力的位置

不要把无关的产品工程细节放进图里。

### 第五步：拆解核心组件

至少检查：

1. Entry / Session / Run Lifecycle
2. Agent Loop
3. State / History
4. Context / Prompt Assembly
5. Model Adapter
6. Tool System
7. Memory / Compaction
8. Control：Stop / Retry / Cancel / Approval / Permission
9. Persistence / Recovery / Replay
10. Event / Streaming / Output

Evaluation 和 Benchmark 单独记录，不默认视为每次运行的核心路径。

上述清单是通用检查起点。还必须按项目实际调用链补齐组件内部的操作，并执行 1.4 的完整性和完成标准，不能因为通用框架已经讲过就认为项目特有的 Runtime 行为也已覆盖。

### 第五步补充：Tool System 和具体工具必须分开拆解

工具研究必须分成两个层次，不能用一份 Tool System 架构说明代替具体工具研究。

第一层是 Tool System，回答：

- 工具如何发现、注册和组成 Registry
- 哪些工具在当前 Session / Run 中对模型可见
- 工具 Schema 和使用说明如何进入模型请求
- Tool Call 如何校验、授权、调度和执行
- Tool Result 如何截断、持久化并写回 Context
- 并发、取消、重试、审批、Hook 和扩展如何工作

第二层是 Concrete Tools，回答 Harness 实际向模型提供了哪些能力。每个 Harness 至少需要：

1. 建立完整工具清单，记录工具名、来源、所属 Toolset、默认是否启用和主要副作用；
2. 区分内置工具、扩展工具、Plugin 工具、MCP 工具和动态生成工具；
3. 对核心工具逐个核对；工具数量较多时，可以按文件、终端、搜索、浏览器、网络、记忆、委派等能力分组。对话选择有设计差异或重要风险的工具深入，相同机制归并讲解；
4. 为具体工具分别标记源码覆盖、证据依据和学习深度；不能因为 Tool System 框架已读，就认为具体工具已研究，也不能因未逐个讲解就把已核对工具写成未研究。

每个具体工具或工具组至少检查：

- 模型看到的名称、描述、参数 Schema 和使用指导
- 工具被选择和触发的条件
- 内部执行流程及关键实现入口
- 返回给模型的 content 与仅供 UI / 日志使用的 details
- 输出截断、外溢、临时文件和大结果取回方式
- 文件、网络、进程或其他副作用
- Permission、Approval、Guardrail 和安全边界
- 并发模式、资源冲突、取消、超时和错误处理
- 是否支持 Hook、Extension、Plugin、MCP 或自定义实现覆盖
- 当前设计的优点、代价、限制及跨 Harness 可比较点

工具组件分别判断研究与学习完成情况：研究要覆盖 Tool System、完整 Concrete Tool Inventory 及核心工具或工具组的实际行为，并如实保留尚未核对项；缺项时不能声称源码研究完整。用户学习则以理解工具体系的关键设计、具有差异或重要风险的工具行为为目标，其他实现按 P0/P1/P2 记录和展开。用户不需要逐项听完所有工具才能继续，但完整清单、模型可见 Schema、副作用与安全边界不能从研究中省略。

### 第六步：分析 Prompt

不要只复制静态 System Prompt。

需要确认：

- Prompt 的源文件
- Prompt 的组装函数
- 各段的插入顺序
- 条件分支和动态变量
- 工具描述如何进入 Prompt 或请求
- 最终发给模型的完整请求结构
- Prompt 规定的行为与代码实际行为是否一致

Prompt 是行为契约的一部分，但最终请求 Payload 才是运行时事实。

### 第七步：回到代码确认

所有重要结论都要尽量绑定代码证据：

- 文件路径
- 类名、函数名或模块名
- 调用关系
- 关键字段
- 必要时记录代码行号

区分三种结论：

- Code-verified：代码已经确认
- Docs-described：文档或注释这样描述
- Inferred：根据代码行为推断

不要把推断写成已确认事实。

## 4. 源码研究清单与对话讲解问题

下列十项用于 Agent 的源码研究和笔记整理，不要求在每次对话中逐条展示。研究任何组件时，至少回答：

1. 它解决什么问题？
2. 什么时候被触发？
3. 输入是什么？
4. 输出是什么？
5. 状态存在哪里？
6. 它与哪些组件连接？
7. 它如何影响 Agent 的下一步？
8. 出错、重试、取消时如何处理？
9. 有哪些替代设计？
10. 当前设计的优点、代价和限制是什么？

面向用户的默认讲解聚焦五个问题：

1. 它解决什么工程问题？
2. 不采用这个设计，最容易出现什么问题或能力缺口？
3. 目标 Harness 怎样解决，相比简单基线改变了什么？
4. 收益、成本、替代方案和适用条件是什么？
5. 对其他 Runtime，尤其 AI-Human，有什么借鉴价值？

输入、输出、触发条件、状态、异常和函数关系继续研究，按理解当前设计所需的程度呈现。研究追求事实与覆盖可靠，讲解追求形成判断，而不是让用户记住内部名称。

## 5. 推荐的单个 Harness 笔记结构

每个 Harness 使用独立子目录：

### 设计决策卡片

对真正具有复用价值的机制，增加简短卡片，可放在相应组件笔记或设计模式汇总中；不要求每个函数或配置项单独建卡。

| 字段 | 内容 |
| --- | --- |
| 工程问题 | 解决什么真实困难或失败场景 |
| 简单基线 | 不采用该复杂机制时可以怎样实现 |
| 目标方案 | 项目实际采用什么设计 |
| 关键差异 | 相比基线获得什么能力或保证 |
| 设计代价 | 增加了哪些状态、配置、并发或维护复杂度 |
| 适用条件 | 什么需求或规模下值得采用，何时简单方案足够 |
| AI-Human 对照 | 可直接借鉴、可简化借鉴、暂不需要或待评估；注明事实或假设 |
| 源码证据 | 关键路径、验证依据、尚未核对与推断部分 |

卡片的目标是形成可复用判断，不是把源码说明换一个模板重复一遍。主题收尾先交代最值得记住的设计思想、项目特有细节和未展开机制，再继续下一个高价值设计。

## 6. 架构图要求

默认使用 ASCII 图，并用中文标注关键含义。

图中至少要能看出：

- 谁接收用户输入
- 谁构造上下文
- 谁调用模型
- 谁决定是否调用工具
- 工具结果如何回到循环
- 谁决定继续或停止
- 状态和历史在哪里保存
- 输出如何返回用户

如果一个组件同时属于多个路径，用横切注释标明，不要重复画出导致误解。

## 7. 研究纪律

- 先看代码，再写结论。
- 不要用产品 README 代替运行时分析。
- 不要因为目录叫 agent 就默认它是核心。
- 不要因为代码在业务目录就默认它与 Harness 无关。
- 不要只列出工具名称，要分析工具生命周期。
- 不要只分析 Tool System 框架；必须另建 Concrete Tool Inventory，并拆解核心工具实现。
- 工具数量较多时允许按能力分组，但不能因此省略工具清单、模型可见 Schema、副作用和安全边界。
- 不要只复制 Prompt，要查看最终请求。
- 不要把 Memory、History、Context 和 Compaction 混成一个概念。
- 不要把漂亮的架构图当作代码证据。
- 不确定的内容标记为待验证。
- 不从源码研究中删除已发现的 Runtime / Harness 相关操作；沿调用链补齐清单和证据状态，对话按学习价值分级。研究未覆盖、已研究未展开与用户未理解必须分开。
- 用户确认当前主题或深度，不等于全部实现已共同学习；按 1.4 分别报告研究覆盖与学习达成，允许记录低优先级细节后继续主线，不机械补完所有实现才推进。
- 研究阶段不修改项目源码；写入 Obsidian 前先确认用户要求。用户已明确授权后续自行选择写入点时，在该范围内持续执行，不重复索取确认；写入不等于用户理解或认可结论。

## 8. 跨 Harness 比较

研究多个 Harness 时，使用同一组比较维度：

- Loop 形态
- State 表示
- Context 组装
- Tool 生命周期
- Memory 和 Compaction
- Stop / Retry / Cancel
- Human Control
- Persistence / Replay
- Model / Provider 抽象
- Plugin / Extension 机制
- CLI、TUI、API 等外壳如何接入核心 Runtime

比较时围绕同一工程问题，记录简单基线、各 Harness 的具体设计、收益与代价，不只记录功能是否存在。以已有 Pi、Hermes 等学习结果建立对照，明确目标项目的差异。迁移建议遵守第 1.5 节的事实与假设区分，不把 AI-Human 对照变成强行移植。

核心问题是：

> 同一个 Harness 问题，不同项目分别选择了什么方案？为什么？代价是什么？
