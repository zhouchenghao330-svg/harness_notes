# Harness 拆解共识

> 本文件是 all_harness 的总规则。研究任何新的 Harness 前，Agent 必须先阅读本文件。

## 0. 研究目标

本项目不做完整产品架构导览，也不复述项目作者的宣传语。

目标是从代码中拆出 Agent Runtime，也就是：

- 模型如何被调用
- 一次 Agent Run 如何循环执行
- 上下文如何构造
- 工具如何注册、选择、执行和返回结果
- 状态、历史、记忆和压缩如何工作
- Agent 如何继续、停止、重试、取消或等待人工控制
- 这些部件之间如何协作

最终要形成的是 Agent Harness Pattern Library，而不是项目功能清单。

## 1. 研究边界

### 1.1 纳入范围

不要只按目录名判断是否属于 Agent 部分。

只要代码会影响下列任一项，就纳入研究：

- 模型输入或输出
- System Prompt、工具描述或上下文
- Agent Loop 和 Run 生命周期
- 工具调用、工具执行或工具结果
- Session、History、State、Memory
- Compaction、Summarization、Checkpoint、Replay
- Stop、Retry、Cancel、Approval、Permission
- 事件流、流式输出和最终回复
- Provider、模型协议和响应格式适配

### 1.2 排除范围

通常排除：

- 与 Agent 行为无关的前端页面布局
- 普通登录、计费、管理后台和 CRUD
- 与 Agent Runtime 无关的部署、监控和基础设施
- 不改变模型输入输出和执行状态的通用业务逻辑

### 1.3 边界判断原则

业务代码不能一律排除。

如果业务代码实现了 Agent 工具、权限策略、结果格式化、领域上下文注入或工作流决策，就要纳入它影响 Agent 行为的那一部分。

判断标准是：

> 这段代码是否会改变 Agent 下一步看到什么、能做什么、是否继续运行，或者最终输出什么？

如果会，就属于 Harness 的行为边界。

### 1.4 Runtime 内容的完整性和模块完成标准

用户可能不运行项目，也不自行阅读源码，而是通过 Agent 的讲解建立对项目的理解。因此，Agent 必须主动发现并说明 Runtime / Harness 的相关行为，承担研究清单和阅读进度的完整性责任，不能依赖用户追问才补充核心操作。

与 Agent 行为无关的普通工程细节可以省略。凡是会影响模型调用、上下文、工具、状态、记忆、持久化、检索结果或运行控制的实现，都必须纳入拆解。名称看起来像工程优化的代码也要按行为判断：例如记忆写入中的实体解析、向量输入加工、事实链接、增量块复用，以及缓存、去重、后台处理或恢复路径，只要影响上述行为，就不能直接略过。

每个组件必须遵守以下规则：

1. **先建立完整操作清单，再分组讲解。** 沿实际调用链检查主要操作、条件分支、后台任务、输入输出和状态变化；不能只列自己准备讲的几项。研究中发现的新操作必须补入清单，并主动告知用户。无法确认的行为标记为待验证。
2. **每项保留明确的阅读状态。** 区分已共同阅读、部分阅读、待共同阅读、用户明确暂缓或待验证。Agent 自己检查过代码、只讲过总体流程或讲过邻近操作，都不能代替这一项的共同阅读；写入状态也要单独说明。
3. **用户说懂了，只确认当前讲解范围。** “大概懂了”“整体 OK”“可以写入”等反馈，不自动授权跳过尚未讲解的 Runtime 内容。除非用户明确要求跳过、停止或缩小范围，否则按清单继续。用户明确暂缓的内容仍保留状态，不改成已经完成。
4. **结束模块前逐项核对。** 主动说明已讲内容和仍未覆盖的内容，并同步组件索引与笔记进度。存在尚未讲解或待验证的 Runtime 操作时，模块只能标记为部分完成，不能宣布全部结束，也不能自行把剩余项改成可选、按需展开或直接进入下一组件。
5. **发现遗漏就恢复对应进度。** 明确指出遗漏内容、它对 Runtime 的影响及其所在位置，修正此前的完成标记，继续补讲；不让用户自行看代码、运行项目或再次追问来补齐研究范围。用户运行项目和提供 trace 是理解及验证的补充，不是完整拆解的前提。

讲解可以分层、分组、分多轮进行，但每一轮必须让用户知道当前讲到哪里、还有什么未覆盖。只有完成清单核对，才能把“当前操作已懂”推进为“整个组件已完成”。

### 1.5 讲解方式：先讲运行行为，再给源码名称

用户通常没有读过项目源码。对话中的组件讲解必须先用人话建立运行画面，不把内部函数名、变量名、类名或缩写当作解释本身。

1. **先讲动作、输入输出和原因。** 用一句具体输入或真实任务说明：谁收到什么、做了什么、留下或返回什么、为什么需要这一步、会影响模型下一步看到什么或系统状态怎样变化。
2. **源码名称后置。** 必须提到函数、变量或类型时，先解释其职责，再给名称作为定位；不要连续堆内部名称、直接照读调用链，或要求用户先看代码才能听懂。详细源码路径、函数名和字段定位可保留在笔记的独立源码锚点中。
3. **先例子和行为图，再抽象。** 优先沿一个连续例子讲清实际数据与责任交接，图中先使用「保存事实」「查找相关记忆」「检查是否冲突」等动作。说明默认路径后，再解释扩展、例外和分工差异；不要直接用抽象接口术语开场。
4. **控制同时出现的概念。** 分小组、分层讲；陌生术语先定义，再解释作用。用 ASCII 流程图、具体前后状态和小表格帮助理解。简化表达不代表省略 Runtime 行为，仍须执行 1.4 的完整性及进度要求。
5. **用户说抽象时，重讲当前内容。** 用具体输入、输出和行为重新解释，不仅道歉或缩短原有术语说明。用户认可当前讲解后，再按授权写入笔记；其余未讲操作继续保留状态。

推荐顺序：具体场景 -> 实际动作及状态变化 -> 为什么需要 -> 分工与边界 -> 可复用抽象 -> 源码定位。讲解应让用户在不打开代码的情况下理解运行行为，同时由 Agent 自己核对代码证据。

## 2. Agent-centric 核心模型

研究重点是下面这条运行链：

用户输入
  ↓
入口 / Session / Run
  ↓
Context Builder
  ├─ System Prompt
  ├─ Conversation History
  ├─ Tool Definitions
  ├─ Runtime State
  └─ Retrieved Context
  ↓
Model Adapter
  ↓
模型文本或 Tool Call
  ├─ 最终文本 → 输出 / 事件流
  └─ Tool Call → Tool Router → Tool Executor
                         ↓
                    Observation
                         ↓
              State / History / Memory
                         ↓
              Continue / Stop / Retry / Compact

以下能力通常作为横切关注点单独记录：

- Permission / Human Approval
- Cancel / Timeout / Error Recovery
- Persistence / Checkpoint / Replay
- Logging / Tracing / Event Streaming
- Provider / Model Configuration

## 3. 固定研究流程

每个新的 Harness 都按以下顺序研究。

### 第一步：粗扫项目

粗扫的目的只有一个：定位 Agent Runtime。

不要先总结整个项目，也不要先画包含前端、后端、数据库和部署的产品架构图。

需要找到：

- CLI、TUI、API 或其他 Agent 入口
- Session、Run 或 Task 的创建位置
- 主 Agent Loop
- LLM 请求入口
- Tool 注册和执行入口
- Prompt / Context 组装入口
- History、Memory、Compaction 和 Persistence 入口

### 第二步：划定 Agent Runtime 边界

建立一份 Scope 记录，明确：

- 纳入哪些目录、模块、类和函数
- 排除哪些产品层代码
- 哪些边界目前仍不确定
- 哪些业务代码只保留其 Agent 行为相关部分

### 第三步：追踪一次完整运行

优先追踪一条真实调用链：

用户输入
→ 创建 Run
→ 组装上下文
→ 调用模型
→ 返回文本或 Tool Call
→ 执行工具
→ 写入结果
→ 继续或停止
→ 持久化和输出

记录每一步的：

- 入口函数
- 关键数据结构
- 输入和输出
- 状态变化
- 失败、重试、取消和停止条件

### 第四步：绘制 Agent 架构图

只绘制 Agent-centric architecture。

架构图必须表达：

- 主要组件
- 数据流
- 控制流
- 循环位置
- 状态写入位置
- 横切能力的位置

不要把无关的产品工程细节放进图里。

### 第五步：拆解核心组件

至少检查：

1. Entry / Session / Run Lifecycle
2. Agent Loop
3. State / History
4. Context / Prompt Assembly
5. Model Adapter
6. Tool System
7. Memory / Compaction
8. Control：Stop / Retry / Cancel / Approval / Permission
9. Persistence / Recovery / Replay
10. Event / Streaming / Output

Evaluation 和 Benchmark 单独记录，不默认视为每次运行的核心路径。

上述清单是通用检查起点。还必须按项目实际调用链补齐组件内部的操作，并执行 1.4 的完整性和完成标准，不能因为通用框架已经讲过就认为项目特有的 Runtime 行为也已覆盖。

### 第五步补充：Tool System 和具体工具必须分开拆解

工具研究必须分成两个层次，不能用一份 Tool System 架构说明代替具体工具研究。

第一层是 Tool System，回答：

- 工具如何发现、注册和组成 Registry
- 哪些工具在当前 Session / Run 中对模型可见
- 工具 Schema 和使用说明如何进入模型请求
- Tool Call 如何校验、授权、调度和执行
- Tool Result 如何截断、持久化并写回 Context
- 并发、取消、重试、审批、Hook 和扩展如何工作

第二层是 Concrete Tools，回答 Harness 实际向模型提供了哪些能力。每个 Harness 至少需要：

1. 建立完整工具清单，记录工具名、来源、所属 Toolset、默认是否启用和主要副作用；
2. 区分内置工具、扩展工具、Plugin 工具、MCP 工具和动态生成工具；
3. 对核心工具逐个拆解；工具数量较多时，可以按文件、终端、搜索、浏览器、网络、记忆、委派等能力分组；
4. 标记哪些工具已经共同阅读，哪些仍待研究，不能因为 Tool System 框架已完成就把具体工具研究视为完成。

每个具体工具或工具组至少检查：

- 模型看到的名称、描述、参数 Schema 和使用指导
- 工具被选择和触发的条件
- 内部执行流程及关键实现入口
- 返回给模型的 content 与仅供 UI / 日志使用的 details
- 输出截断、外溢、临时文件和大结果取回方式
- 文件、网络、进程或其他副作用
- Permission、Approval、Guardrail 和安全边界
- 并发模式、资源冲突、取消、超时和错误处理
- 是否支持 Hook、Extension、Plugin、MCP 或自定义实现覆盖
- 当前设计的优点、代价、限制及跨 Harness 可比较点

工具章节的完成标准是：

~~~text
Tool System 架构已确认
        +
Concrete Tool Inventory 已建立
        +
核心工具或核心工具组已共同阅读
~~~

缺少其中任一项时，Tool 组件只能标记为“部分完成”。

### 第六步：分析 Prompt

不要只复制静态 System Prompt。

需要确认：

- Prompt 的源文件
- Prompt 的组装函数
- 各段的插入顺序
- 条件分支和动态变量
- 工具描述如何进入 Prompt 或请求
- 最终发给模型的完整请求结构
- Prompt 规定的行为与代码实际行为是否一致

Prompt 是行为契约的一部分，但最终请求 Payload 才是运行时事实。

### 第七步：回到代码确认

所有重要结论都要尽量绑定代码证据：

- 文件路径
- 类名、函数名或模块名
- 调用关系
- 关键字段
- 必要时记录代码行号

区分三种结论：

- Code-verified：代码已经确认
- Docs-described：文档或注释这样描述
- Inferred：根据代码行为推断

不要把推断写成已确认事实。

## 4. 每个组件必须回答的问题

研究任何组件时，至少回答：

1. 它解决什么问题？
2. 什么时候被触发？
3. 输入是什么？
4. 输出是什么？
5. 状态存在哪里？
6. 它与哪些组件连接？
7. 它如何影响 Agent 的下一步？
8. 出错、重试、取消时如何处理？
9. 有哪些替代设计？
10. 当前设计的优点、代价和限制是什么？

## 5. 推荐的单个 Harness 笔记结构

每个 Harness 使用独立子目录：

- 00_overview.md：项目定位和核心思想
- 01_scope.md：Agent Runtime 边界
- 02_architecture.md：Agent-centric ASCII 架构图
- 03_runtime_loop.md：一次 Run 的完整生命周期
- 04_context_and_prompt.md：Context 和 Prompt 组装
- 05_tool_system.md：Tool 的注册、选择、执行和观察
- 05_tools/00_inventory.md：具体工具清单、分类、来源和阅读状态
- 05_tools/<tool-or-group>.md：核心工具或工具组的参数、执行逻辑、安全边界和设计取舍
- 06_memory_and_compaction.md：Memory、History、Summarization、Compaction
- 07_control_persistence_output.md：取消、审批、重试、持久化和输出
- 08_design_patterns.md：设计模式、取舍和可比较结论

不要一开始就填满所有文件。

先完成 Scope、一次运行链路和 Architecture，再根据代码实际情况拆分细节。

## 6. 架构图要求

默认使用 ASCII 图，并用中文标注关键含义。

图中至少要能看出：

- 谁接收用户输入
- 谁构造上下文
- 谁调用模型
- 谁决定是否调用工具
- 工具结果如何回到循环
- 谁决定继续或停止
- 状态和历史在哪里保存
- 输出如何返回用户

如果一个组件同时属于多个路径，用横切注释标明，不要重复画出导致误解。

## 7. 研究纪律

- 先看代码，再写结论。
- 不要用产品 README 代替运行时分析。
- 不要因为目录叫 agent 就默认它是核心。
- 不要因为代码在业务目录就默认它与 Harness 无关。
- 不要只列出工具名称，要分析工具生命周期。
- 不要只分析 Tool System 框架；必须另建 Concrete Tool Inventory，并拆解核心工具实现。
- 工具数量较多时允许按能力分组，但不能因此省略工具清单、模型可见 Schema、副作用和安全边界。
- 不要只复制 Prompt，要查看最终请求。
- 不要把 Memory、History、Context 和 Compaction 混成一个概念。
- 不要把漂亮的架构图当作代码证据。
- 不确定的内容标记为待验证。
- 不主动省略已发现的 Runtime / Harness 相关操作；沿调用链补齐清单，并公开尚未覆盖的内容。
- 不把用户对当前操作的理解确认当成整个模块的完成确认；结束模块前按 1.4 核对清单和阅读状态。
- 研究阶段不修改源码；写入 Obsidian 前先确认用户要求。

## 8. 跨 Harness 比较

研究多个 Harness 时，使用同一组比较维度：

- Loop 形态
- State 表示
- Context 组装
- Tool 生命周期
- Memory 和 Compaction
- Stop / Retry / Cancel
- Human Control
- Persistence / Replay
- Model / Provider 抽象
- Plugin / Extension 机制
- CLI、TUI、API 等外壳如何接入核心 Runtime

比较时记录具体设计取舍，不只记录功能是否存在。

核心问题是：

> 同一个 Harness 问题，不同项目分别选择了什么方案？为什么？代价是什么？
