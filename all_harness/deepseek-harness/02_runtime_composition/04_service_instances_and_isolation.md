## 1. 工程问题：同一套代码怎样同时服务两种配置

假设同一个 DSH 进程里有两类 Agent：日常助手希望上下文达到容量的 70% 时压缩，研究助手希望达到 90% 时才压缩。两者可以使用同一套压缩算法，但需要各自的参数。

复用代码不要求共用同一个对象。同一份实现可以创建多份对象，每份对象保存自己的配置和运行状态。

```text
同一套压缩实现代码
    │
    ├─ 压缩实例甲：70% 时压缩
    │
    └─ 压缩实例乙：90% 时压缩
```

这里的“服务实例”，就是程序运行时创建的一个对象，提供可调用的方法，并保存这份服务需要的配置和状态。当前基础压缩实现确实是类：`BasicCompactionEngine` 的实例保存解析后的 `config`，也保存按 Agent、Session 区分的部分运行状态。

因此，把压缩组件理解成“可以实例化的类”，适合解释这个例子。它不是所有 Cordis 插件的统一写法；插件也可以是函数，服务实例只是插件可能提供的一类贡献。

## 2. 简单基线：创建两个对象，再传给使用者

普通 Runtime 可以直接创建两份压缩对象，把实例甲传给日常助手，把实例乙传给研究助手。这种设计合理，也能做到配置一次、后续复用。

```text
创建日常助手 → 连接已配置好的压缩实例甲
创建研究助手 → 连接已配置好的压缩实例乙
```

另一种方式是共享一个服务，每次调用时传入不同策略参数。它同样可行，只是调用方需要负责传递本次应采用的配置。

如果只有一个保存固定配置的全局压缩实例，两类 Agent 就会使用这一份配置；修改该实例上的共享配置，可能同时影响它们。是否需要多份实例，取决于配置、状态和资源的共享需求，不能仅凭存在多个 Agent 就认定必须拆开。

## 3. DSH 方案：把服务提供者和调用方组成一组

DSH 把功能组织成插件。压缩实现是一个插件，处理用户 `/compact` 命令的代码是另一个插件。装配时既要选择实现和参数，也要让调用方连接到正确的服务实例。

```text
同一个 DSH 进程
│
├─ 日常助手 Preset 的插件组合
│    └─ 压缩插件组
│         ├─ 压缩服务甲：70%
│         └─ /compact 命令插件
│              └─ ctx.compaction → 服务甲
│
└─ 研究助手 Preset 的插件组合
     └─ 压缩插件组
          ├─ 压缩服务乙：90%
          └─ /compact 命令插件
               └─ ctx.compaction → 服务乙
```

`ctx` 是插件使用的 Cordis 运行对象，`ctx.compaction` 表示访问当前插件所连接的压缩服务。两个组里的调用代码可以使用相同名称，由装配配置决定分别连接哪份实例。

这里的隔离按服务名指定。为一个组隔离 `compaction`，并不意味着这个组用到的模型、会话、工具注册表等服务全部复制一份；没有另行隔离的服务继续按继承的配置查找。

当前 Web 的 `standard` Preset 有真实的压缩插件组：组上配置 `isolate.compaction: true`，组内装载基础压缩实现、`/compact` 命令和工具结果裁剪插件，并另外隔离裁剪服务。这说明服务提供者与消费者需要正确组合，而不是只给提供者单独加标记。

`/compact` 命令声明依赖压缩服务，执行时调用其 `compactNow()`，并传入本次操作的 Agent。它不需要在命令代码里写死“日常助手服务”或“研究助手服务”。

## 4. 参数仍需配置，隔离解决连接与共存

“不用每次重新配置”应理解为：装配插件组合时给出参数，创建实例，后续调用复用这份已配置实例。不同 Preset 需要不同参数时，仍然要分别配置。

配置一次后复用，并非服务隔离独有的能力。DSH 服务隔离增加的是：多份同名服务可以在不同组中同时存在，调用插件按所属组连接相应实例。

| 问题 | 对应设计 |
| --- | --- |
| 多种 Agent 使用相同的压缩算法 | 复用实现代码 |
| 两种组合使用不同压缩参数 | 创建并配置不同实例 |
| 多份实例都叫压缩服务，调用方该找哪份 | 按隔离标识查找服务 |
| 多个 Agent 使用同一份已装载组合 | 可以共享该组合中的服务实例 |

底层查找先读取当前插件对于该服务名的隔离标识，再找到对应实现，不采用“同名就任意选一个”。同一服务位置重复注册会报错；Preset 内的插件若把服务发布到全局范围，装配检查也会拒绝该组合。

## 5. 不必每个 Agent 创建一个实例

“为不同 Agent 配置不同实例”可以表达需求，但当前 DSH 的常见装配单位是一份 Preset 修订所装载的插件组合。修订就是该 Preset 某次定义对应的运行版本，详见 02.2。

使用同一份已装载组合的多个 Agent，可以共享其中的服务实例。

```text
日常助手 Agent A ─┐
                  ├─ 共享日常助手组合中的压缩实例甲
日常助手 Agent B ─┘

研究助手 Agent C ─── 使用研究助手组合中的压缩实例乙
```

共享实例不等于共享所有会话数据。压缩方法接收本次 Agent，服务仍须按 Agent 或 Session 管理各自的数据。服务隔离不能代替实例内部正确的数据归属，也不自动提供独立进程、独立文件系统或操作系统沙箱。

## 6. 设计收益、代价与适用条件

最值得保留的思想是：代码复用、配置复用与实例共享是三种不同的选择。先判断哪些配置、状态和资源可以共享，再决定创建多少实例，以及怎样把实例交给使用者。

| 设计决策 | 判断 |
| --- | --- |
| 工程问题 | 多套插件组合需要同时使用配置或实现不同的同名服务 |
| 简单基线 | 创建不同对象，显式传给使用者；或共享服务并在调用时传策略参数 |
| DSH 方案 | 为插件组指定服务隔离，将提供者与消费者连接到同一组的实例 |
| 关键收益 | 调用代码保持相同，多套组合可以通过装配选择各自的实例 |
| 设计代价 | 排查一次调用时，需要同时核对服务名、调用插件所属组、对应实例与组合生命周期 |
| 适用条件 | 多套能力组合需要配置装配、替换实现和复用；组件关系固定时，显式传对象通常更直接 |
| AI-Human 对照 | 尚未核对当前实现，不判断其是否需要此机制；可借鉴“先确定共享单位，再选择实例组织方式”的原则 |

## 7. 已核对范围与后续问题

已共同理解当前深度：同一份压缩代码可创建不同参数的实例；参数在装配时配置；隔离让不同组合的同名服务共存，并使调用方连接对应实例；同一份 Preset 运行组合中的多个 Agent 可以共享实例。
