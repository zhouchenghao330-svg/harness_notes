## 1. 核心选择：从 Session 记录生成模型历史

DSH 把 Session 记录作为构造模型输入的依据。循环先记录接纳的模型可见内容，再从当前生效的消息节点生成模型历史；模型选择、参数与工具定义由已记录的请求配置配合提供。这是事件溯源思路在模型上下文上的应用。

普通 Runtime 可以维护 `messages[]`，依次加入用户消息、模型回答和工具结果。这种实现本身合理；如果另外维护一份运行记录，就需要确定哪份是依据，以及如何保证它们一致。

假设插件给本次请求临时补充“项目使用 Python 3.12”，却没有保存这段内容。模型当时可以正常使用它，但以后检查记录或恢复会话，就可能无法解释模型为何按该版本处理。这个例子说明的是可重建性需求，不是对其他 Runtime 当前实现的判断。

DSH 的要求是：模型看到的内容必须能从 Session 记录重建。注入背景、修改历史等行为都要留下相应记录，不能只修改本次请求而把影响模型判断的事实留在记录之外。

## 2. 沿读取 README 的任务看典型路径

```text
用户要求：读取 README，告诉我怎样启动项目
                    ↓
领取输入，准备提示、工具与请求
                    ↓
把接纳的消息、提示及必要的请求配置记入 Session
                    ↓
从 Session 当前生效的内容生成模型请求
                    ↓
模型返回读取文件的工具调用
                    ↓
记录模型回答，执行工具并记录结果
                    ↓
从更新后的 Session 生成下一次请求
                    ↓
模型给出启动方式
```

默认循环中的 `step()` 追加接纳的系统提示和用户消息，然后调用 `buildRequest()`。后者按需记录请求配置，调用 `session.deriveMessages()` 取得历史，再构造并冻结本次请求。

headless 的输入最终通过 `agent.followup()` 进入队列；runner 等待运行及相关子任务收束，调用 Session flush，再输出结果。入口只在这里定位，不把它的完整恢复和退出路径视为已经共同学习。

## 3. 完整记录与当前模型历史分开

Session 的完整事件记录不等于每次发送给模型的聊天消息。当前生效的消息集合由 Session 的 surface 管理；这里把 surface 理解成“当前模型历史采用哪些消息节点的有序视图”，不要求先掌握其内部数据结构。

| 内容 | 完整 Session 记录 | 当前模型历史 |
| --- | --- | --- |
| 当前生效的用户消息、模型回答、工具结果 | 保留 | 进入 |
| turn 开始、结束等运行事件 | 保留 | 不作为聊天消息进入 |
| 已被压缩摘要替代的旧消息 | 仍保留 | 不再按原文进入 |
| 模型与工具定义等请求配置 | 保留必要的快照和变化 | 配合消息生成请求，不全部转成聊天消息 |

因此，压缩不等于删除日志中的旧消息。DSH 记录替换关系，改变当前生效的消息集合；后续历史生成采用替换后的内容。压缩范围选择、摘要算法、失败处理和持久化仍在对应组件单独研究。

“先记录再调用模型”中的记录是追加到 Session，不等于每次请求前都完成了磁盘落盘。Session 可以只存在于内存；持久化插件、写入缓冲、flush 和关闭操作分别提供什么保证，仍需核对。

## 4. 收益、代价与迁移判断

| 项目 | 判断 |
| --- | --- |
| 工程问题 | 模型实际看到的输入与调试、恢复所依据的记录可能分离 |
| 简单基线 | 维护并保存完整消息列表；若有额外运行记录，明确其与消息列表的同步关系 |
| DSH 方案 | 记录模型可见事实与请求配置，从记录派生当前历史并构造请求 |
| 关键收益 | 调试、恢复和压缩后的历史生成可以依据同一份记录解释 |
| 设计代价 | 需要事件定义、当前消息生效关系和历史生成规则，修改输入也要维护相应记录 |
| 适用条件 | 对恢复、分支、压缩、多插件扩展和请求可解释性有持续需求时更有价值 |
| 可简化借鉴 | 先确定模型历史的唯一依据；插件改变模型可见内容时留下可重建的记录，不必直接复制完整事件体系 |
| AI-Human 对照 | 尚未核对当前实现，不判断其是否存在记录与请求不一致的问题 |

最值得保留的原则是：明确模型历史从哪里生成，并让所有影响它的修改留下记录。DSH 特有的组织方式是 Session 类型化事件、当前生效消息视图与请求配置记录的配合。

## 5. 工具结果缺失：记录未知状态，再决定怎样继续

工具没有返回结果，不代表工具没有产生效果。假设工具已向 `CHANGELOG.md` 追加一条记录，却在保存工具结果之前中断；统一告诉模型“失败，请重试”，可能导致重复追加。这个例子用于说明副作用与回执之间的不确定性，不是本次实际执行的操作。

默认工具调度的典型顺序是：模型提出调用，Harness 登记 `tool/call`，准备并执行工具，再登记 `tool/result`。开始标记在工具准备之前写入，因此它不证明工具主体已经执行。

| 已有记录 | 缺失结果的处理 |
| --- | --- |
| 已有 `tool/result` | 保留原结果，不改写 |
| 模型提出调用，但没有开始记录 | 补入“未记录为开始”的错误工具结果，代码为 `TOOL_NOT_STARTED` |
| 有开始记录，但没有结果 | 补入“结果未知”的错误工具结果，代码为 `TOOL_OUTCOME_UNKNOWN` |

有开始记录却没有结果，可能表示尚未执行、只执行一部分，或已完成但没有留下结果。DSH 根据现有证据保守分类，不把它直接解释成成功、失败或已回滚。

补齐的内容是模型可见的工具结果，不只是运行诊断。对于当前执行或崩溃恢复中的“结果未知”，结果文字要求模型根据操作语义决定是否重试：只读或幂等操作可考虑重试；可能有副作用时先检查外部状态，必要时询问用户，不盲目重复。幂等表示重复执行同一操作不会继续增加效果。

在追加变更记录的例子中，安全的下一步是先读文件，确认记录是否已经存在，再决定是否追加。这是给模型的恢复指导；该恢复模块本身没有自动重跑原工具，也没有对任意外部操作实施幂等检查。

当前进程内发生这类步骤异常时，默认调度器会等待已经派发的调用收束，循环补齐缺失结果，再关闭失败的 step 和 turn。后续再次调用模型时，使用已补齐的历史。重启恢复未完成的会话时，恢复入口读取已有记录，补入同类工具结果及未关闭的生命周期事件。

这同时维护工具请求与结果的配对，并把外部执行结果的不确定性留给后续模型。代价是额外的开始／结果跟踪与恢复处理。它不提供外部操作只执行一次的保证；尤其内存事件追加不等于持久化完成，日志状态分类不能替代外部事务或幂等机制。

可简化借鉴的原则是：区分没有开始证据、已有结果与结果未知；恢复时描述能够确认的事实，再选择后续操作。尚未核对 AI-Human 当前实现，不判断它是否需要新增这一机制。

## 6. 模型请求重试：保留步骤决定，重新生成请求

重试需要先确定重新执行的范围。假设任务是“修改配置，然后解释变更”：第一步已经执行文件修改并记录结果，第二步请求模型解释时失败。把整个任务入口重新执行，可能重复领取输入、运行准备逻辑，甚至重做已完成的操作。

DSH 在同一个 step 内重试模型请求，不由框架重放前一步工具。一个 step 可以包含多次实际模型请求；得到可接受的模型响应后，才继续处理该响应中的工具调用。

```text
同一个 turn
│
├─ step 1：模型要求修改文件 → 工具执行 → 结果已记录
│
└─ step 2：模型请求失败 → 再次请求失败 → 再次请求成功并解释
```

| 工作 | 模型请求重试时 |
| --- | --- |
| 领取本步输入 | 不重新领取 |
| 完整装配提示和工具 | 不重新装配 |
| 执行步骤前的钩子 | 不重新执行 |
| 把已接纳的原始输入写入历史 | 不重复追加 |
| 准备模型调用、解析请求参数 | 重新执行 |
| 刷新已注册的动态运行上下文 | 重新执行 |
| 从当前 Session 生成请求 | 重新执行 |

循环使用首次尝试标记控制原始输入接纳，避免重试时把同一条用户消息再次追加进历史。本步捕获的 provider、model 和显式 reasoning effort 选择继续用于重试；重新准备调用不等于允许恢复代码任意更换本步模型选择，后续已记录的新选择在下一步使用。

重试不保证请求内容完全相同。上下文超长的恢复处理可以先记录历史压缩，再要求重试；循环从当前 Session 重新生成请求，于是下一次使用压缩后的历史，同时保留本步原先的装配决定。请求参数重新解析与动态上下文刷新也必须通过相应记录保持可重建性。

这类失败请求的流结算为 `assistant/attempt`，保留诊断信息，不作为已完成的助手消息进入模型历史。它不把失败半截内容自动当成正式对话继续。用户主动取消响应流时采用另一种前缀结算规则，见第 7 节。

恢复插件与 provider 策略决定是否重试、等待多久和次数规则；循环收到重试决定后继续同一步内的请求循环。等待可取消，取消后不会因迟到的重试决定继续发送。本节限定为进入模型请求恢复扩展点的失败，不把任意插件异常、工具异常都解释成可以原地重试。

可简化借鉴的原则是：明确已接纳的输入、已完成操作与可重新执行工作。DSH 通过 turn、step、实际请求尝试的区分，避免把一次模型请求失败扩大成整轮任务重放；代价是需要维护步骤状态，并明确重试期间允许哪些请求变化。

## 7. 用户取消：保留已输出内容，等待执行收束

取消需要确定已输出内容怎样参与后续对话。假设模型正在回答“三步修改配置”，用户看到第一步和第二步开头后停止，随后要求“第一步不用，直接讲第二步”；如果整次回答从历史消失，后续模型就缺少理解这些指代的内容。

DSH 在正常响应流中途被取消时提取可保留的已收到内容，存在内容就写入 `assistant/message`，记录 `interrupted: true`，并保留该尝试的流记录。消息加入当前生效历史，后续请求可包含它；没有可保留内容时，只记录 `assistant/attempt`，不制造空助手回答。

```text
正常流式输出 → 收到取消信号
                    ↓
         提取可保留的文本／推理内容
                    ↓
     记录中断的助手消息，关闭本步与本轮
                    ↓
           后续请求包含这段内容
```

| 取消或失败发生的位置 | 对模型历史的处理 |
| --- | --- |
| 模型请求失败，进入恢复处理 | 保存失败尝试，半截内容不作为正式助手消息 |
| 用户在正常输出过程中停止 | 保留可用前缀，记录为中断的助手消息 |
| 已失败、正在等待重试时再停止 | 仍保留为失败尝试，不重新变成助手消息 |

这是对不同执行状态的明确选择：失败尝试准备被替换，主动停止则结束当前输出，并保留后续对话可能引用的已输出内容。代价是模型历史中可能存在不完整回答，记录与展示需要识别中断状态。

中断内容提取只保留非空白的文本和推理块，排除响应流中的工具调用。不能把半截参数作为可执行调用，也不在这条中断消息中保留尚未派发的调用。该结论限于流中途取消；整条助手消息已经提交后才取消时，已有调用按工具结果配对规则获得取消结果，不能删除已提交历史来冒充从未存在。

已经开始执行的工具采用协作式取消：向调用传递取消信号，并等待已开始的执行收束。`cancel()` 发出请求后返回，不表示所有工作已经结束；工具若不响应信号，框架仍可能需要等待它自行结束。已经产生的文件等副作用不会因取消而自动撤销。

当前进程可完成结算时，记录先明确保留了什么输出，再关闭运行单元。这不提供突然终止进程时所有流式前缀均已落盘的保证，仍须区分消息追加、持久化和执行结果。可简化借鉴的原则是：取消语义同时定义输出保留、后续调用停止和当前工作收束，不能仅以取消函数已返回判断运行已结束。

## 8. 工具批次：安全调用并发，独占调用形成屏障

模型一次响应可以提出多个工具调用。全部串行容易保持顺序，但独立 I/O 会互相等待；直接并发整批调用，又可能破坏读取、修改、检查之间的顺序。DSH 让明确声明可并行的调用进入有数量上限的并发池，让独占调用隔开前后两组。

假设模型依次提出五个参数已确定的调用，读取已被声明可并行、修改需独占，调度关系如下：

```text
读取 README ─┐
             ├─ 并行执行，两个都结束
读取旧配置 ──┘
                    ↓
              修改配置：独占
                    ↓ 修改结束
读取新配置 ──┐
             ├─ 并行执行
读取日志 ────┘
```

工具实现者通过 `isConcurrencySafe(args)` 根据本次参数声明是否允许并行。只有明确返回 `true` 才并行；未声明、返回其他值或判断抛错，都按独占处理。该元数据不进入模型工具 Schema，调度器也不自动分析任意工具代码以证明没有副作用冲突。

这个判断是工具定义中的普通回调，与真正执行操作的 `execute()` 一起保存。调度器在调用开始前先找到当前工具定义，把本次参数传给判断回调，再决定并行或独占；它不会为了判断并发先执行工具主体。

真实的 `read` 工具直接写 `isConcurrencySafe: () => true`。接口也允许按参数区分，例如一个假设的读写工具可写 `isConcurrencySafe: args => args.mode === 'read'`；这是接口用法示意，不是当前文件工具的实际合并设计。使用 `defineTool()` 时，包装代码先校验参数，参数非法就返回不可并行，不调用作者的判断函数；后续执行仍有自身的参数校验。

该回调要求是纯同步判断。接口传入本次调用参数，不传整批其他调用的路径列表，因此作者应在能够保证这一类调用可与并行组重叠时返回 `true`。框架不证明回调没有副作用，也不会纠正错误的安全声明；无法保证时省略回调或返回 `false` 即采用独占。

并发池按配置限制同时在执行的调用数量，调用结束后可补入后续可并行调用；遇到独占调用则等待前面的组收束。前置策略处理与结果后处理仍按模型调用顺序进行，执行阶段可以重叠。

实际完成顺序可以是 B、A，结果提交仍然是 A、B。较晚调用先完成时，结果暂存在对应位置，等待前面的调用完成后再按序写入 Session。这样历史和后续模型输入的排列不会仅因本次网络快慢变化；代价是前面的慢调用可能阻塞后面已完成结果的提交。

独占范围是当前 Agent 的这一批调用，不是跨 Agent 的全局资源锁。共享资源是否支持多 Agent 同时访问，仍需要相应的同步或隔离。可简化借鉴的原则是默认串行、显式允许并行，并分别定义执行重叠、屏障和结果提交顺序。

### 与已经学习的 Hermes 对照

用户已在 Hermes 学过同类模式：安全调用并行、需要顺序的调用形成屏障，完成先后可以变化，最终结果仍按模型原始调用顺序写回。这部分复用已有知识，不重复作为新机制讲解。

2026-11-04 核对当前本地 Hermes `main` / `4e7eb39947`：它的段规划器按原始顺序建立连续并行段和顺序段，后续调用不能跨越前面的屏障；并行执行器按原始索引保存和回收结果。

“有副作用就独占、无副作用就并行”适合作为初步理解，但不是 Hermes 当前的完整分类规则。Hermes 对文件工具比较读写目标：读与读路径重叠仍可并行，涉及写入的目标冲突会切开并行段，不重叠目标的写入也可能进入并行段；另有工具类别与 MCP 显式启用规则。

| 对照项 | DSH 当前批次调度层 | Hermes 当前段规划层 |
| --- | --- | --- |
| 共同思想 | 安全调用并发、独占屏障、按模型顺序提交 | 安全调用分段并发、顺序屏障、按模型顺序写回 |
| 并发判断的主要组织方式 | 工具提供本次参数的安全判断，通用调度器消费该结果 | 集中按工具类别、文件目标读写冲突与 MCP 启用规则规划 |
| 判断依据的表述 | 本次调用是否被声明可安全重叠 | 本次调用能否与当前并行段安全重叠 |

两者共有的保证是结果归位与屏障保序，不承诺并行段中的物理完成顺序。这一区分属于当前深度的关键对照；未核对两项目所有具体工具的全部并发约束，不据此声明整体工具安全性相同。

## 9. 输入路由与唤醒：followup、steer、inject

输入的内容、处理时机与是否唤醒 Agent 是分开的决定。DSH 把普通后续任务排到下一轮，把改向或背景补充排到后续步骤，并独立控制是否启动空闲的运行循环。

| 接口 | 意图 | 正在运行时 | 空闲时 |
| --- | --- | --- | --- |
| `followup()` | 普通后续任务 | 排到下一轮 turn | 唤醒运行 |
| `steer()` | 调整接下来的执行方向 | 在后续 step 接纳 | 唤醒运行 |
| `inject()` | 补充模型可见背景 | 在后续 step 接纳 | 只排队，等待其他操作唤醒 |

底层分别是 `send(input, 'next-turn', true)`、`send(input, 'next-step', true)` 和 `send(input, 'next-step', false)`。`steer` 在后续步骤边界生效，不修改已经准备好的当前请求，也不撤销已经执行的工具；本步模型请求重试期间的新输入仍等待后续 step。

### inject：先放入背景，不因此启动运行

用户对空闲状态下的理解是准确的：inject 类似于输入，但不唤醒；等下一次能够启动运行的输入到来，再让模型一起看到这条背景。

```text
Agent 当前空闲
    ↓
文件监控发现 config.json 被外部修改
    ↓
inject("config.json 已发生变化")
    ↓
信息排队，暂不调用模型
    ↓
用户后来输入：“继续检查配置”
    ↓
Agent 被唤醒，新请求一起包含：
  原有历史 + 文件变化的背景 + 用户这次的要求
```

该例是用途说明，不代表当前默认配置必然装有这样的文件监控插件。它说明后台组件可以先补充信息，而不用每来一条通知就发起模型请求。

两个边界需要同时保留：Agent 如果已经在运行，inject 可在后续 step 接纳并让当前轮继续，不必等下一次用户输入；唤醒来源也不限于用户，其他调用 `followup()` 或 `steer()` 的程序同样可以启动运行并接纳排队背景。

因此，inject 的准确含义是：“这条背景先放入待处理队列，下次运行到可以接纳新输入的位置时，让模型看到。”它不保证进入已领取输入的当前步骤，也不修改当前请求。

入队和模型历史接纳分别记录：`inject()` 会先留下队列变更事件；步骤开始前领取待处理消息，之后按正常准入路径写入模型历史。新 turn 的首次领取会先收取下一步背景，再收取一个下一轮任务。背景在工具执行期间到来时，仍等工具结果记录后再在后续步骤接纳，不插入未结束的工具调用与结果之间。

这项设计可借鉴的原则是，把补充上下文与发起运行分别表达，并明确输入进入哪个执行阶段。取消清空队列、保留队列以及取消后新输入的处理仍有专门规则，尚未作为本节已理解内容展开。

## 10. 研究与学习保留项
