## 1. 先区分四件事

Profile、Bundle、Preset 都涉及配置，但它们不是同一种东西，也不是三个各自实现业务逻辑的代码层。“用户能不能修改”不是区分标准。

| 名称 | 解决的问题 | 管理的内容 | 使用与复用的范围 |
| --- | --- | --- | --- |
| Plugin：插件 | 某项功能具体怎样工作？ | 实际功能代码，也可以注册工具、服务、提示、事件处理等 | 可以装在进程共享部分，也可以装在 preset 中 |
| Profile：应用运行配置 | 这次把 DSH 组成并启动成什么应用？ | 有序 Bundle 列表、外部插件安装信息、自定义配置覆盖等 | 启动整个应用，如 Web、headless、SDK |
| Bundle：插件组合的分发包 | 怎样把一批插件代码及其配置交给不同运行配置复用？ | 插件配置入口、所需代码与依赖；也能包含 preset 声明 | 被一个或多个 Profile 选用，一个 Profile 也可以组合多个 Bundle |
| Preset：Agent 能力组合 | 这类 Agent 采用什么提示、工具、技能和运行策略？ | 一份有名字的子插件配置列表 | 被运行中的 Agent 选择和复用；同一进程可以提供多个 Preset |

基本关系是：插件实现行为；Bundle 打包可复用的插件组合；Profile 选用 Bundle 并叠加修改来组成应用；应用中可以提供多个 Preset，再由 Agent 选择能力组合。

Preset 本身也通过一个声明插件注册到运行环境中。因此 Bundle 可以同时带有共享服务插件、界面插件和若干 Preset 定义。插件不只属于 Preset，Bundle 也不只是 Preset 的包装。

## 2. 用仓库里的真实组合看关系

以下是理解组成关系的简图，不是所有插件的完整清单，也不表示启动顺序由图中书写顺序决定。

```text
启动 Web Profile
    │
    ├─ base Bundle
    │    └─ 模型、会话、工具注册表、权限等基础运行插件
    │
    └─ web-app Bundle
         ├─ 网页相关插件与配置覆盖
         ├─ standard Preset 定义
         │    └─ 工具、提示、技能来源、压缩等子插件配置
         ├─ ptc Preset 定义
         │    └─ 类似的底层能力，加上程序编排执行器等差异
         └─ minimal、cordis 等其他 Preset 定义

应用启动后
    ├─ Agent A 选择 standard
    ├─ Agent B 选择 standard
    └─ Agent C 选择 ptc
```

这里的 base 与 web-app 不只是简单相加。Web 配置会停用 base 中若干全局工具、提示与策略插件，再由 Preset 提供这些贡献；工具注册表、会话、循环等共享运行服务继续保留。最终组成必须看所有配置层叠加后的结果。

另一种真实组合：headless Profile 使用 base Bundle 加 headless Bundle，后者提供单任务输入、等待、输出和退出行为。默认 headless runner 没有组成 preset roster，即没有提供那套可选 Preset 列表；它使用该运行配置已装好的能力。因此不能假设所有 Profile 都必须让每个 Agent 选择 Preset。

`sdk-minimal` 又是一个例外：它使用自足的 Bundle，不叠加 base。base 是多个官方 Profile 共用的选择，不是启动 DSH 的强制前置。

## 3. Profile 管什么，边界在哪里

Profile 可以理解成“这次运行整个 DSH 应用的配方”。选择 Web、headless 或 SDK，既选择了运行入口，也选择了该应用要装入的插件组合。

一份 Profile 保存选用哪些 Bundle、它们的顺序，以及自己的覆盖配置。它还可以管理安装进来的外部插件。Profile 是可以定制的命名配置，不局限于仓库附带的几种模板。

### 3.1 它能改变 Agent 行为吗？

能。Profile 虽然面向整个应用，但它的配置覆盖可以修改共享插件，也可以修改某个 Preset 声明及其子插件配置。因此“改提示词只能改 Preset、Profile 不能影响提示词”是错误理解。

职责的区别在于修改目的：定义或调整某类 Agent 的组合，主要看 Preset；定义整个应用安装、启动和覆盖什么，主要看 Profile。它们不是互不接触的配置权限层。

### 3.2 Patch 是什么？

Patch 是一组配置修改指令，例如新增插件行、按标识修改一行、停用一行。它不是新增的一种 Agent，也不是业务逻辑代码；Bundle 与用户配置都可以使用 Patch 表达修改。

普通配置层的应用顺序由低到高为：

1. Profile 列出的各 Bundle，按列表顺序应用。
2. 该 Profile 自己的覆盖配置。
3. Harness home 中影响多个 Profile 的用户覆盖配置。
4. 本次命令行指定的额外覆盖配置。

后面的配置可以覆盖前面的选择。当前启动代码还会在最后应用遥测禁用开关的专用配置；它不改变上述四类普通配置层的职责。

这里的覆盖不是任意深度合并：对一个插件行写新的 `config` 时，替换的是该行整份配置。省略字段之后采用什么值，由插件自己的配置定义决定。专门针对 Preset 内部的 Patch 可以修改其子列表；如果直接用整份 `plugins` 列表覆盖 Preset，则不能期待自动合并内置列表以后新增的内容。具体 Patch 语法仍留待专门阅读。

Profile 也不是一份运行中的 Session，不负责替每个 Agent 保存对话历史；启动和配置刷新后怎样重新装入资源，由运行框架及相关插件执行。

## 4. Bundle 管什么，边界在哪里

Bundle 把 Cordis 插件配置及其引用的功能代码组织成可分发、可复用的包。配置可以新增插件、修改已有插件配置、停用插件，也可以注册 Preset 定义。

一个 Bundle 可以包含：

- 进程共享服务，例如模型适配、会话和工具注册表。
- 应用入口和界面相关插件。
- 一个或多个 Preset 声明，以及相应的子插件配置。
- 对其他 Bundle 已插入插件的配置覆盖。

所以不能把 Bundle 等同于“单个 Agent 的工具包”，也不能理解成“只能打包一个 Preset”。它的直接使用者是 Profile 的应用装配过程；创建每个 Agent 时，不会重新加载一次该应用的全部 Bundle。

### 4.1 新能力一定要先做成新 Bundle 吗？

不一定。先区分“实现能力”和“选择能力”：实现一个新行为，需要相应插件代码；把它加入现有运行环境，可以修改部署配置或某个 Preset 的插件列表。要把这套组合交给其他运行配置或用户反复安装使用时，Bundle 才提供相应的分发与复用方式。

这不取消正常的安装与模块解析要求：配置引用的插件代码必须在该运行环境中可用，依赖和声明也必须满足加载规则。

### 4.2 Bundle 自己会执行压缩吗？

不会仅凭“它是 Bundle”就获得压缩算法。算法写在压缩插件中，Bundle 的作用是选择装入哪个插件以及给它什么参数。如果某个分发包同时提供功能代码与 Bundle 配置，这仍是代码实现和配置装配两个职责。

## 5. Preset 管什么，边界在哪里

Preset 是一份有名字的 Agent 子插件组合。它可以组织模型可见内容，也可以组织影响运行行为的后端策略。

| 可由 Preset 组织的内容 | 对 Agent 的影响 |
| --- | --- |
| persona、指令读取与动态上下文插件 | 提示内容与上下文来源 |
| 文件、Shell、网络、委派等工具插件 | 当前 Agent 可用的工具能力 |
| 技能发现与加载插件 | 从哪里发现技能、怎样提供给当前 Agent |
| 压缩、计划模式等策略插件 | 历史保留、工作方式与相应运行控制 |
| 工具执行器及其依赖 | 原生工具调用，或让模型通过程序编排底层工具 |

因此“Preset 只是模型看得到的提示词和工具列表”不完整。实际提供哪些内容，取决于它装了哪些插件。技能来源的配置也不等同于把所有技能正文一次性塞进提示，加载机制需要在技能组件单独确认。

### 5.1 插件只能放在 Preset 中吗？

不是。共享服务和部署贡献可以在进程级装载；某类 Agent 专用的提示、工具或策略可以放在 Preset 中。具体放置还取决于谁需要访问该服务、插件是否支持按范围注册，以及是否需要独立服务实例。

Web 的工具注册表就是共享服务，而不同 Preset 可以向它贡献不同工具。共享注册表不等于所有 Agent 看到同一份工具清单。

### 5.2 选择 Preset 会生成一套完全独立的 DSH 吗？

不会。它为 Agent 绑定能力组合，不自动生成独立进程、独立文件系统或独立沙箱。

需要区分：贡献范围决定某个 Agent 能找到哪些工具、提示和技能；服务实例隔离决定某组插件使用哪个服务对象；操作系统沙箱限制文件、进程等实际访问。不能用“Preset 隔离”概括这三件事。

如果 Preset 内提供自己的服务，该服务提供者和消费者需要正确组成同一隔离分组。仅仅把插件放进 Preset，不会让它发布的每个服务自动成为 Agent 私有服务；当前装配代码会检查泄漏到全局的服务并拒绝错误组合。

## 6. “我想改某项行为”应该改哪里

| 具体需求 | 直接修改的对象 | 是否必须新增 Bundle |
| --- | --- | --- |
| 同一应用中提供不同提示、工具或技能来源的 Agent | 新建或修改 Preset，并确保相关插件代码可用 | 不必须；需要分发时可以把定义打包 |
| 调整压缩阈值、保留量等已有选项 | 修改实际装载的压缩插件配置；Web 的对应选择可在 Preset 内 | 不必须 |
| 换成新的压缩算法 | 编写或修改压缩插件，再替换相应配置中的实现选择；保留使用者依赖的操作与行为保证 | 不必须；Bundle 可以携带其代码依赖与装配配置 |
| 改成另一种应用入口，或调整整个应用的共享插件 | 新建或修改 Profile，选择 Bundle 和配置覆盖 | 可复用已有 Bundle，也可以制作新的组合包 |
| 把一套共享插件及多个 Preset 交给其他运行环境复用 | 制作 Bundle，由目标 Profile 选用 | 这是 Bundle 直接解决的需求 |

压缩示例的完整分工：你实现新的压缩插件；某个 Preset 配置使用它；一个 Bundle 可以同时携带该插件的可用代码和这个 Preset 定义；Profile 选用相应 Bundle 来启动应用；新 Agent 选择该 Preset 后使用对应组合。

上面是一条可采用的分发路径，不是每次修改都必须依次新建插件、Preset、Bundle、Profile 四种对象。

## 7. 复用与修改的生效范围

### 7.1 新 Agent 直接复用什么？

在提供 Preset 的应用中，新 Agent 直接选择 Preset。当前实现会为一份 Preset 修订装载插件子树，使用该修订的多个 Agent 可以共享这份已装载组合；不是每创建一个 Agent 就重新启动应用、重新加载全部 Bundle。

修订指某次 Preset 配置对应的一份运行版本。Agent 各自保留 Session、输入队列和运行控制状态。插件共享也不意味着会话数据可以混用，插件仍须按 Agent 或 Session 正确管理各自的数据。

### 7.2 修改 Preset 后，已有 Agent 会立即变化吗？

当前进程中，修改或移除声明会让旧修订进入等待回收状态。已有 Agent 等使用者保留对旧组合的引用；后续新的绑定使用当前可用修订；旧修订没有使用者后才释放。

这是 Preset 修订管理提供的保证，不是所有共享插件配置变化的统一承诺。Profile、共享服务或具体插件自身刷新时怎样影响已有 Agent，需要按对应生命周期和更新路径确认。

### 7.3 能否在对话中随便换 Preset？

当前公开的 Preset 选择操作只允许在 Session 首个 turn 开始之前进行；会话已经开始后会拒绝该选择。turn 在这里指循环记录的一次运行单元；即使后来已经空闲，也不等同于会话从未开始。

因此“修改 Preset 定义”“修改新 Agent 的默认 Preset”“让已开始的会话改用其他 Preset”是不同操作，不能互相替代。

### 7.4 重启以后会恢复旧插件版本吗？

Session 记录所选 Preset 的身份。进程重启后恢复会话，使用该身份对应的当前定义；旧修订的运行实现不会自动跨进程保留。缺失定义会导致恢复组合失败，而不是静默换成别的 Preset。

所以“当前进程中已有 Agent 保留旧组合”不等于“持久化了旧版插件代码”。完整恢复、迁移及选择流程仍需在生命周期组件展开。

## 8. 快速检查容易混淆的说法

| 容易混淆的说法 | 应怎样理解 |
| --- | --- |
| Profile 就是一个启动命令 | 它是有名字的应用组合，既确定运行入口，也确定装入的 Bundle、插件与覆盖配置 |
| Bundle 就是打包一个 Preset | 它能打包共享插件、应用配置及多个 Preset，也可以完全不提供 Preset |
| 插件属于 Preset 这一层 | 插件是功能单元；它可以在共享部分装载，也可以由 Preset 装载 |
| Preset 只控制模型看到什么 | 它还可以选择影响运行行为的策略和执行方式；但不自动形成安全隔离 |
| 要改变压缩逻辑，必须修改 Bundle | 改算法的是插件代码；配置选择实现和参数；Bundle 负责可复用的分发与装配 |
