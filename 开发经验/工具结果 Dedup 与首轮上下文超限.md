# 工具结果 Dedup 与首轮上下文超限

> **重复的工具结果会占掉后续执行所需的上下文。一轮任务能不能完成，也取决于这些重复内容有没有被及时识别和折叠。**

这次是第一次切身感受到 dedup 的作用如此重要：一个写作会话在第一轮内就因上下文过长失败。自动压缩已经开启，但重复读取和整篇编辑参数都发生在活动轮次中，历史摘要无法为它腾出空间。

案例依据是 `ai-human-bug` 对 31 服务器的排查记录。以下运行时数据和策略覆盖情况对应当时的部署；写作去重规则属于后续设计建议。

## 首轮上下文是怎样被撑满的

当时模型总容量为 32,768 tokens，扣除输出预留 4,096 和安全余量 1,024，实际输入硬预算是：

```text
32,768 - 4,096 - 1,024 = 27,648 tokens
```

排查记录中的完整候选请求大小如下。这里统计的是各阶段准备送给模型的输入，包含固定提示词、工具定义、历史和调用记录等，并非某一份工具结果本身的大小。

| 执行阶段 | 候选输入 tokens | 距离输入硬预算 |
| --- | ---: | ---: |
| 获取文档索引后 | 7,203 | 剩余 20,445 |
| 第一次 `doc_read` 后 | 16,668 | 剩余 10,980 |
| 第二次 `doc_read` 后 | 24,879 | 剩余 2,769 |
| 生成整篇 `doc_edit` 提案后 | 29,314 | 超出 1,666 |

两次 `doc_read` 指定了不同的 chunk，但都传了 `block_count=5, direction=around`。在这份文档上，两次实际返回了完全相同的两块，合计 108 个文档块。调用参数不同，并没有带来新的读取内容。

第二次读取后，候选输入已经达到 24,879 tokens，距离当时 24,883 tokens 的压力收尾线只有 4 tokens，仍允许继续调用工具。随后模型生成整篇编辑提案，工具参数带入了 6,463 字符的新正文，下一次候选请求增长到 29,314 tokens，被硬检查拦住。

提案生成成功与整个 run 成功需要分别判断。此次提案已经生成，但后续模型请求失败，数据库最终记录为 `FAILED / CONTEXT_TOO_LARGE`；也不能据“提案生成成功”推断正文已经应用。

第二轮又因读取内容累积而提前收尾，最终只返回说明，没有生成新的编辑提案。

## 自动压缩为什么没有救下这一轮

当时的压缩机制处理的是**已经完成的历史轮次**。本次重复读取、长编辑调用都位于活动中的首轮，没有可通过历史摘要回收的旧轮次。

这说明“自动压缩已开启”仍需结合它能处理的范围理解：

| 机制 | 主要处理什么 | 本次遇到的边界 |
| --- | --- | --- |
| 历史摘要 | 已完成轮次的历史内容 | 无法处理活动首轮内的膨胀 |
| 压力收尾与回包省略 | 临近预算时减少后续增长并结束执行 | 省略工具结果不能消除已有的长调用参数 |
| 输入硬检查 | 检查下一次完整请求是否能送模 | 能拦住超限请求，但任务仍然失败 |

超限后，运行时省略了编辑结果；排查中的离线复算显示，这只节省约 86 tokens。大段新正文已经存在于 assistant 的工具调用参数中，缩短 tool 回执能回收的空间很有限。

因此，上下文管理需要同时看**工具返回了多少内容、模型生成了多长的调用参数，以及下一步还能否继续执行**。只控制回包大小，会漏掉长编辑调用这类增长来源。

## 已有 Dedup 为什么没有生效

当时的 dedup 采用“公共入口＋每个工具注册自己的策略”。公共入口负责调度，具体哪些内容可以合并，由工具策略决定。

| 工具 | 当时是否注册了结果去重策略 |
| --- | --- |
| `rag_atom_search` | 是 |
| `doc_read` | 否 |
| `doc_get_index` | 否 |
| `doc_edit` | 否 |

`doc_read` 会经过公共入口，但没有对应策略，因此直接返回原结果。排查时用该会话两次真实回包调用正式 dedup 函数复核：两份结果的 `items` 完全相同，第二份去重前后仍是 14,266 字符。

这是一次明确的**策略覆盖缺口**。判断某个业务有没有获得 dedup 能力，需要检查具体工具的登记情况，并用真实回包验证最终模型表示。

当时 9 月 17 日的方案明确限定第一版仅登记 `rag_atom_search`，验收也写了“未做其他工具 dedup”。方案中的“Chat/Writing 共用”，指两个场景调用 RAG 时共用去重机制。记录没有说明专门排除 `doc_read` 的理由，只能确认第一版的范围限定。

## 这次对 Dedup 的认识发生了什么变化

以前容易把 dedup 理解为重复检索后的 token 优化。这次能看到它与任务可用性的直接关系：重复内容持续占用空间，后面的编辑、校验和最终回复就可能无法完成。

更值得注意的是，这种问题可以发生在第一轮。即使没有冗长历史，同一轮中几次重叠读取，也可能把一个原本可执行的任务推到预算边缘。**去重覆盖应当成为上下文管理设计和验收的一部分。**

去重也不能只比较调用参数。两个不同的 chunk 参数，可能因邻域读取返回同一批内容；反过来，相同参数在文档更新后，也可能返回新内容。是否重复，需要结合实际结果、资源身份和版本判断。

本案例还暴露了表示开销：每份读取回包约 14,266 字符，正文合计只有约 2,453 字符，其余大部分是 ref 和结构信息。因此，正文折叠之后仍需检查整个回包的表示，不能把“正文去重”直接算成“整包省掉”。

第二次读取前后的候选请求差值也不能直接当作 dedup 收益。实际能节省多少，需要计入调用记录、必要定位信息、引用说明和序列化开销，并使用对应 tokenizer 重新计算完整请求。

## 写作读取可以怎样接入

第一步适合给 `doc_read` 增加**同轮精确去重**，复用现有扩展入口，由 Writing 能力提供文档语义相关的策略。

### 用文档身份和版本界定重复

折叠条件应保守：同一轮、同一文档、同一版本、同一块，并且正文完全一致。相同文字出现在不同位置，不能自动合并成同一块；文档版本或正文发生变化，也应完整返回。

如果暂时没有可靠的版本或块身份依据，就保留原结果。不能为了减少 token，猜测两段内容等价。

### 第一份完整保留 后续只折叠重复部分

例如第一次读取返回 A、B，第二次返回 B、C，可以保留第一次的完整 A、B，第二次保留完整 C，并用简短说明指向此前的 B。整个第二次调用不能因为部分重叠就被当成空结果。

读取成功、覆盖范围以及仍需用于编辑的定位 ref 等信息，应保持清楚。重复正文可以引用已有内容，新的有效定位信息不能随之被丢弃。

### 读取仍然执行 去重作用于模型副本

工具仍实际读取文档，获取当前版本和结果，再决定模型需要接收哪些重复内容。这样才能发现文档更新；只按“以前读过”跳过执行，会把旧内容误当作当前事实。

原始回执与模型副本分别维护，调用与返回仍保持配对。模型看到的短回执应明确表示“此次读取成功，重复内容已在此前提供”，避免被误解为空文档或读取失败。

### 引用目标必须仍在模型可用范围内

如果后续回执引用了前一次完整正文，压缩或 GC 就必须一起处理这组关系。数据库里还保存着原文，不代表模型此时仍能读取它。

当引用目标已离开当前上下文时，需要重新提供正文，或提供实际可用的恢复入口。不能留下一个模型无法解析的引用，更不能因为去重台账还记着“读过”，就持续省略已经不可见的内容。

## Dedup 与其他上下文措施怎样配合

这次案例把几种机制的职责区分得更清楚：

| 措施 | 主要减少什么 | 关键边界 |
| --- | --- | --- |
| 单份回包的结构压缩 | 重复字段、等价包装、重复长值 | 保留约定的事实、身份和定位信息 |
| 跨调用结果 dedup | 多次读取返回的相同内容 | 先前完整内容必须仍可用 |
| 历史工具清理 | 较旧、允许回收的工具正文 | 保护近期依赖并考虑恢复成本 |
| 语义摘要 | 适合交接的历史对话与任务状态 | 存在信息损失，受压缩范围约束 |
| 完整请求预算检查 | 防止请求越过输入硬预算 | 还需规划超限前的处理和收尾 |

对于这次故障，优先给 `doc_read` 补上去重覆盖有明确依据；但长 `doc_edit` 参数仍需单独治理。只要整篇新正文继续进入调用历史，就需要在允许调用前考虑后续请求和收尾空间，不能只检查当前是否刚好低于压力线。

后续验收可以围绕这个真实样本和几个边界展开：

- 完全重复读取和部分重叠读取，是否只折叠重复部分。
- 版本变化、同文异位、必要 ref 变化，是否仍保留有效新信息。
- 压缩或 GC 移走原文后，是否会出现不可用引用或持续误去重。
- 原始回执、读取状态和调用配对是否保持正确。
- 使用实际 tokenizer 复算后，完整请求净节省多少，以及长编辑之后能否继续完成任务。

这些是后续设计与验证方向，不能把接入策略本身当作已解决本次全部超限问题的证明。
