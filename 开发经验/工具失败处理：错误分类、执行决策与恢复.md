# 工具失败处理：错误分类、执行决策与恢复

## 1. 核心认识：失败后的执行决策

工具失败处理是一套**失败后的执行决策机制**。重试只是其中一种动作，其他动作包括修正参数、等待、查询状态、继续处理已完成部分、更换方案、停止或请求人工介入。

Agent Runtime 的核心问题是：**工具执行出现异常或结果不完整后，如何根据错误原因、执行状态和操作性质，决定下一步，并把足够的信息交给 Agent？**

这里有三条相互配合的原则：

1. **可由规则明确判断的故障，用程序确定性处理。** 例如按约定处理短暂连接故障、限制请求次数。
2. **需要理解任务语义的恢复，由 Agent 决策。** 例如文件不存在后搜索其他路径，或根据业务需求选择其他工具。
3. **涉及权限、成本和副作用的边界，由 Runtime 强制约束。** 例如额度耗尽后阻止继续出网，对结果未知的写操作禁止无条件重做。

错误信息不仅用于解释失败，也是后续决策的输入。但模型可见的建议不能代替程序约束：提示 Agent 不要重试，不等于 Runtime 已经阻止了重试。

## 2. 错误原因不等于恢复决策

不能仅凭一个错误码或 `retryable: true/false` 判断下一步。至少要结合以下维度：

| 维度 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 错误原因 | 为什么没得到预期结果？ | 参数错误、网络中断、限流、权限不足、内部异常 |
| 执行状态 | 操作实际上进行到哪里？ | 未执行、已成功、确定失败、部分成功、结果未知 |
| 操作性质 | 重复执行有什么后果？ | 只读、具有可靠幂等保障的写入、非幂等写入 |
| 恢复条件 | 什么变化后可以继续？ | 参数修正、等待时间到期、授权完成、查到目标状态 |

这些事实共同决定动作：原样重试、修改后重试、等待、查证、从部分进度恢复、终止或交给人处理。

例如同样是 `TIMEOUT`：

- 只读数据库查询超时：若成本和超时预算允许，可以有界重试；也要注意两次查询可能看到不同数据快照。
- 创建工单超时：请求可能已经生效，应先按操作标识查询，或依赖目标端明确支持的幂等机制。
- 模型调用超时：即使没有拿到结果，也可能已消耗额度；重试前需要考虑成本和调用预算。
- 用户已经取消：应遵守取消语义，不因为底层表现为超时就自动恢复。

**执行状态要基于证据记录。** 连接前明确失败可以认定请求未发出；请求发出后响应丢失通常只能认定结果未知。收到错误响应也不自动证明所有副作用都未发生，取决于目标服务的契约。无法确认时保留 `UNKNOWN`，不要为了方便决策猜成失败。

### 常见原因与可能动作

| 原因 | 常见处理思路 | 需要确认的边界 |
| --- | --- | --- |
| 参数错误 | 返回具体字段与约束，让 Agent 修正 | 原样重复通常无意义；修正后是否属于新的语义尝试 |
| 认证或权限不足 | 停止无条件重试，修复凭证或请求授权 | 凭证刷新或权限变化后是否允许重新尝试 |
| 限流、短暂不可用 | 在安全且预算允许时等待并有界重试 | 等待条件、服务指引、实际副作用和总预算 |
| 配额耗尽 | 阻断受影响范围内的继续调用，并说明可用的替代方案 | 配额属于哪个服务、账号或租户，何时可恢复 |
| 状态或版本冲突 | 重新读取状态，再决定是否重新规划 | 不可用过期依据强行覆盖新状态 |
| 部分成功 | 记录每项结果，恢复未完成部分或补偿 | 哪些副作用已经发生，是否支持单项恢复 |
| 内部程序缺陷 | 保留诊断信息并终止或升级处理 | 不应把不确定异常一律当成临时故障 |
| 取消 | 停止继续调度并确认执行终态 | 正在执行的外部操作可能未被取消，仍需查证副作用 |

这张表是决策方向，不是仅凭错误分类即可套用的自动重试规则。操作的实际语义、执行状态和目标系统能力仍然是前提。

## 3. 两层失败处理与重试责任

一次工具调用可能经过多层：

```text
主 Agent → Runtime → Tool → SDK → 外部服务
```

### 工具内部：处理底层故障并保留事实

Tool 和 SDK 能观察到网络、协议和目标服务的细节，适合处理工具契约允许的短暂故障。例如对安全的只读请求做有限次数的连接重试。内部重试成功时可以正常返回结果；耗尽后应保留实际原因、尝试次数、执行状态以及恢复所需信息。

工具不能只返回“失败，请重试”，也不能把内部异常吞掉并伪装成空结果。对于多步骤工具，返回的信息还应表明哪些步骤已经完成，哪些未完成。

### 主 Agent：理解失败并做语义决策

Agent 看到最终工具回执后，根据任务上下文决定如何继续。例如：

- 参数错误：修正指定字段后重新调用。
- 文件不存在：搜索其他路径，或向用户说明无法找到。
- 工具不支持某种操作：判断能否选择其他合适的工具。
- 部分结果：结合用户需求决定是否继续获取剩余内容，不能把部分结果说成完整答案。

Agent 的决策应以回执中的事实为基础；不能因为“有重试能力”就忽略结果未知、副作用或明确的禁止条件。

### Runtime：统一限制并执行强制边界

Runtime 管理本次运行的调用、时间和成本预算，执行权限、取消、失败循环和副作用等限制。合理的分工是：底层负责有限的短暂故障恢复，Agent 负责语义调整，Runtime 负责全局约束。具体由哪一层发起重试，应按工具和 SDK 能力明确约定，而不是每层都默认重试。

如果 SDK、Tool、Runtime、Agent 各自最多调用下一层 3 次，最坏可能产生 `3 × 3 × 3 × 3 = 81` 次底层请求。这里的 3 指**每层总尝试次数**；如果指“初次请求加重试 3 次”，次数还会更多。

设计时需要：

- 明确各层的重试权、适用错误和总尝试上限，避免重复配置。
- 使用同一逻辑操作 ID 串联多次尝试；每次实际尝试有独立 ID。
- 尽可能把 SDK 和工具内部的实际出网次数、等待时间和消耗汇总到 Runtime。若底层不可观测，应明确标记统计不完整，不能假装只发生了一次请求。
- 同时限制次数、总时间和成本；退避与随机抖动用于减少集中重试，服务明确给出等待时间时应按契约处理。
- 用户取消或总预算耗尽后，不再调度新的自动尝试。已经发出的请求仍可能完成，结果要按实际状态处理。

## 4. 失败、空结果和不完整结果

返回结果不仅要描述工具是否正常结束，还要描述**业务结果是否完整**。建议分别表达执行状态和结果完整性，不要把两者压成一个布尔值。

| 情况 | 正确理解 | 后续处理 |
| --- | --- | --- |
| SQL 查询成功，返回 0 行 | 成功的空结果 | 如实报告；是否调整条件取决于用户需求或明确的任务语义，不能擅自放宽后冒充原查询结果 |
| 查询成功，但只返回前 100 条 | 成功取得一部分数据 | 标明截断、分页信息和是否还有后续；需要全部数据时继续分页或说明限制 |
| 搜索服务仅返回部分结果 | 可用但不完整，或按工具契约视为部分失败 | 明确缺失范围和降级情况，避免声称已经搜索完整 |
| 批量 10 项中 7 项成功 | 部分成功 | 按项目记录结果；根据幂等性和失败原因处理剩余项，不应整批盲目重做 |
| 查询失败 | 未获得可靠结果 | 保留失败原因，不能伪装成“没有数据” |

空结果本身也可能触发下一步探索，但探索是新的语义决策，不是把原查询条件悄悄改掉。

## 5. 防止 Agent 进入失败循环

传统重试可能是固定代码循环；Agent 还可能在每次看到错误后重新规划，换一个搜索词或工具参数，表面上调用不同，实际仍在撞同一个不可恢复条件。

例如搜索服务的本轮配额已经耗尽，模型连续更换关键词仍然调用同一服务。仅靠提示词说“不要再调用”不够，Runtime 应识别明确的阻断条件：

- **服务级条件：** 对已确认额度耗尽的服务，在适用范围和有效期内阻止继续出网，向 Agent 返回可识别的阻断回执。
- **参数级条件：** 对同一参数校验错误，要求相关参数或前提发生有意义的变化；仅修改无关字段不能无限绕过限制。
- **进展级条件：** 跟踪连续相同或等价的失败，以及是否出现新的恢复条件；达到阈值后停止自动循环或要求重新规划。
- **全局预算：** 限制工具调用总次数、底层请求、时间和成本，覆盖 Agent 重新调用与底层重试。

这些限制需要有**范围和解除条件**。例如本轮配额耗尽可以阻断本轮同一服务，但配额恢复、凭证变化或用户明确开启新任务后，应重新评估；相同参数在数据已变化或等待条件已满足时，也可能是合理的新查询。不能简单永久封禁相同参数。

## 6. 持久化恢复：执行事实与 Agent 消费分开

工具执行期间和结果交付期间都可能崩溃，至少区分：

1. **尚未执行：** 有可靠证据表明请求未发出，可按规则重新调度。
2. **可能已执行，但完成结果未可靠记录：** 调用方不能推断成功或失败，应按结果未知处理。
3. **结果已可靠记录，但 Agent 尚未消费：** 恢复时优先交付已记录结果，不应因为 Agent 没看到就重新执行。

典型窗口：外部工单已创建成功，Runtime 在保存成功回执之前崩溃。重启后本地没有成功记录，但外部副作用已经发生。仅有本地检查点无法消除这个窗口。

对有副作用的工具，恢复需要结合稳定的逻辑操作 ID、目标端持久化幂等键、外部状态查询、进度记录和必要时的人工核对。幂等键只有在目标端确实支持并按约定保存时才有效；如果无法查证且没有可靠去重，就应保留结果未知并升级处理，而不是假装可以安全自动重试。

部分成功也要记录每个子操作的身份和结果，恢复时只处理有依据的剩余工作。取消同样需要区分“停止继续调度”和“外部操作已经停止”：前者不能证明后者。

## 7. 结构化回执：事实、建议与强制限制

不要让 Agent 仅凭自然语言猜测下一步。工具或 Runtime 可以提供结构化回执，再按消费者需要投影给 Agent、用户和诊断系统。以下只是一个**示意协议**，字段和枚举应按实际工具契约定义：

```json
{
  "code": "QUOTA_EXHAUSTED",
  "message": "搜索服务的本轮额度已耗尽。",
  "execution_state": "NOT_EXECUTED",
  "next_action": "STOP_FOR_RUN",
  "retry_after": null,
  "attempts": 2,
  "operation_id": "op_example"
}
```

此例假设有证据确认**当前被阻断的逻辑操作**未执行；`attempts: 2` 指本轮此前为判断服务可用性而发生的两次底层请求，计数范围需要在真实协议中明确。若当前请求已发出且执行情况不明，应使用 `UNKNOWN`，不能因为额度错误就固定填写 `NOT_EXECUTED`。

| 字段 | 职责 |
| --- | --- |
| `code` | 稳定识别错误类别，供程序和 Agent 区分；不单独决定是否重试 |
| `message` | 解释发生了什么，以及必要的具体上下文 |
| `execution_state` | 根据证据描述实际状态，例如未执行、部分成功、结果未知 |
| `next_action` | 表达建议的恢复动作，或说明 Runtime 已实施的限制 |
| `retry_after` | 存在可靠等待条件时提供；没有信息时为空，不代表可以立即重试 |
| `attempts` | 标明统计范围内的实际尝试次数，并注明是否完整 |
| `operation_id` | 串联同一逻辑操作的回执、诊断与恢复；不等于目标端已支持幂等 |

对于部分成功和不完整结果，还需要按需提供子项结果、完整性标记、分页指针或已完成范围。对于参数错误，应指出字段、约束及可修正信息。

**动作有两类：** `修改参数后重新尝试` 等是给 Agent 的建议；`本轮禁止调用该服务` 等是 Runtime 必须执行的强制规则。即使两者都在回执中表达，也不能把建议字段当作安全边界。

诊断日志可以关联原始异常、堆栈、调用链和更详细的尝试记录；模型视图只提供其决策所需、经过处理的信息，不直接暴露凭证或敏感数据。稳定错误码与可读描述应相互配合，不能只保留一个通用 `ERROR`。

## 8. 用故障注入验证行为

实现后不能只检查报错文案，还要观察请求、状态、副作用和 Agent 后续行为。至少覆盖：

| 注入场景 | 需要验证 |
| --- | --- |
| 连接前失败或超时 | 确认未发出时才标为未执行；重试次数和总预算符合约定 |
| 外部执行后响应丢失 | 结果标为未知；通过查询或幂等机制恢复，不产生重复副作用 |
| 429 限流 | 依据服务契约等待；底层实际请求次数受到限制 |
| 配额耗尽 | Runtime 在正确范围内阻止重复出网；恢复条件明确 |
| 参数错误 | 返回具体字段；原样或只改无关参数不能无限循环 |
| 批量部分成功 | 成功项不被误报为失败；只对允许恢复的项目采取动作 |
| 用户取消 | 不再调度新尝试；对已发出操作核对终态，不把超时当作恢复许可 |
| 结果已持久化、Agent 尚未消费时崩溃 | 恢复后交付已记录回执，不重复执行工具 |
| 空结果与截断 | 空结果保持成功语义；截断和缺失范围对 Agent 可见 |

观测至少能关联逻辑操作 ID、尝试 ID、错误类别、执行状态、恢复动作、调用层级、实际请求次数、耗时和最终结果；对不可观测的底层尝试标识统计缺口。对于有副作用的场景，还要核对目标系统中实际发生了什么，而不是只检查本地日志。

最终要验证的是：**系统有没有根据可信事实采取正确的下一步，而不是仅仅“抛出了一个错误”。**
