# 知识图谱建模经验：确定节点、关系与属性的边界

> 图谱建模的核心不是把所有名词变成节点、动词变成边，而是围绕实际任务，决定哪些对象需要独立存在，它们如何关联，以及哪些规则必须被保留。

## 1. 从任务出发，而不是从节点数量出发

同一份业务知识可以有多种图结构。选择哪一种，要先看系统需要回答什么问题、哪些信息要独立维护，以及后续如何查询和更新。

图谱节点更多、关系更丰富，并不自动意味着模型更好。结构过细会增加维护和查询成本；结构过粗则可能把关键关系、时间或条件藏进一段难以操作的文字中。

建模时可以先写下几个具体问题，例如：

- 某台装备发生过哪些故障？
- 一次维修由哪些人员参与，消耗了哪些备件？
- 故障与工单之间的关联是否有条件或多条路径？

再根据这些问题决定需要保留什么。下文的装备维保只是教学示例，实际结构应以具体业务和数据为准。

## 2. 四类需要考虑的内容

| 内容 | 回答的问题 | 示例 |
| --- | --- | --- |
| 节点（Node） | 哪些对象值得独立表示？ | 装备、故障事件、维修工单 |
| 关系（Edge） | 这些对象之间有什么联系？ | 装备发生故障、故障产生工单 |
| 属性（Property） | 节点或关系有什么特征？ | 装备编号、故障时间、维修开始时间 |
| 约束（Constraint） | 哪些规则应当成立？ | 编号唯一、关系两端的类型、状态的合法取值 |

节点、关系和属性是属性图模型的基本表达方式。约束可以在业务模型中定义，再由数据库、应用程序或校验流程中的一部分来执行；具体能否自动执行，取决于所用技术和实现，写在描述里本身并不等于已生效。

## 3. 先确定抽象边界：关系还是独立节点？

假设业务描述是：“装备发生故障，故障产生维修工单，维修人员处理工单。”可以先抽象为：

```text
装备 ──发生──→ 故障事件 ──产生──→ 维修工单 ←──处理── 维修人员
```

这是业务概念示意，不代表数据库一定按这些节点和边存储，也不表示每条关系都一定是直接关联。

接下来，如果要记录维修开始时间、结束时间和结果，可以将它们放在人员与工单的维修关系上：

```text
维修人员 ──处理──→ 维修工单
          开始时间、结束时间、维修结果
```

但如果一次维修具有独立编号、多个参与人员、备件消耗、审批和生命周期，或者同一工单存在多次需要分别跟踪的维修，就可以考虑把“维修活动”作为独立节点：

```text
维修人员 ──参与──→ 维修活动 ──处理──→ 维修工单
                       └──消耗──→ 备件
```

这通常叫作**关系实体化**：把原先用一条关系表达的联系，改为独立对象，并让其他对象连接到它。独立节点便于把多个人员、备件和时间绑定到同一次活动，但也增加结构和维护成本。

关系也可以有属性，属性也可以被查询和建立索引；因此“需要记录时间”或“需要查询”并不自动要求创建节点。关键是是否需要独立身份、多个关联、分别维护的生命周期等能力。

## 4. 字段通常是属性，也可以作为元数据建模

装备编号、名称、剩余寿命和寿命单位，通常可以作为装备节点的属性：

```text
装备
  编号：EQ001
  名称：示例装备
  剩余寿命：120
  寿命单位：小时
```

如果要管理字段定义之间的关系，例如明确“剩余寿命需要结合寿命单位解释”，也可以在**元数据层**表示：

```text
剩余寿命字段 ──依赖──→ 寿命单位字段
```

这里的字段节点描述的是字段定义，而不是把每台装备的每个属性值都变成节点。是否这样建模，取决于是否需要独立管理、关联或分析字段定义；也可以用其他结构保存这条规则。

节点、关系和属性的划分没有脱离任务的唯一答案。需要关注的是选定的表示是否能保留信息，并方便后续使用。

## 5. 描述要具体到可以消除歧义

“装备关联故障”只能说明存在联系，往往不足以指导查询或校验。对需要精确使用的概念和关系，可以按需记录：

| 对象 | 可以记录的内容 |
| --- | --- |
| 实体类型 | 名称、业务定义、别名、标识规则、字段定义 |
| 关系类型 | 关系含义、方向、两端类型、适用条件、基数 |
| 数据映射 | 实际表和字段、关联依据、可用路径、去重要求 |
| 业务规则 | 有效状态、排除条件、统计对象、时间口径 |

例如，“装备关联故障”还可以继续问：

1. 关联是直接发生，还是也包括通过部件关联？
2. 两端的角色和方向是什么？是否存在多条合法路径？
3. 实际数据通过哪些字段连接，哪些条件必须满足？
4. 多条关联是否可能指向同一故障，统计时按什么标识去重？
5. “有效故障”如何定义，时间按发生时间还是登记时间？

这些内容既可以为人和语言模型提供上下文，也可以成为程序校验的依据。但自然语言描述、结构化规则和真正执行的校验是不同层次，需要分别确认。

## 6. 区分类型定义和实际数据

构建图谱时，还需要区分描述“有哪些概念和关系”的知识，与描述“具体发生了什么”的实例：

| 层次 | 示例 |
| --- | --- |
| 类型与规则 | 装备是一种实体类型；装备可以发生故障；装备编号有定义 |
| 实例数据 | 编号为 EQ001 的某台装备、某次故障及参与维修的人员 |

前者帮助统一概念、关系和规则；后者记录实际对象及事实。实例既可以存入图数据库，也可以保留在原有数据库，通过映射或其他方式关联到定义，具体取决于系统用途。不需要因为建立了业务概念模型，就默认迁移所有实例数据。

业务模型、图数据库中的 Schema 与实例图各有侧重点，实践中可能存在映射或重叠，不必把它们理解成只能采用某一种物理存储方式。

## 7. 建模时的判断清单

1. **先确定任务。** 写出实际要回答的问题、需要维护的知识和预期查询方式。
2. **判断独立性。** 需要独立身份、生命周期、多个关联或复用的对象，可以优先考虑节点；这些是启发式，不是硬规则。
3. **判断联系。** 主要表达两个对象之间的联系时，可以优先考虑关系；联系本身复杂到需要独立管理时，再考虑实体化。
4. **判断特征。** 主要描述对象或关系特征时，可以优先考虑属性；需要对定义或取值进行独立关联和管理时，再评估是否提升为节点。
5. **明确语义与规则。** 检查关系方向、适用条件、时间、基数、标识、单位和必要的数据映射。
6. **用例子验收。** 用代表性数据和查询检查是否遗漏信息、是否引入歧义，以及更新时是否容易维护。

最后，图数据建模侧重如何用节点、关系和属性表达与查询数据；本体建模进一步关注概念类型、关系语义及逻辑约束等。两者有交集，实际边界取决于采用的模型和工具。
