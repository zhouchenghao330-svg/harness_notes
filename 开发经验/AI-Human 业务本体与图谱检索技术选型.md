# AI-Human 业务本体与图谱检索技术选型

> **选型结论（2026-10-29）**：以有源码依据的版本化业务本体作为事实源，展开成类型级图谱；将带必要上下文的单条定义作为检索单元。装备维保已启用 SQL Workflow 的 App 默认使用向量召回、显式依赖递归补全与知识预算装配。笔录图谱及独立 SQL 试查已建成，但笔录 SQL 试查仍使用完整可查询语义目录，尚未建立自己的 Embedding/BM25 索引。本文记录已选架构及当前接入范围，不把实验对比能力写成已接入能力。

## 一、图谱表达什么

图谱节点表达**业务类型和定义**，不是数据库中每一条具体记录。案件、笔录、装备等实体节点代表对象类别；具体对象继续留在业务库。一个实体节点也不等于一张物理表：笔录业务的多种对象共用 `object_resource`，依靠 `app_id`、`type_code` 区分；真实关联存于 `link_object`。SQL 场景再将本体概念映射到可查询的语义视图。

规范文件 `ontology.json` 是事实源，`graph.json` 是从规范展开的图。图及检索索引采用版本化文件和内存加载；当前方案未引入 Neo4j。构建时由 Coding Agent 核对业务注册、元数据、ORM、读接口、回调、聚合服务以及 AI-Human 调用，再把解释过的定义和依据写入声明。构建器读取源码 AST 字面量与经核对的定义，校验后生成产物；构建过程不调用 LLM 或 Embedding 来自动猜测关系。

笔录核心 v1 展开后的节点和边可以说明所选模型：

| 节点 | 数量 | 主要内容 |
| --- | ---: | --- |
| 业务实体 `entity` | 9 | 名称、别名、职责、对象身份、存储/读取映射、来源 |
| 字段 `field` | 335 | 含义、类型、空值、单位、取值域、存储路径、解释或计算依赖、来源 |
| 业务规则 `rule` | 13 | 约束及其适用字段、关系和源码依据 |
| 统计定义 `measure` | 1 | 聚合方式、粒度、分组、单位和依据 |

字段在规范中归属实体，编译图时展开为独立节点。335 个字段定义含公共字段、JSON 路径及兼容名称，不代表 335 个独立业务事实。节点还保留稳定 ID、`meaning_status` 与 `source_refs`；来源记录文件位置和哈希，待确认事项单列。

业务边连接实体：笔录版有 17 条直接边和 1 条派生边。直接边写明 `source`/`target`、方向、端点角色、`relation_type`、业务域及端点类型、过滤、去重、读取映射和来源；输入文件与生成文件是不同边。派生边必须列出**批准路径**，例如“案件 → 笔录 → 提取结果，仅保留 ready”，其依据是现有聚合服务，不能因为图上可达就自动生成。另有字段归属、字段依赖、历史名称镜像、规则引用等元数据边。笔录完整图合计 358 个节点、386 条边，其中只有 18 条是实体间业务关系。

核心笔录本体的 `query_mapping=null` 是明确边界：`storage_mapping` 说明实际存储，`read_mapping` 说明现有读取接口，二者都不冒充 SQL 映射。后来的 SQL 试查另建实验映射，不回填或改写冻结的核心 v1。

## 二、装备维保如何建立检索单元

装备维保把**一条定义加必要上下文**做成一条索引文档。实体、字段、关系、规则、指标分别可被命中，共 332 条定义文档。`embedding_text` 和 `lexical_text` 来自同一份可读语义文本，但用于两条独立检索路线。

| 定义 | 送入检索文本的上下文 |
| --- | --- |
| 实体 | 业务域、名称、ID、别名、职责 |
| 字段 | 业务域、所属实体、名称、ID、含义、类型、声明取值或状态、依赖的名称与 ID |
| 关系 | 名称、两端实体、方向/角色、含义、直接或派生、批准路径、去重粒度、SQL 语义映射 |
| 规则 | 名称、ID、描述、结构化约束 |
| 指标 | 名称、定义、统计粒度及关联路径 |

例如 `equipment.remaining_life` 的文档包含“装备档案”所属关系，以及 `equipment.usage_life_unit`、`equipment.usage_life`、`equipment.online_date` 等依赖的名称和 ID。它**不拼入**依赖字段的完整定义、装备的全部字段或全部相邻边。单位的完整 `year/hour/mileage` 声明保留在自己的定义里，命中“剩余寿命”后由图补全带入 SQL 上下文。索引内容是本体定义文本，不是实际装备记录、附件正文或源码全文。

实验中，同一批文档可以分别走：Embedding 向量相似度；jieba 分词、业务词典与英文 ID 拆词后的 BM25；以及两路排名的 RRF 融合。**jieba 不先把词送进 Embedding。**已接入装备 SQL 客户端的默认选型是 `Qwen3-Embedding-0.6B` 向量路线；BM25 与 RRF 是 labs 中的横评路线，当前不作为该客户端的默认运行链路。

查询侧的向量输入组合本次子任务、本轮原话、有限公开对话，以及可信已选对象的资源类型、名称和编号，以支持“刚才那几台”等指代。运行时先取得后端可信 SQL 上下文，核对本体版本与原手册指纹，然后只替换交给 SQL Workflow 的 `manual`；原 `schema_version`、已选对象、权限范围、SQL 生成/修复及执行链继续由原服务负责。这个接入只作用于显式启用实验 SQL 工具的装备 App。

2026-10-29 的故障分析确认：给 SQL 模型展示图谱内部关系 ID 与实际执行表名，可能让模型把前者误写成表名；把首次 SQL 的结构当修复基准，也可能拦住正确的表名修正。本机现已改为向 SQL 模型展示执行名称、内部保留图谱 ID，并移除旧结构冻结检查；定向测试和真实接口已验收，原问法中主 Agent 自行缩小列表范围的问题仍待解决。经过、验收证据及业务语义边界见 [[开发经验/Text-to-SQL 上下文设计：清晰 Schema 与少量关键业务规则#7. 后续故障：图谱名称与 SQL 执行名称、修复校验的边界|Text-to-SQL 后续故障经验]]。

## 三、命中后如何补图：按依赖闭包，而非固定几跳

每个命中定义按其类型递归补全，已访问的定义 ID 不重复处理：

| 命中类型 | 自动补入 |
| --- | --- |
| 实体 | `id`、`object_code`、`name` 三个身份字段 |
| 字段 | 所属实体、声明的 `depends_on`、`derived_from`、`historical_mirror_of` |
| 关系 | 两端实体、派生关系声明的批准路径 |
| 指标 | 统计路径、聚合字段、分组字段 |
| 规则 | 明确引用的字段或关系 |

这些依赖继续按同一规则展开，所以没有统一的“一跳/两跳”。单独命中 `equipment` 得到实体加三个身份字段，共 4 项；命中 `equipment.remaining_life` 补到所属实体、身份、寿命值、单位、使用寿命、列装日期，共 8 项；命中 `equipment_workorders_all` 会沿已批准的工单、故障、部件和告警路径补到 29 项。**不会**从“装备”实体遍历全部邻边和全部字段，也不会按最短路径发明业务关联。只命中装备实体时，若未召回剩余寿命字段，补全本身不会发现该字段；字段召回仍需单独评测。

当前已接入装备 SQL 客户端取相似度 Top-K=12，先保留固定公共规则，再对每条命中计算完整闭包，并按 2500 个**知识上下文 Token**预算逐组加入。放不下就拒绝整组，不截断关系路径；2500 不是整个 SQL 请求的 Token 总数。索引、模型服务、预算或版本/手册不匹配时，记录 `effective_mode` 与 `fallback_reason`，回退到后端当次返回的完整手册。正常业务澄清或语义错误不借此自动全量重跑。

选择 K=12 的依据和局限见 [[开发经验/知识图谱检索单元的组织与分阶段横评|分阶段横评]]：在当时的冻结题集里，K=24 使部分回执包含更多事实，但严格 SQL 交付没有提高、累计模型 Token 增加约 20.6%。因此保留 K=12 作为当前成本基线；这不代表所有召回遗漏已经解决，也不是通用准确率结论。

**2026-11-02 补充（装备 v1.4.1）**：在上述2026-10-29装配方式基础上，主 Agent 先取得完整业务概览和本题相关资源的简明详情；内部 SQL 模型收到同版本业务说明，并先装配声明资源的完整已开放字段映射，再使用 Top-12 补充关系等知识。必要映射不能因预算部分缺失，整体超出知识预算时回退完整手册。核心经验是同源业务定义、按职责分层披露；资源、状态、关系口径和本次对象范围需要跨模型一致。正式50题复测、剩余对象焦点问题及归因边界见 [[开发经验/Text-to-SQL 上下文设计：清晰 Schema 与少量关键业务规则#8. 多模型查询链路：主 Agent 与 SQL 模型共享业务认知|主 Agent 与 SQL 模型的业务认知对齐]]。

## 四、笔录图谱当前用在哪里

笔录图谱已经有类型、字段、规则和带来源的业务关系，也有独立 SQL Workflow 试查。但其 SQL 映射属于 labs 的只读快照适配：模型收到**完整的可查询语义目录**，通过原 SQL Workflow 生成和修复 SQL，在实验独立快照中执行。它没有使用装备索引，也没有建立自己的 Embedding、jieba/BM25 或混合检索。页面“定位节点或关系”只是名称/ID 本地文本匹配，不参与 SQL 知识选择。

笔录 SQL 试查未注册为正式聊天工具，实验快照不等于实时用户权限视图，也未接通正式 `AISQLReadService` 的会话引用、审计和权限链。后续若要改成检索裁剪，需要针对笔录自己的语义目录构建索引，并在相同映射、模型和快照下验证召回、知识预算与 SQL 结果；不能直接把装备实验结果视为笔录效果。
