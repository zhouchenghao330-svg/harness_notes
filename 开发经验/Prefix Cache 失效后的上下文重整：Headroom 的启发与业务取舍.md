# Prefix Cache 失效后的上下文重整：Headroom 的启发与业务取舍

> **缓存仍热时，保留已经送模的稳定前缀；缓存已经冷却时，可以重新评估旧工具内容怎样进入下一次请求。具体保留哪些内容，由业务依赖决定。**

记录来源：2026-10-20 关于 Headroom 和 ai-human 上下文管理的讨论。本次核对 Headroom 官方仓库提交 `fbf7bc3278c11975299b9bd0a2ecf200dfd25a05` 中的缓存文档、冷前缀判断、Anthropic handler 和相关测试。下文把源码机制与延伸设计分别说明；ai-human 部分是待验证的设计设想，本次没有接入或改变其运行策略。

## 1. 这次最有意思的启发

讨论中的想法是：

> Prefix Cache 超时之后，可以对上下文做一些处理，让下一次对话少读一些内容、回复更快。是否这样处理，要根据业务场景决定。例如 ai-human 的一些新问题，可能不需要继续依赖之前的工具正文。

这个想法有价值，因为它把**何时值得改写表示**与**哪些信息需要继续保留**分开考虑了。

原来容易只盯着“上下文快满了没有”：没满就继续累积，快满了再做语义摘要。现在可以多一个决策维度：缓存是否仍然值得保护。即使上下文距离容量上限还远，冷却后也可能有机会通过较小的重整，减少下一次请求的输入工作量。

不过，缓存失效只改变计算与复用的条件，不改变业务事实的价值。**缓存冷却是重整的机会窗口，业务依赖才是撤下内容的依据。**

## 2. 为什么热缓存和冷缓存值得采用不同策略

一次模型请求通常包含稳定指令、工具定义、历史消息和新输入。前缀相同且缓存仍可用时，服务端可以复用部分已计算结果。

假设一段工具正文已经送给模型，也成为后续请求的历史前缀：

```text
稳定指令 / 工具定义
   ↓
历史消息＋旧工具正文
   ↓
本轮新增消息
```

如果每一轮都重新压缩旧工具正文，变化点之后的前缀可能无法继续命中。虽然文本更短，也可能多付出重新计算历史的成本。

缓存仍热时，可以先对新工具回包做紧凑处理，接纳后固定其表示；后续重放同一份文本。

缓存已经冷却时，继续维持那段旧工具正文，只是为了保护其原有缓存，就未必还有收益。此时可以考虑重新编码、去重，或按明确业务规则撤下不再需要的正文，再以新表示建立后续可复用的前缀。

这里的“缓存已经冷却”必须限定到相应前缀或缓存区段。旧历史的一部分不可复用，不代表 system、tools 等更早的公共前缀也全部失效，仍应尽量保持它们稳定。

## 3. 从 Headroom 核对到的机制

### 3.1 Cache Mode：保护之前实际转发的表示

Headroom 的缓存文档说明，Proxy 的默认 cache 模式主要压缩新增 delta，之前已经转发的内容保持稳定。这保护的是**模型服务实际收到的前缀**，不能只检查业务侧原始消息是否没变。

例如，客户端每次重新发送原始工具结果，而代理上次发送的是压缩结果。代理需要继续重放上次转发的版本，才能维持它此前建立的前缀。不能本轮突然恢复成原始大正文，再认为“业务原文没变，缓存应该还在”。[缓存优化文档](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/docs/content/docs/cache-optimization.mdx)

### 3.2 Cold Prefix：冷却后允许重新处理旧前缀

`is_cold_prefix()` 的主要判断可以简化为：

```text
空闲时长 > 本次适用的 TTL + 安全余量
   ↓
把该前缀判为冷却候选
```

该提交中默认安全余量为 60 秒；无法取得所需信息或判断出错时，返回 False，避免轻易把仍热的缓存当成冷缓存。[cold_prefix.py](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/headroom/transforms/cold_prefix.py#L34)

它不是直接查看服务端 KV 内存后确认删除，而是根据可获得的 TTL 和时间信号进行判断。Anthropic 路径会读取请求里的缓存 TTL 和相关配置；通用 tracker 还存在按 Provider 配置或默认值回退的路径。因此，不能把默认 TTL 当作任意服务的可靠过期事实。[TTL 解析](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/headroom/transforms/cold_prefix.py#L124)、[tracker 回退](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/headroom/cache/prefix_tracker.py#L1340)

本次核对的 Anthropic handler 中，冷前缀重整通过 `HEADROOM_COLD_RECOMPACT` 显式启用，默认关闭。冷却分支会执行全消息范围的重新整理，并跳过原本用于恢复旧转发前缀的 overlay，避免新整理结果又被旧版本覆盖。[判断入口](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/headroom/proxy/handlers/anthropic.py#L1809)、[重整分支](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/headroom/proxy/handlers/anthropic.py#L2245)

### 3.3 重整后的表示也需要稳定下来

`cold_recompact_messages()` 会创建一个新的 ContentRouter，允许处理原先冻结的消息范围，执行相应的无损折叠和跨轮去重。引用型去重还受恢复能力约束：无法解析引用的路径，应保留正文而不是发出无法使用的短指针。异常时返回原输入。[重整函数](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/headroom/transforms/cold_prefix.py#L198)、[引用可恢复性测试](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/tests/test_cold_prefix.py)

值得借鉴的是“冷却时选择一次新表示，后续继续稳定重放”，而不是每轮随着新 query 把全部历史重新洗一遍。

另外，Headroom 的 `densify()` / agent 模式与冷前缀重整不是同一个入口。前者明确要求可验证的无损回环，无法证明还原的消息回退原文；不能把这一保证直接套到所有上下文撤除、旧读取淘汰或引用恢复策略上。[agent 模式](https://github.com/headroomlabs-ai/headroom/blob/fbf7bc3278c11975299b9bd0a2ecf200dfd25a05/headroom/compress.py#L163)

## 4. 可以借鉴的三层上下文管理

这三层各自有触发条件，不必绑定为每次请求都完整执行的固定流水线。

| 层次 | 主要时机 | 处理内容 |
| --- | --- | --- |
| 新回包表示优化 | 工具结果进入模型上下文之前 | 表格化、等价去重、公共字段复用等 |
| 缓存感知重整 | 缓存冷却，且存在值得处理的旧内容时 | 重新编码、跨轮去重，或按业务策略调整旧正文的可见性 |
| 语义摘要与任务交接 | 容量压力或明确的任务交接需求 | 概括用户目标、完成项、未完成项、约束与必要依赖 |

前两层可以大量使用程序规则，不必增加一次生成式模型调用。第三层仍可以沿用自己的 Conversation Compaction 机制。

**缓存超时和上下文接近上限是独立事件。** 缓存超时不要求立即摘要；上下文超限也不能为了保住缓存而继续发出放不下的请求。

## 5. ai-human 中适合讨论的业务场景

“有些新问题不依赖上一轮工具正文”可以作为策略设计的出发点，但不能直接推广成所有会话的默认事实。

| 场景 | 对旧工具正文的处理方向 |
| --- | --- |
| 上轮已完成，本轮明确是独立查询 | 可以评估撤下旧明细，保留用户需求与已完成结论等必要状态 |
| 本轮要求查询当前状态，旧结果已经过时 | 评估用本轮新查询提供事实；避免继续把旧快照当当前状态 |
| “继续刚才的任务”“比较上一轮两份结果” | 保留相关旧正文，或在回答前显式重新取得证据 |
| 正在编辑文档、填写草稿或等待确认 | 保留任务状态、版本、引用及尚未完成操作所需的信息 |
| 精确计数、跨轮筛选或核对历史结果 | 保留精确数据或可用的结构化查询入口，不能只剩模糊概述 |

例如，上轮查询了某批装备的详细数据，本轮转向一个明确独立的人员查询。如果旧装备明细对本轮没有依赖，缓存又已经冷却，就可以评估不再把整批明细原样放入请求。

但如果本轮是“刚才第二台设备和第三台比较一下”，旧明细就是必要输入。不能因为经过一段时间，就认定它们已经没有用途。

判断也不应只靠某几个 query 关键词。当前任务是否完成、待确认状态、明确选中对象、业务流程边界和可恢复的数据入口，通常比“消息有多旧”更能说明依赖关系。

## 6. 按业务撤下旧正文，需要明确保留什么

可以把旧工具回执里的信息分开看：

| 信息 | 处理考虑 |
| --- | --- |
| 大量已完成且当前无依赖的结果明细 | 可以作为撤下或重新编码的候选 |
| 对象 ref、已选对象、分页位置 | 后续可能用于可信指代和继续查询，按任务状态保留 |
| 当前业务手册与工具使用前提 | 仍需满足可见性和调用协议，不能与旧明细一起粗删 |
| 草稿 ID、版本、待确认操作、幂等状态 | 优先保留在明确的结构化状态中 |
| 来源与获取方式 | 需要恢复时，应知道在哪里、以什么权限重新取得 |
| 成功、失败、取消与完整性状态 | 不能因为缩短文本而把“未取得”变成“没有数据” |

这里也要区分两类操作：

- **重编码、精确去重**：目标是让约定的数据或事实仍能完整恢复。
- **撤下不再需要的正文**：模型当前视图中确实少了内容；即使原文仍存于别处，也属于带恢复条件的信息选择。

后者可以合理，但不能一概叫作无损压缩。尤其要确认原文确实有保存、仍有访问权限和恢复入口。不能假设所有 raw 回包都已经统一落库，也不能把重新查询当前数据等同于恢复过去那一刻的快照。

## 7. 放到 ai-human 中，应该先视为一个可选策略

当前本地 `context_manager.py` 的正式工具历史路径，明确重放首次投影和准入后保存的文本，不按后续调用或轮数重新执行 projector。这个稳定重放边界已经存在。

```text
app/agent_runtime/context_manager.py:633
docs/plans/2026-09-16-stable-tool-history.md
```

因此，这次想法是在讨论一个新的决策点：在确认业务边界和缓存条件之后，是否允许创建新的模型上下文表示。不能把它当作当前代码已经具备的行为，也不能直接恢复以前那种“旧了就删”的统一规则。

一种候选组织方式是：

```text
新请求到达
   ↓
确认会话、模型、工具集合与任务状态
   ↓
评估可用的缓存信号
   ├─ 仍热 / 状态不明确 → 沿用稳定表示，主要处理新增内容
   └─ 可靠地判断已冷却 → 评估本业务是否允许重整
                            ↓
                       生成候选模型视图
                            ↓
                       校验依赖、工具消息协议和完整预算
                            ↓
                       采用新表示，并在后续稳定重放
```

这里重整的是**送模副本**。原始会话记录、审计、任务状态及业务写入结果，仍需要按各自职责保存。删除一条 ToolMessage 也要考虑对应 tool call 的协议完整性，不能独立留下失配消息。

这只是后续实现讨论的候选设计，本笔记不要求增加一套新状态表、意图分类模型或自动启用所有场景。

## 8. 为什么“下一次更快”仍需实测

这条路线最直接期待减少的是输入侧 prefill 工作量，因此可能改善首 Token 时间。但最终收益还取决于整理成本、缓存判断是否准确，以及模型是否因此需要重新查询。

例如，撤下 10,000 Token 的旧结果，可能减少下一次输入；如果随后为了恢复关键事实多调用两次工具、再增加一轮模型推理，整轮任务反而可能变慢。

在具体模型服务上，还要先确认缓存是按什么规则保留或驱逐、有哪些可见命中指标。不能把某个 Provider 的固定 TTL 直接套到 ai-human 当前部署，也不能只凭客户端的一次空闲时长就宣称服务端缓存已经消失。

比较时可以记录：

- 输入 Token、可见的缓存读取和写入用量。
- 上下文整理耗时、首 Token 时间与任务总耗时。
- 额外工具调用及恢复次数。
- 独立问答、连续任务和历史对比任务中的正确性。

先确认业务确实允许撤下哪些内容，再比较相同任务的效果。当前没有在 ai-human 上运行这组性能实验，不能把该启发写成已经获得的时延收益。

## 9. 这次保留下来的判断

这次最值得延伸的，不只是“工具结果可以压短”，而是**上下文管理可以同时考虑业务依赖、缓存状态和容量压力**。

对于独立问答占比较高的业务，缓存冷却后按规则撤下已完成、无后续依赖的大回包，值得实验。对于连续写作、分析、精确对比和多步业务操作，应更重视证据与状态的持续可用性。

策略的目标是让模型更快且可靠地完成下一项任务。更小的请求、更高的缓存命中率和更少的摘要调用，都只是实现这个目标时需要一起衡量的指标。
