# 向量化经验：为检索文本补充必要上下文

> 做向量检索时，值得先设计“什么内容一起送进 Embedding 模型”。一条正文、字段或关系的名字，可能不足以说明它的含义；把理解它所需的上下文一起编码，可能让它更容易被相关问题召回。

**用于生成向量的文本，可以是为检索加工过的表示；原始内容和结构化字段仍然单独保存。** 补充上下文是检索设计选择，是否有效需要通过实际查询验证。

## 1. 一条内容可以有两种表示

假设要保存一条事实：

```text
事实正文：Alice 在 Acme 公司使用 Python 编程。
相关实体：Alice、Acme、Python
参考日期：2026 年 10 月
```

可以保留原事实正文，同时构造另一份用于向量化的文字：

```text
事实正文 + 日期信息 + 相关实体名称 → Embedding → 向量
```

这样做的意图是让日期和实体名称也参与语义表示，为相关查询提供更多线索。原始正文、精确日期和实体关联仍应保存在各自的字段中，供展示、筛选、追溯和后续重建使用。

检索文本是从原始数据派生出来的视图。向量检索找到的是候选内容；要确认原文、精确条件或事实依据，仍应回到原始记录和结构化字段。

## 2. Hindsight 的一个实际例子

已有的 Hindsight 学习笔记记录了其事实向量化的一种做法：以**一条事实**为单位，生成用于 Embedding 的新字符串，在事实正文后按条件追加可读日期和相关实体名称；原事实正文单独保存。

例如，教学输入是：

```text
事实正文：Alice 在 Acme 公司使用 Python 编程。
参考日期：2026-10-01
实体名称：Alice、Acme、Python
```

笔记中核对的加工结果为：

```text
Alice 在 Acme 公司使用 Python 编程。 (happened in October 2026) [Alice, Acme, Python]
```

这个例子说明的是**向量输入的构造方式**，不代表向量内容取代了原事实。日期优先使用事件开始日期，没有时回退到被提及的参考日期；参考日期不一定是事件发生日期，不能仅凭追加后的 `happened in` 就把它当作发生时间的证据。日期和实体提供匹配线索，但原笔记没有证明它们一定改善召回。

详细的字段、执行顺序和源码位置见 [[all_harness/hindsight/02_retain_pipeline#5.2 第 10 项 加工用于 Embedding 的文字|Hindsight：加工用于 Embedding 的文字]]。

## 3. 图谱中的节点、字段和关系可以怎样组织

如果检索对象是知识图谱中的定义，也可以先明确**每条向量代表什么**，再围绕它组装必要上下文。以下是设计示例，不是固定模板：

| 检索单位 | 可以考虑一起编码的内容 | 目的 |
| --- | --- | --- |
| 节点或实体类型 | 名称、别名、简短定义 | 区分同名概念，让不同叫法有机会匹配 |
| 字段定义 | 字段名、所属对象、业务含义、单位 | 避免只凭“名称”“状态”等通用字段名检索 |
| 关系定义 | 两端对象、关系名、方向、简短语义及适用条件 | 让关系在向量文本中保留足够的上下文 |
| 一条事实或事件 | 事实正文、参与对象、可靠的时间信息 | 将同一次事实相关的信息组织在一起 |

例如，单独对“剩余寿命”编码，可能无法区分它属于什么对象、采用什么单位。可以尝试：

```text
对象：装备
字段：剩余寿命
含义：装备尚可使用的预计时间
单位：小时
```

这里的定义和单位只是教学假设，真实使用时必须来自实际资料。如果单位因记录而异，应明确它是另一个字段，而不是替所有数据写死一个单位。

关系也一样。只编码“处理”可能含义太宽；可以尝试把两端和角色带上：

```text
维修人员 ──处理──→ 维修工单
含义：维修人员负责处理相关维修工单。
```

如果同一关系有时间、适用条件或其他区分信息，是否加入检索文本要看查询需要；这些信息仍应在原始结构中保留。图里的箭头和角色必须与真实关系一致，不能为了让检索文本更丰富而添加没有依据的事实。

## 4. 一起编码多少内容，要看检索单位

把相关信息放在一起，可以让一条向量表达更完整的含义；但将无关字段、多个不同对象或大量背景混在一起，也可能冲淡主要信息，使召回结果难以解释。

可以按下面的顺序设计：

1. **确定检索目标。** 要找的是实体、字段、关系、事实，还是整篇文档？
2. **确定最小有意义的单位。** 例如一个字段定义或一条关系定义，而不是默认把整个图谱放入一个向量。
3. **加入必要上下文。** 补充能消除歧义、可能被用户提到的名称、定义、角色、单位或时间。
4. **保留原始信息和来源。** 检索文本、向量与原始对象保持关联，以便查看依据和重建索引。
5. **检查长度和更新。** 长度过大可能被模型截断；正文、别名或规则变化后，需要考虑重新生成相应检索文本和向量。

同一个对象也可以按不同检索需求建立多种表示，但需要管理各表示与原始对象之间的对应关系，并评估额外成本。

## 5. 用实际问题验证，而不是假设加得越多越好

可以准备一组有代表性的查询，比较不同输入方案：

```text
方案 A：只编码名称或正文
方案 B：名称或正文 + 简短定义
方案 C：名称或正文 + 定义 + 与任务有关的上下文
```

在同一组查询、模型和检索设置下，对比能否找回正确对象、前几条结果是否相关，以及错误结果为什么出现。尤其检查同名字段、同义说法、关系方向、日期和单位等容易混淆的情况。增加信息可能改善某些查询，也可能让其他查询变差；应根据评测结果调整。

向量检索之外，也可以根据任务结合关键词检索和结构化过滤。中文关键词检索若使用 jieba，是分词方案的一种选择；它与构造 Embedding 输入是不同环节，使用向量检索本身并不要求先用 jieba 分词。
