# World State 设计：初始快照加追加 Diff

> 环境状态需要进入模型上下文时，可以先给出一份初始快照，之后只把状态变化追加到上下文末尾。这样既保留状态变化的过程，也有机会维持已经发送过的稳定前缀。

这是一种值得参考的设计思路。下文示例根据关于 Codex Harness 的文章描述整理，**是概念示例，不代表 Codex 实际的数据结构或已核实的实现**。

## 1. 把环境信息组织成有身份的状态

模型执行任务时，可能需要知道当前工作目录、项目规则、权限提示等环境信息。如果每次请求都重新生成一份完整环境描述，哪怕只有一个字段发生变化，也可能改动已发送内容的前部。

一种思路是将环境组织成多个有类型、有标识符的 Section，先记录初始状态：

```yaml
# Snapshot v1：概念示例
world_state:
  permissions: read_write
  project_rules:
    run_tests: true
    use_uv: false
  working_directory: /project
```

之后，如果项目规则中的 `use_uv` 发生变化，可以生成带版本信息的 Diff：

```diff
# Diff v1 → v2：概念示例
project_rules:
-  use_uv: false
+  use_uv: true
```

下一次请求中的逻辑顺序可以是：

```text
初始 Snapshot v1
    ↓
已有历史对话
    ↓
新增 Diff v1 → v2
    ↓
本轮新输入
```

模型需要把快照和后续变化结合起来理解：当前 `use_uv` 是 `true`，其他没有被修改的字段沿用已有状态。更复杂的场景还需要明确如何表达新增、删除和整体替换，避免把“字段没有出现在 Diff 中”误解为删除。

## 2. 为什么追加 Diff 有利于 Prefix Cache

前缀缓存通常依赖后续请求中**实际送给模型的前缀保持一致**。如果把历史里的初始快照从 `false` 改写成 `true`，改动位置之后的前缀可能无法沿用原有缓存。

保留原快照、在末尾追加变化，则前面的内容有机会保持不变，模型服务可以在缓存仍可用且其他条件满足时复用相应前缀。具体收益还取决于模型服务的缓存机制、缓存是否仍在、消息序列化和其他请求内容是否稳定，不能仅凭“用了 Diff”就认定一定命中。

**逻辑上只新增 Diff，不等于每次网络请求只发送 Diff。** 有的接口仍需要客户端重放完整的逻辑上下文，由服务端复用其稳定前缀；也有接口提供不同的会话或状态管理方式，要以实际接口为准。

## 3. Diff 积累到什么时候，应该重建快照？

如果一个字段反复变化，或者环境已经发生大量调整，模型仍然需要结合旧快照和后续所有 Diff 才能还原当前状态。此时继续追加，可能让上下文变长，也增加引用旧值或理解错顺序的风险。

可以考虑定期把**当前完整状态**生成新的快照，作为后续变化的新基准：

```text
Snapshot v1 + Diff v1→v2 + ... + Diff v29→v30
                         ↓
         从状态真源生成完整的 Snapshot v30
                         ↓
            后续从 v30 继续追加 Diff
```

这里的 30 次只是便于理解的例子，**不是推荐阈值，也不是已经验证的安全次数**。需要通过具体任务测试，确定一个可配置的重建策略。可以考虑同时观察：

| 信号 | 需要考虑的问题 |
| --- | --- |
| Diff 次数 | 追加次数是否达到为当前场景设定的上限？ |
| Diff 总长度 | 累积变化是否已经接近或超过重新给出当前快照的成本？ |
| 同一字段反复修改 | 同一字段出现多个旧值时，模型是否仍能稳定识别最新值？ |
| 状态变化范围 | 如果很多 Section 都发生变化，旧快照是否已很难代表当前环境？ |
| 上下文压力与缓存 | 状态表示是否占用太多上下文；重建带来的前缀失效代价是否可以接受？ |

实际阈值应结合状态大小、变化频率、模型表现和缓存状况测量，不必只依靠次数。也可以把次数作为容易实现的上限，同时用其他信号提前触发。

**只在末尾追加新快照，并不会自动缩短已有上下文。** 如果要减少旧 Snapshot 和 Diff 的占用，需要在新的模型上下文视图中以新快照作为基准，并按需移除或压缩旧状态表示。这会改变相关位置之后的前缀；原始状态历史、审计记录或任务仍需要的变化依据，应按用途另行保留，不能因为模型只需要当前值就一并删除。

重建时应从可信的 Runtime 状态源或经过程序校验的完整状态生成快照，明确版本边界；生成期间的新变化需要按版本衔接，避免遗漏或重复应用。后续再围绕新快照稳定追加。

## 4. 需要验证的问题：长 Diff、压缩与权限

这套设计不能只看文本是否变短，还要验证模型看到的状态是否始终足够准确。可以用下面的问题设计测试：

1. **经过 30 次状态变化，模型还能正确还原当前状态吗？** 用实际初始状态和一串变化生成测试，比较模型回答与程序计算出的最终状态。30 是测试样例，不预设它一定安全或一定失败。
2. **同一个字段多次修改后，模型会不会引用旧值？** 覆盖反复切换、删除后重建和多个字段交错更新等情况，检查模型引用的版本及最终值。
3. **发生 Context Compaction 后，早期 Snapshot 被压缩掉，后续 Diff 还能解释吗？** 如果 Diff 的基准消失，单靠 Diff 不一定能恢复完整状态。压缩或重建模型上下文时，可以从状态真源生成当前完整快照，再让后续 Diff 以它为基准；要保留任务所需的历史变化，而不是假定当前状态可以替代全部历史。
4. **权限变化后，模型上下文与 Runtime 的实际权限一致吗？** 在权限变更和上下文重建后检查两者的版本与内容。Runtime 的实际权限检查是执行时的权威依据，模型里的权限描述用于理解环境，不能代替执行校验。

还应测试快照生成时同时发生新更新、Diff 丢失或顺序错乱，以及压缩后继续执行未完成任务的情况。对于错误或缺失的状态变化，系统需要能发现问题并重新同步，不能依赖模型自行猜测。

## 5. 这种设计需要注意什么

- **状态身份与顺序**：给 Section 和版本明确标识，按顺序应用变化；版本不连续或更新乱序时，需要检查、补齐或重新取得快照。
- **变化语义**：明确字段的新增、修改、删除和替换如何表达，尤其不能用模糊自然语言代替关键状态变更。
- **状态真源**：快照和 Diff 是提供给模型的环境表示；实际权限、工作目录和工具可执行范围仍应由运行环境及确定性的程序控制。
- **历史增长**：持续追加会增加上下文长度。变化较多时，可以在合适的时机生成新的完整快照并重新建立上下文，但这通常会改变前缀，需要权衡缓存收益与上下文预算。
- **一致性与验收**：检查模型是否正确理解最新值，并用实际请求观察缓存命中、输入 Token、时延和任务正确性；不能只凭示意图判断实现效果。

这个思路尤其适合**大部分状态稳定、每轮只有少量变化**的场景。它把“已知的初始状态”和“后来发生了什么”分开表达，也为排查状态变化提供了清晰线索。
