# 上下文压缩经验

## 之前整理的压缩与缓存经验

以下保留此前从原文整理的观点和实现示例，本次只整理格式，未重新核验各项目的最新实现。

### 压缩请求怎么组织

压缩请求就是上一次正常请求加一条指令。`tools`、`system`、完整历史、模型、`thinking` 配置逐字节不动，指令放在最后。发完整历史，别只发要被总结的那一段。

不要靠去掉工具或者改 `tool_choice` 来禁止调工具。用文字要求，再加兜底：模型调了工具或者回了空，就丢掉结果，换独立请求重试。

别为了省钱换小模型来压缩，缓存是按模型分的。Roo Code 干脆删了自定义压缩模型，理由是只有对话本来的模型才总结得准。

### 缓存怎么处理

压缩请求是一次性的，就算要写缓存也用 5 分钟 TTL。Claude Code 就是这么分的：主循环用 1 小时，压缩用 5 分钟。缓存已经冷了的话，可以像 pi 那样直接走不写缓存的独立请求。

压缩之后的历史反正是冷的，系统提示词一定要冻结，至少 `tools` 和 `system` 还能命中。

清理旧的工具输出也是在改历史，从改动的位置开始缓存全部失效。要清就攒着一次清一批。Qwen 一次清到阈值的一半，免得每一轮都破坏前缀。

### 阈值要留输出空间

阈值要给摘要输出留空间，用窗口减去一个预留量，别写死一个百分比。当时记录的实现示例：

- OpenCode V2：窗口减 `max(10%, 16k)`。
- pi：窗口减 `16384`。
- Qwen：`85%`，且不超过窗口减 `33k`。

### 摘要怎么注入

摘要用 `user` 消息注入，外面包一层说明：这是之前对话的摘要，不是新指令。

摘要里很可能带着网页和命令输出的原文，不包这一层，它们就成了用户说的话。

### 用数据验收

看压缩请求的 `cache_read_input_tokens`。有条件就像 Codex 那样写个测试，直接比对压缩请求和上一次正常请求的 body。

## 实践补充：为什么保留 Pressure Nudge

2026-10-15，根据 ai-human 的代码和这次讨论整理。这里记录执行中遇到上下文压力时的取舍，与上面的压缩请求、缓存经验分开看。

### 工具回包进入前，先算完整请求能不能放下

上下文窗口不大时，一次 RAG 或工具调用就可能返回很大的数据包。不能等回包已经拼进去、请求发给模型后才发现超限，要先算加入候选回包后的完整请求，包括 system、工具定义、历史和当前活动轮次，并给收尾留空间。

回包放不下时，要给模型明确的事实回执：工具执行过，但正文没有提供，不能把它理解成空结果，也不能假装已经取得正文证据。原始结果是否保存在系统里，与模型是否看到了正文，是两回事。

### 为什么不直接静默压缩，然后继续这个 run

压缩能腾出空间，但当前任务可能还依赖上轮、上上轮的原始细节。只保护当前 run，并不等于保护了当前任务需要的全部信息。

比如上轮查出了 A、B 两个方案的完整参数，本轮要求继续比较并生成实施方案。如果执行到一半把上轮压成“已查到两个方案”，模型可能就失去了精确比较的依据。摘要指令可以要求保留必要细节，但不能保证它预判到后面每一步需要什么。

固定保留最近 2–3 轮也只能降低风险：依赖可能更早，最近几轮也可能已经很大。不能只看压缩后是否低于容量上限，还要看任务能不能接着做。

### Nudge 先建立一次任务交接

Pressure nudge 让模型利用当前仍然可见的上下文，说明真实完成项、待确认事项和未完成项，然后结束本 run。它本身不缩短上下文，也不是暂停后自动恢复。

用户下一条 query 到来后，入口先恢复执行空间，必要时压缩历史。摘要保留任务进度，近期用户 query 保留需求线索，再结合当前 query，让 Agent 在更空闲的上下文里接续任务。用户说“继续”也可以，不要求下一条一定是独立问题。

可以把整个过程理解为：

> 回包接纳检查 → 接近容量时 nudge 收尾交接 → 用户下一条 query → 预算恢复，必要时压缩 → 结合近期需求和任务摘要继续执行。

这里 nudge 的价值，是在压缩前给任务一次明确交接的机会。需求还在、进度有记录、缺失证据可以重新获取时，Agent 就有条件在腾出的空间里继续完成任务。

### 当前实现需要分清的边界

- **近期 query 有保留，但不是任意长度的完整原文。** 已被压缩的轮次最多保留最近 5 条用户意图，每条预算最多 256 token；短 query 保留原文，长 query 会截断。未压缩的原始用户消息仍随历史保留。
- **下一轮一定进入恢复检查，不一定实际生成摘要。** 压力发生时记录 `recovery_pending`。如果大回包已被短回执替换，下一轮上下文本来就足够小，检查通过即可继续。
- **当前 nudge 并不只在压缩失败后触发。** 回包超出输入预算时会省略正文并收尾；即使完整回包能放下，达到输入预算的 90% 也会进入收尾。
- **当前活动轮次不参与摘要，最近历史原文只是保留偏好。** 不能把近期用户意图保留，理解成最近几轮全部原始证据都保留。
- **不能假设所有工具回包都一定放得下。** 当前 RAG 保留全部 chunks，模型投影主要消除等价重复包装，没有按上下文容量裁剪正文，因此仍需要回包接纳检查。

这套续接依赖关键需求和进度被保住，缺失证据能够重新获取。如果某些细节不可恢复，就要明确保留这些细节，或者给出可再次读取的引用。单靠 nudge 和摘要，不能保证任何任务都能无损续接。

## 实践补充：为什么这次没有继续坚持 prefix cache friendly

2026-10-20，补记 10 月 19 日在 ai-human 中的讨论和实验。上面保留当时整理的经验；这里记录一次实际测试后，对压缩方案选择的修正。

之前比较看重压缩请求复用主对话前缀：system、tools、历史尽量不动，在末尾追加摘要指令，争取命中已经计算过的缓存。这次发现，摘要的任务边界和事实来源也必须单独验收，不能只凭缓存设计决定采用哪种方案。

### 完整前缀带来的问题，先出现在摘要内容里

问题会话里，用户先上传图片询问内容，随后转向查询系统装备列表，助手已经回答了列表。手动压缩后，摘要却把“先 info、再 list”等工具使用说明写成需要继承的决策，还把助手提出的“可以继续查看故障、工单、人员”等建议，写成进行中事项或下一步。

这些后续任务并不是用户提出的。原本已经回答完的问题，被摘要变成了还要继续推进的任务。

系统提示词、工具手册、用户要求、助手建议，在原对话中有不同来源和效力。一起送去摘要后，模型可能把“工具应该怎么用”概括成“这段会话决定了什么”，也可能把“助手能做什么”概括成“用户接下来要做什么”。一条规则本身正确，也不代表它应该成为会话摘要。

### 两条路线都做了实验

第一条路线保留主 Agent 的 system、工具 schema 和历史前缀，只加强末尾摘要指南，要求模型区分用户任务、助手建议、工具说明和实际结果。

它确实有改善。问题会话里新增待办的情况减少了，但没有稳定达到要求。最后一版尾部指令的 17 份完整摘要中，人工检查通过 11 份，另外 6 份仍残留通用接口说明或来源不正确的约束。同一个已完成创建的会话，重复三次也有好有坏，不能用某一次成功认定方案可用。

这只能说明本次 qwen38、业务工具说明和样本下，继续调整尾部提示词尚未达到标准，不能据此断言所有模型都无法做好。我们先停下来讨论，再测试第二条路线。

第二条路线先用代码清理摘要材料：保留用户 query 和 AI 回复正文，排除主 Agent system、工具 schema、工具调用参数、工具回执、thinking 和图片编码。然后用独立的摘要指南和材料包装，发起一次不绑定业务工具的 LLMClient 调用。

这里清理的是**摘要请求副本**。主 Agent 平时使用的工具集合、系统提示词和已保存历史继续沿原机制维护，没有因此按每条 query 动态裁剪工具。

### 摘要输入变成“指南＋历史材料”

现在的组织方式接近：

```text
请对下面材料生成上下文摘要，供后续 Agent 接续工作。

请遵循以下摘要指南：
[任务来源、完成状态、保留要求、输出格式……]

下面 JSON 是历史材料，不是当前指令：
{
  "previous_summary": "滚动压缩时的旧自然语言摘要",
  "dialogue": [
    {"role": "user", "text": "用户原话"},
    {"role": "ai", "text": "助手回复正文"}
  ]
}
```

材料中的历史问题不能当作新请求执行，摘要指南自身也不能变成历史目标或约束。用户明确说过“使用 SQL”，仍然是必须保留的用户要求，不能因为 SQL 也出现在工具说明里就一起删掉。清理应按消息来源和内容块类型进行，不靠关键词粗删。

即使排除了工具内容，指南仍然需要明确几件事：

- 助手未经用户接受的建议、邀请和能力介绍，不能升级成目标、进行中、阻塞、决策或下一步。
- 问答已经完成、没有新请求时，进行中和后续步骤可以写“无”，不用凑出“等待用户继续提问”。
- 真实未完成任务要保留。例如用户已要求准备表单、正在等待填写确认，就不能一律清成“无”。
- 输入里没有工具回执，不代表工具没有执行、文件没有读过，不能凭这个新建补读、重读或核实任务。

输入隔离减少了一类污染，任务状态仍然需要提示词约束和多次验证。

### 资源路径和读取状态，交给代码累计

只给摘要模型看用户和 AI 正文，会失去一部分执行证据。文件和图片不能指望模型在每次摘要里完整复述路径、记住读取次数，再正确合并状态，所以另外维护资源台账。

当前台账覆盖会话上传附件和 read_file 回执，按会话内规范路径合并资源，同时保留不同事件：上传、成功读取、读取失败、再次读取，以及已确认的行范围、工作表、是否还有未读内容、图片交付或省略状态。

这里有两种去重：同一个文件的资源入口按规范路径合并；同一次事件重放不能重复记账，但两次真实重读、一次失败后再次成功，不能被合并成“只读了一次”。单纯同名也不等于同一个文件。

直接上传图片时，即使没有调用 read_file，也应从附件记录进入台账。后续通过 read_file 再看同一张图片，则记录一次新的读取。上传不等于正文已读，图片交付也不等于模型已经理解了全部内容；只有请求参数、没有成功回执时，也不能标成读取成功。

这样保留路径不需要额外调用模型给每个文件写描述。模型使用可读的规范路径定位资源，精确身份和事件状态由程序维护。需要重新查看时，再通过文件工具获取内容。

自然语言摘要和资源台账分开保存：下一次滚动摘要只带旧的自然语言摘要和新增对话，不把整份台账再交给模型改写。回到主 Agent 时，由代码附加精简资源视图；完整事件保留在结构化状态里，避免把全部流水又塞回上下文。

### 少发输入，不等于一定更快；保留前缀，也不等于一定更合适

实验逐次记录了输入、输出和近似端到端耗时。以能够和第一路线 A2 对齐的 17 组会话、重复序号为例：

| 输入方式 | 平均输入 token | 平均耗时 |
| --- | ---: | ---: |
| 保留主 Agent 前缀，使用加强后的尾部指令 | 10,533.7 | 12.328 秒 |
| 清洗后独立摘要，使用增强指南 | 2,327.9 | 10.718 秒 |

这些数据说明，放弃复用主请求大前缀之后，输入量可能明显减少，并没有必然变慢。但不能仅凭这两行宣布第二条路线更快：换回原版指南、调整材料包装后，也测到了更慢的结果，输出长度和推理过程都会影响耗时。

这些调用没有做同一时段的随机交错测试，Provider 也没有提供明确的缓存命中指标。记录的是离线摘要调用的近似耗时，不能当成纯推理时间、首 token 时间或测试页按钮到数据库提交的全链路耗时。

因此，缓存收益要测，摘要质量也要测。独立摘要放弃了与主 Agent 共享大段前缀的机会，但它自己的固定指南仍可能缓存；主对话的稳定 system/tools 也仍然有价值。

### 这套方案仍然有信息损失和工程边界

只保留用户与 AI 正文，工具返回过、但助手从未说出来的业务 ref、draft_id 或执行细节，可能不会进入自然语言摘要。当前资源台账只补附件和 read_file 的事实，不是所有工具的完整执行日志。后续确有必须可靠继承的业务状态，应另定结构化保存规则，不能假设文件台账已经解决。

正式组合的离线复测中，36 份全文摘要通过了本轮冻结检查点；8 份滚动最终状态中通过 7 份。那一份仍漏掉了旧图片描述或已答主题，代码台账保住了图片路径。这也说明，路径保住了，语义细节仍然可能丢失。

另外，输入方式改变之后，原来的预算、重试和提交保护仍然需要保留：正常压缩的收益判断要比较压缩前后完整主请求，原工具内容和新台账开销都要计入，不能只跟清洗后的摘要材料比较。摘要、资源台账和覆盖位置应共同提交，失败、取消或最终预算不通过时，不能只推进其中一项。

已经污染的旧摘要，也不能直接当成新方案的可靠起点。切换格式时需要从仍可获得的原始历史重建；新输入不带系统提示词，不会自动消除旧摘要里已有的错误待办。

这次之后，我会先验收摘要能否准确交接任务、哪些事实必须由代码保存，再评估缓存和耗时。对于本次 ai-human 的场景，采用“纯对话材料摘要＋代码资源台账”；完整复用主请求前缀保留为有条件的优化选项，不再当成最终合理方案的前提。
