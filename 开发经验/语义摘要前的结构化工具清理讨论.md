# 语义摘要前的结构化工具清理讨论

2026-10-21，记录讨论中形成的候选方案。尚未实现，也没有完成实验验证。相关的语义摘要实践见 [[上下文压缩经验]]。

## 为什么先清工具正文

上下文达到压力阈值，不一定要立刻把整段对话改写成摘要。可以先检查 token 构成，再决定回收什么。

例如历史中用户 query 与 AI 回复正文共 12k，工具结果共 32k，合计 44k。如果旧工具结果中有大量可以回收的正文，就可能先腾出足够空间，继续保留用户与 AI 的原始对话，减少语义重写造成的信息损失。

这里的数字只是说明思路。实际准入要计算包含 system、工具 schema、调用参数、历史和当前输入的完整请求，并预留输出空间；占位回执也有 token 开销。

## 方案成立的业务前提

这次讨论针对的业务 Agent，通常是“查询 → 回答 → 本阶段任务完成”。用户可能连续追问几轮，但较少跨越很长历史继续依赖某一次工具结果。任务阶段相对明确，历史信息的使用具有较强的近期性。

这不代表工具结果在回答结束后就没用了。近期追问仍需要原始结果，所以只把较旧结果列为候选，在真正出现上下文压力时才执行清理。

第一版不需要识别任务阶段，也不需要再调用一个 LLM 判断工具结果的重要程度。利用近期保护窗口和明确的例外规则即可；接受远期追问可能需要恢复证据的成本。这是基于业务使用习惯的取舍，不是无损保证，后续仍需用真实日志验证。

这种策略不应直接推广到所有 Agent。长期维护代码、持续推导或多步骤协作的 Agent，可能仍依赖很早以前的原始结果。

## 第一层：哪些结果有清理资格

满足压力触发条件后，扫描历史工具结果，按确定性规则排除：

- 当前 run 的工具结果：一律保护，不在 Agent 尚未完成回答时拿掉其依据。
- 最近 N 个用户轮次内的工具结果：一律保护，用于连续追问。
- 显式配置为不可清理的工具或必要状态：按例外规则保护，例如不能通过重执行恢复的关键写入回执。

剩余的旧工具正文进入候选集合，不再增加任务阶段分类器或复杂的语义依赖图。

**最近 N 轮按用户轮次计算，不是最近 N 条 message，也不是最近 N 次工具调用。** 一次用户请求可能产生多条 assistant/tool 消息，应作为同一轮保护。当前 run 独立保护，N 的具体计数边界在实现前固定。

“工具已经被模型看过”不等于“工具结果不再有价值”；窗口之外只代表允许按这套业务策略回收，不代表证明了它永远不会再被使用。

## 第二层：这次清理是否值得执行

需要分清三个参数：

| 参数 | 解决的问题 |
| --- | --- |
| 触发水位 | 什么时候开始上下文管理？ |
| 目标水位 | 这次处理后，希望回落到哪里？ |
| 最低净释放量 | 至少腾出多少 token，才值得改写历史前缀？ |

净释放量要扣掉替换后的短回执开销，不能把旧工具正文的 token 全算成收益。候选估算之后，还要用完整请求重新核算。

例如当前 44k、目标 30k、最低净释放量 8k，需要回收约 14k。这些数值均为示例，不是已确定的默认配置。

- 如果候选能净释放 24k，可以批量选择旧结果，回收到目标附近；不要求把所有候选清空。
- 如果候选只能净释放 4k，低于最低收益，就跳过单独的工具清理，进入语义摘要。
- 如果候选能净释放 10k，收益不小，但仍达不到本次目标，可以在同一次规划中结合语义摘要处理，不必先提交一次清理、再提交一次摘要。

触发水位和目标水位不是模型的物理窗口上限。当前输入是否可执行，仍由完整请求预算和输出预留决定；不能只看是否低于示例中的 44k。

## 处理顺序与执行位置

第一版优先放在新 run 的入口：上一轮已经结束，用户发来新 query，恢复历史后、正式送模前进行检查。平时不逐轮清理旧结果，只在压力达到阈值时处理。

候选流程：

```text
用户提交新 query
  → 计算完整请求预算
  → 未达到触发条件：保留当前视图，继续执行
  → 达到触发条件：收集旧工具结果
      → 排除当前 run、最近 N 个用户轮次、受保护工具
      → 计算净释放量和预计剩余 token
      → 收益足够且能达到目标：仅清理工具正文
      → 收益不足或剩余压力仍过高：进入语义摘要或联合处理
  → 校验消息结构、完整请求预算与实际收益
  → 提交本次上下文视图，开始执行
```

当前 run 自身产生超大回包时，仍需沿既有回包准入和压力收尾机制处理。保护当前 run 不等于允许超预算，也不要求这次讨论新增一套 run 内依赖分析或紧急压缩器。

## 工具正文具体怎么清理

优先讨论的是修改模型看到的 Context View：保留原来的调用结构，把旧 tool 消息正文替换成程序生成的短回执。用户 query 和 AI 正文保持原样。

例如一次成功的 RAG 调用可以替换为：

```text
执行状态：成功。
历史结果正文已从当前上下文移除，不代表空结果或未执行。
如果当前任务需要该证据，可使用原调用参数重新检索。
```

执行失败就保留真实失败状态，不能统一写成成功。调用与返回仍须按模型 API 的要求配对，不能物理删掉 tool 消息却留下悬空的调用。

原来的 tool_call 通常已经保留工具名和参数，例如 RAG 的 query，不一定需要在短回执里再复制一份。若后续语义摘要会覆盖调用记录，恢复入口则需要由代码另外保留。

“可重新调用”是按需恢复的提示，不是要求模型立即重查。创建、修改、删除等有副作用的操作，不能靠再次执行来恢复回执。

## 正文是否持久化，单独决定

清理模型可见正文与删除服务器原始记录，是两个独立决定。

| 选择 | 好处 | 成本与边界 |
| --- | --- | --- |
| 不额外保留正文，保留调用参数 | 实现直接，不需要新的结果读取工具 | 需要时重新查询，承担耗时、费用及结果变化；原始正文若彻底删除就无法精确恢复 |
| 沿用已有原始历史，只清送模视图 | 不破坏已有真源，方便审计和后续设计恢复 | 数据库里有结果，不代表 Agent 已有主动读取它的能力 |
| 短期保存结果快照，提供恢复引用 | 避免再次调用 RAG 等服务，可以取回当时结果 | 要增加存储、过期管理、权限校验与实际读取入口 |

第一版可以先采用“只清模型视图、原始历史沿用既有保存方式”的最小改动；不必把 result_ref、TTL 或新读取工具作为实现前提。是否真正提供主动找回、何时过期或物理删除，仍是待确定项。

如果后续支持重取，需要区分：**重新执行查询拿到当前结果，与读取旧结果快照不是同一件事。** 业务数据、RAG 索引或文件版本可能变化。要求“继续分析当时那批对象”时，不能擅自用新查询扩大或替换原来的对象集合。

## 如何接受低频远期追问

最近 N 轮内的追问由完整工具结果保护。对于很久之后突然回到旧任务的情况，允许承担一定的恢复成本，不为它默认建立复杂的历史依赖保护系统。

恢复方式取决于最终选择的存储策略：读取旧快照、按原参数重新查询，或在缺少必要条件时向用户确认。无法恢复时应明确说明，不能仅凭旧 AI 回答补造原始细节。

这里保留的是业务上的取舍：常见近期追问优先保护，低频远期追问允许额外恢复；不是认定远期追问不会发生。

## Prefix cache 与实验

工具清理仍会改变请求前缀，通常影响从首个改动位置开始的缓存复用。不能因为没有调用摘要模型，就直接认定整条链路更快。

应集中在压力节点批量处理，避免每轮零散修改历史；最低净释放量就是控制收益的一道门槛。最终仍要测清理后的正常推理和后续重取成本。

可以先对真实日志统计完整请求的构成、保护窗口内外的工具 token，以及扣除短回执后的净释放空间，再对比：

- 现有语义摘要策略。
- 优先工具清理，收益不足再语义摘要。
- 在预算允许的样本内，保留原始上下文作为对照。

重点测试 N=3、N=5 等保护窗口对清理收益与近期追问的影响。记录完整请求 token、摘要耗时、下一次正常回复耗时和 TTFT、可获取的缓存指标、额外查询次数、任务与追问成功率。超过预算时不能把“完全不处理”当作可执行对照。

## 当前形成的方向与待定项

方向已经明确：**压力触发 → 按用户轮次保护近期工具结果 → 计算清理资格和净收益 → 优先结构化清理 → 不足再语义摘要。** 按 Agent 的业务特点启用，不做全局统一策略；第一版不引入语义重要性判断或阶段分类器。

后续需要确定：保护窗口 N、触发/目标水位、最低净释放量、受保护工具，以及原始正文的保留期限和远期追问恢复方式。先落讨论，不在这次笔记整理中修改 Runtime、启动实验或把候选参数写成已验证配置。
