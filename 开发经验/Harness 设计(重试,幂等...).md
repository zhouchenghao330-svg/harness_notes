# Harness 设计：重试、幂等与安全写入

## 先记住的判断规则

只要工具会改变外部状态，设计之前先问三个问题：

1. **同一请求执行两次会怎样？**  
   可能因为模型再次调用、运行时重试、网络超时后重发，或者用户重复提交。先判断重复执行会不会造成重复追加、重复创建、重复发送等结果。
2. **读取之后、写入之前，状态变了会怎样？**  
   模型可能根据旧文件或旧业务数据做决定。写入时要确认所依据的版本仍然有效，否则应返回冲突并重新读取。
3. **执行到一半失败会怎样？**  
   要分清哪些步骤已经成功，哪些尚未发生；设计原子写入、事务，或可检查、可恢复的流程。

再补一句：**调用方看到超时或报错，不代表操作没有生效。** 遇到结果不明的写入，先确认实际状态，再决定是否重试。

这些是设计问题，不意味着每个工具都需要同一套复杂机制。先弄清操作的副作用和失败后果，再选择相称的保护措施。

## 为什么模型生成内容与工具写入不同

在一种常见的写作流程里，模型产出候选内容，框架检查后再提交：

    模型提出内容 → 框架校验 → 框架写入

模型多生成一次，通常只是多了一个候选结果。真正的副作用发生在框架提交时；因此提交步骤仍然要处理并发、失败和重复请求。

有副作用的工具把提交入口暴露得更近：

    模型请求 write_file → Runtime 执行 → 磁盘状态变化

模型可以提出要做什么，但是否允许提交、如何提交、提交后怎样确认，应由 Runtime 和目标系统决定。

## 问题一：成功了，但调用方不知道

以追加一行文本为例：

    1. 工具将一行写进文件。
    2. 返回结果之前，进程断开或响应丢失。
    3. 模型只看到超时，无法判断第 1 步是否成功。
    4. 直接重试，可能把同一行追加两次。

这叫**结果不明**。它和明确的失败不同：如果在执行前就被拒绝，通常可以修正后再试；如果请求已经发出、结果没有返回，就要先查实际状态。

常见处理办法：

- **检查结果**：读取目标状态，确认预期修改是否已经出现。
- **幂等请求**：给一次逻辑操作分配固定的请求 ID。相同 ID 再次到达时，返回第一次的结果，不再执行副作用。目标系统必须支持识别或持久记录这个 ID。
- **谨慎重试**：只有确定尚未生效，或确定重复执行安全时，才自动重试。对发邮件、付款、追加内容、执行任意 shell 命令等操作尤其重要。

“幂等”指同一个逻辑请求重复执行，最终效果与执行一次相同。例如“把文件内容设置为指定字节”在目标内容层面通常比“向文件追加一段内容”更容易做到幂等。不过覆盖文件仍可能有并发覆盖、触发器或其他附带副作用，不能仅凭函数名判断安全。

## 问题二：读到的状态已经过期

典型时间线：

    1. 模型读到文件版本 A。
    2. 模型依据 A 生成修改方案。
    3. 另一个进程或用户把文件改成版本 B。
    4. 工具直接写入，覆盖了 B 的改动。

解决思路是**条件写入**：读取时记录版本号或内容 hash；提交时再次核对。只有当前版本仍与读取时一致，才允许写入。若不一致，返回冲突，让调用方重新读取并决定如何处理。

这里的 hash / 版本校验解决的是**过期读取和并发修改**；请求 ID 解决的是**同一操作重复执行**。两者不能互相替代。校验和写入本身也需要在合适的边界内完成，否则“校验通过”和“真正写入”之间仍可能发生竞争。

## 问题三：写到一半进程挂了

如果直接覆盖文件，进程中断可能留下不完整内容。单文件场景常见做法是先写临时文件，写完整并校验后，再用原子替换把它放到目标位置。涉及多个数据库记录时，通常需要事务；跨多个外部系统时，则要记录进度，并设计查询、补偿或人工处理方式。

这里还要分开看两件事：

- **原子性**：失败时是否会留下“写了一半”的状态。
- **持久性与恢复**：工具报告成功后，状态是否可靠保存；进程重启后能否确认之前做到了哪一步。

单文件替换、数据库事务、发邮件与执行 shell 命令的能力边界不同，不能用同一种办法覆盖所有工具。

## 设计一个写工具时的实用顺序

1. **定义操作语义**：是覆盖、追加、创建、删除，还是发送？重复一次的具体后果是什么？
2. **定义提交前提**：依据的是哪个版本？权限、参数和目标状态要怎样校验？
3. **定义结果**：区分“确定成功”“确定失败”“结果不明”“版本冲突”，不要把它们都压成一个失败。
4. **定义重试规则**：哪些错误可以直接重试？哪些必须先查状态？是否有请求 ID 或目标侧去重能力？
5. **定义中断恢复**：每个可能中断的步骤之后，如何确认已完成的部分，以及如何继续或处理残留状态？
6. **提交后验证**：检查最终状态是否符合预期，再把准确结果返回给模型。

最值得反复追问的两个故障注入问题：

> 如果这一行已经执行成功，但下一行之前进程挂了，会怎样？  
> 如果这次其实成功了，但调用方以为失败又执行一次，会怎样？

它们能很快暴露重试、幂等、原子性和恢复方面的缺口。

## 一句话总结

**模型负责提出修改意图；Runtime 负责在当前状态下安全提交，并在结果不明时查证和恢复。**

## Harness 工程稳定性与可靠性审查规范（扩展）

补充日期：2026-10-21。

### 一、定位与核心原则

本文用于指导 AI Agent / Harness / Runtime 系统在新增功能、修改执行链路、调整工具协议、变更持久化逻辑后，开展针对性的工程稳定性审查。

**目标不是消除所有理论风险，而是在合理成本下识别和控制真实工程风险。**

本规范属于横切关注点（Cross-cutting Concerns），涵盖执行、状态、上下文、流式协议、权限、性能、恢复等方面。

#### 1.1 基本原则

1. **按风险选择保障措施**：不同业务、不同操作具有不同失败后果，不能统一采用最复杂的机制。
2. **优先确定性保障**：能通过唯一约束、版本校验、原子操作、类型校验解决的问题，不应主要依赖 LLM 判断。
3. **区分事实与推断**：模型认为操作成功，不代表操作实际成功。应以 Runtime 和目标系统的可验证状态为准。
4. **优先复用现有基础设施**：不因新功能轻易引入新的队列、状态机、数据库表或调度系统。
5. **明确恢复边界**：不是所有操作都能自动重试或回滚。需要明确哪些状态可恢复，哪些需要重新执行或人工介入。
6. **保护现有契约**：新功能不能无意破坏已有工具协议、消息结构、事件语义、持久化兼容性。
7. **优化应当可测量**：稳定性保障自身也有成本，需关注延迟、Token、缓存、复杂度和新增故障面。

#### 1.2 审查时必须区分四种结论

- **已有保障**：现有代码已经处理，不重复建设。
- **需要补充**：存在实际风险且当前保障不足。
- **风险可接受**：存在理论风险，但发生概率、影响程度与处理成本不成比例。
- **当前不适用**：该功能不存在对应操作或执行条件。

审查者不能把所有理论风险都视为必须修复的问题。

### 二、执行生命周期与中断恢复

#### 核心问题

**Worker 或 Runtime 在任意位置中断，系统会进入什么状态？再次执行是否安全？**

#### 审查要点

**执行状态**

- Run 是否有明确的开始、运行、等待、成功、失败、取消等状态？
- 状态转换是否合法？是否可能从终态重新回到运行态？
- 是否可能产生多个互相矛盾的终态？
- 任务状态与数据库记录、队列状态之间是否保持一致？

**Worker 生命周期**

- Worker 执行前崩溃，任务是否丢失？
- 执行过程中崩溃，是否能够识别未完成的 Run？
- 数据库提交成功，但队列 ACK 失败，是否可能重复执行？
- 多个 Worker 是否可能同时领取同一个任务？
- 如果使用租约，过期 Worker 是否仍可能继续提交结果？
- 是否需要运行所有权检查、Lease 或 Fencing Token？

**恢复行为**

- 是否支持从明确的 Checkpoint 或持久化状态恢复？
- 恢复时会不会重复调用已经成功的副作用工具？
- 是否会重放已经完成的模型输出或工具事件？
- 恢复行为是否与普通执行使用相同的状态校验规则？

#### 重要区分

- **事件恢复**：已经发生的事件可以重新获取。
- **执行恢复**：未完成的任务可以重新调度。
- **副作用恢复**：外部操作状态可以被确认，避免重复执行。

三者并不等价。

#### 典型故障注入

- Worker 领取任务后立即崩溃。
- 工具执行成功，但结果尚未持久化时崩溃。
- 状态持久化成功，但队列确认之前崩溃。
- Worker 租约过期后，旧 Worker 继续提交结果。

#### 设计取舍

短时间、无副作用的 Run 可以接受失败后重新执行；长时间或具有外部副作用的 Run，则可能需要更严格的持久化与恢复机制。

不要仅为理论上的 Worker 崩溃风险引入复杂分布式调度系统。

### 三、工具调用与协议契约

#### 核心问题

**模型提出的工具调用，能否被 Runtime 安全、正确、可预测地执行？**

#### 审查要点

**参数与执行边界**

- 参数是否有明确 Schema？
- 是否存在仅依赖 Prompt、但 Runtime 未强制执行的约束？
- 工具参数校验失败时，是否返回清晰、可修正的错误？
- 是否可能出现伪工具调用、非法工具名或格式不完整的调用？
- 工具是否拥有超出当前任务需要的权限？

**返回结果**

- 成功、业务失败、系统异常、超时、取消是否区分？
- 工具返回的部分成功是否被误报为完全成功？
- 大型工具结果是否需要分页、截断或外部引用？
- 结果中的文件、图片、资源 ID 是否具有明确生命周期？
- 工具返回结构发生变化，是否会破坏上层 Agent 的处理逻辑？

**工具调用历史**

- Tool Call 与 Tool Result 是否保持合法配对？
- 调用 ID 是否稳定且唯一？
- 工具结果被裁剪、重放或摘要后，协议结构是否仍然合法？
- 工具调用失败后，模型能否获得足够的信息修正下一次调用？

#### 特别关注

工具执行是否成功，应以实际工具结果为准，不能只依据模型的自然语言解释。

对于重要写操作，工具结果应该具有明确、可机器判断的状态，而不只是一个模糊的文本字符串。

### 四、上下文管理与历史一致性

#### 核心问题

**对模型可见历史进行修改时，是否会破坏执行依赖、消息语义或持久化状态？**

#### 审查要点

**上下文构建**

- 模型可见 Context 与持久化原始消息是否明确区分？
- 历史清理、压缩是否会意外修改原始数据？
- Context 的构建是否具有可重复、可验证的输入输出？
- 不同业务模块是否可能错误复用同一套上下文规则？

**语义压缩**

- 摘要是否正确区分用户意图、系统指令、工具返回和 Agent 内部计划？
- 是否可能把工具结果中的内容提升为用户指令？
- 压缩是否会丢失当前 Run 依赖的信息？
- 压缩失败时，旧 Context 是否仍然可用？
- 新摘要是否只有在验证成功后才提交？
- 历史摘要与后续消息是否可能出现重复或缺失？

**工具结果回收**

- 最近若干轮的工具结果是否受到保护？
- 当前正在执行的 Run 是否受到保护？
- 工具结果清理后，Tool Call / Tool Result 结构是否完整？
- 工具引用、RAG 去重引用、图片或文件资源引用是否可能悬空？
- 原始工具结果是否仍可恢复？若可以，恢复的是历史快照还是重新查询的当前数据？
- GC 清理标记是否与消息身份、调用身份和原文版本关联？
- 语义摘要覆盖旧历史之后，原 GC 标记如何处理？
- 功能开关关闭后，已持久化的清理状态如何解释？

**提交一致性**

- 是否先构造候选 Context，再检查最终模型输入？
- 候选校验失败、取消或准入拒绝时，是否可能提前推进压缩游标？
- 摘要与 GC 是否可能产生互相矛盾的历史视图？

#### 性能考虑

- 是否需要执行本次压缩？
- 是否可以先释放可回收工具结果？
- 清理会破坏多少可复用的 Prefix Cache？
- 压缩本身的成本是否高于实际收益？

#### 重要原则

**历史真源与模型可见视图应尽可能分离。**

清理 Context 不一定意味着物理删除历史信息。

但必须明确持久化数据的保留期限、安全边界和恢复语义。

### 五、流式输出与事件一致性

#### 核心问题

**网络断开、重连、事件重复、乱序或取消时，前后端看到的 Run 状态是否一致？**

#### 审查要点

**事件生成**

- 每个 Run 内事件是否具有稳定顺序？
- 事件序号是否单调递增？
- 事件持久化与实时推送是否存在丢失窗口？
- 事件发布失败时，能否通过持久化记录补齐？
- 是否可能产生多个终态事件？

**断线恢复**

- 客户端重连时能否从最后确认的事件序号继续？
- 重复事件是否会造成内容重复追加？
- 发现序号跳跃时，是否会补拉缺失事件？
- Redis 或消息通知丢失后，客户端是否仍能恢复？
- 重连之后是否能获得准确的最终 Run 状态？

**输出完整性**

- 模型输出中途断开，是否被误认为完整回答？
- Tool Call 参数只输出一半时，是否可能被错误执行？
- 是否区分模型自然结束、工具失败、用户取消、服务异常？
- 前端展示完成状态的依据是什么？

**取消**

- `/stop` 被接受是否等同于实际执行已经停止？
- 取消与成功几乎同时发生时，以哪个权威状态为准？
- 取消是否会错误回滚已经成功的外部副作用？
- 取消后是否还可能有晚到事件？客户端如何处理？

#### 典型故障注入

- SSE 连接在事件持久化之后、发送之前断开。
- 同一事件被发送两次。
- 客户端从旧序号重新订阅。
- 用户取消时工具刚好执行成功。
- 终态已经持久化，但最终 SSE 事件未送达。

#### 重要原则

**事件流属于可恢复的状态观察通道，不应成为唯一的执行状态真源。**

### 六、多用户、多会话与数据隔离

#### 核心问题

**一个用户或会话的操作，是否可能读取、覆盖或影响另一个用户或会话的数据？**

#### 审查要点

**身份与归属**

- `user_id`、`conversation_id`、`run_id`、`message_id` 的身份和归属关系是否明确？
- 数据库读取和写入是否具有必要的所有权约束？
- 全局 ID 与会话内 ID 是否被混用？
- UPSERT 是否可能因为主键冲突更新其他会话的数据？
- 更新操作是否检查预期影响行数？

**资源隔离**

- 文件、文档、RAG 资源、工具结果是否校验所属用户及授权范围？
- 单凭资源 ID 是否可能越权读取？
- 缓存 Key 是否包含必要的用户、租户或业务命名空间？
- 不同业务模块是否可能共享不该共享的可变状态？
- 后台 Worker 是否正确继承并验证任务的授权上下文？

**副作用**

- 某用户的取消是否可能影响其他用户的 Run？
- 删除、修改资源时是否重复校验归属？
- 是否可能通过日志、错误信息、模型上下文暴露其他用户的数据？

#### 典型故障注入

- 两个会话使用相同的消息 ID。
- 用户 A 尝试访问用户 B 的文件 ID。
- 相同资源标识存在于不同业务命名空间。
- 跨会话主键冲突触发 UPSERT。
- 一个批量事务的中间步骤遭遇归属校验失败。

#### 重要原则

**身份隔离不能只在 API 入口校验一次。**

重要的持久化与资源访问边界同样需要可靠的所有权限制。

### 七、并发控制与状态竞争

#### 核心问题

**多个执行单元同时操作同一份状态，是否会产生丢失更新、重复提交或状态覆盖？**

#### 审查要点

**并发 Run**

- 同一会话是否允许多个 Run 同时执行？
- 如果不允许，限制在哪里强制执行？
- 如果允许，消息顺序和会话状态如何合并？
- 一个 Run 能否覆盖另一个 Run 更新过的上下文状态？

**资源写入**

- 两个 Agent 是否可能同时修改同一个文件或文档？
- 修改是否基于明确版本？
- 版本校验与写入是否在可靠的原子边界中完成？
- 写入冲突时返回什么错误？
- Agent 是否知道需要重新读取或重新规划？

**共享状态**

- 是否存在多个请求共用的可变对象？
- 工具注册表、业务配置、上下文管理器是否可能被单个 Run 意外修改？
- 缓存更新是否可能覆盖较新的状态？

**确认式操作**

- Proposal 生成后，资源可能已经发生变化，确认应用时是否再次检查版本？
- 同一个 Proposal 是否可能被重复应用？
- 权限是否在真正提交时重新校验？
- 过期或已经取消的 Proposal 是否可能继续提交？

#### 重要区分

- **幂等性**解决同一逻辑请求重复执行的问题。
- **并发控制**解决不同操作同时修改状态的问题。
- **原子性**解决一个操作执行到一半的问题。

三者不能互相替代。

#### 典型故障注入

- 两个 Run 同时读取版本 A，并尝试写入不同结果。
- Proposal 确认之前文档被其他用户修改。
- 旧 Worker 在新 Worker 接管后继续写入。
- 同一个确认请求连续发送两次。

---

### 八、失败语义、重试与恢复决策

#### 核心问题

**失败被准确识别了吗？系统是否知道下一步应该重试、查询状态、恢复还是终止？**

#### 8.1 建议区分的执行结果

| 结果类型 | 含义 | 一般处理 |
| --- | --- | --- |
| 确定成功 | 已验证操作完成 | 正常继续 |
| 确定失败 | 已确认操作未完成 | 根据错误类型修正或重试 |
| 暂时性失败 | 可重试的服务异常 | 有界重试 |
| 结果不明 | 请求可能已经生效 | 先确认真实状态 |
| 版本冲突 | 操作依据的状态已过期 | 重新读取或重新规划 |
| 部分成功 | 部分步骤已产生效果 | 记录进度并恢复或补偿 |
| 已取消 | 执行收到取消并到达相应终态 | 确认已发生的副作用 |

#### 审查要点

- 是否把所有异常都压缩成通用 `ERROR`？
- 是否区分工具超时与工具执行失败？
- 重试是否存在次数、时间和成本上限？
- 重试是否具备退避机制？
- Runtime 自动重试与模型自主重试是否可能叠加？
- 结果不明的写入是否会被无条件再次执行？
- 业务错误是否会被误判为基础设施异常？
- 是否存在无限重试或 Agent 死循环？
- 失败后是否保留足够的诊断与恢复信息？

#### 重要原则

**不是所有失败都应该自动重试。**

尤其是具有副作用的操作，应优先确定操作是否已经生效。

详细的幂等性、条件写入和原子提交原则沿用原文《Harness 设计：重试、幂等与安全写入》。

工具内部与主 Agent 的失败处理、恢复决策、重试责任、回执和故障注入，另见 [[开发经验/工具失败处理：错误分类、执行决策与恢复|工具失败处理：错误分类、执行决策与恢复]]。

### 九、安全边界与工具权限

#### 核心问题

**模型、外部内容或工具结果是否可能绕过 Runtime 的权限与执行约束？**

#### 审查要点

**权限控制**

- 是否由可信代码决定可用工具及其实际权限？
- 是否存在仅通过 Prompt 限制危险操作的设计？
- 文件访问是否限制允许的路径和资源范围？
- SQL 是否在执行层强制限制可访问对象和操作类型？
- 工具参数是否有服务器侧验证？

**不可信内容**

- RAG 文档、网页、数据库字段和工具结果是否被当成低信任数据？
- 外部文本是否可能冒充系统指令？
- 上下文摘要是否会错误提升外部内容的指令权威性？
- 工具返回的路径、URL、资源 ID 是否经过验证？

**敏感操作**

- 哪些工具具有不可逆副作用？
- 哪些操作需要用户确认或独立审查？
- 审查通过后，最终执行参数是否仍然与被审查的操作一致？
- 模型审查是否被错误当成唯一的安全边界？

**数据保护**

- 日志和执行轨迹是否可能包含敏感业务数据？
- 外部模型调用是否符合数据访问要求？
- 错误信息是否泄露文件路径、身份信息或内部凭据？

#### 重要原则

**模型可以参与安全决策，但确定性的权限边界必须由可信执行层强制保障。**

---

### 十、持久化状态与协议演进

#### 核心问题

**新版本上线、回滚或重启之后，是否仍然能够正确理解旧版本保存的状态？**

#### 审查要点

- 新增字段是否存在兼容的默认行为？
- 旧数据缺少新字段时是否能够正常读取？
- 序列化格式变化是否需要显式版本号？
- 历史 Checkpoint、Context、Tool Result 是否仍然可加载？
- 版本不兼容时是明确拒绝，还是静默使用错误数据？
- 功能开关关闭后，已产生的持久化状态如何处理？
- 回滚旧版本是否可能重新解释或错误恢复旧数据？
- 摘要、GC 或执行恢复的游标是否具有正确生命周期？
- 多条相关状态是否需要在同一事务中提交？
- 数据库迁移过程中是否可能出现新旧代码同时访问的情况？

#### 特别关注

功能开关通常只能控制**新行为是否执行**，不能天然保证已产生的历史状态被撤销。

需要明确区分：

- 关闭新功能
- 停止产生新状态
- 继续读取已有状态
- 回滚已有状态

这些行为不能默认等价。

### 十一、性能、Token 与资源成本

#### 核心问题

**新的稳定性设计是否引入了不必要的模型调用、上下文开销或系统瓶颈？**

#### 审查要点

**LLM 开销**

- 是否增加额外模型调用？
- 是否可以使用确定性代码代替模型决策？
- 新增指令是否每轮都被注入？
- 是否扩大系统提示词和长期固定上下文？
- 是否导致更多无意义的工具调用？

**上下文与缓存**

- 是否改变稳定前缀的位置？
- 是否破坏 Prefix Cache？
- 是否频繁重写完整历史？
- 是否产生过度频繁的压缩或整理？
- 是否能通过大型工具结果卸载降低 Context Pressure？

**执行性能**

- 是否新增不必要的数据库读取？
- 是否把可以并行处理的独立任务串行化？
- 是否引入耗时的同步审查？
- 是否在主请求路径加入复杂的状态扫描？
- 大量历史消息、工具事件或文件块是否会造成非线性性能退化？

**资源边界**

- 是否有最大上下文预算？
- 是否有最大工具返回大小？
- 是否有执行时间、重试次数、并发数和资源使用上限？
- 队列堆积时是否有合理的背压或拒绝策略？

#### 建议观测指标

- TTFT
- 完整 Run 耗时（P50 / P95）
- Prefill Token 和缓存命中 Token
- 单次任务模型调用次数
- 工具调用次数及重试次数
- 上下文压缩与 GC 的频率和净收益
- 任务成功率与执行成本

#### 重要原则

**性能优化不能只比较 Token 数量，应结合模型部署环境和端到端任务效果评估。**

对于本地部署模型，Prefix Cache、Prefill、TTFT 等因素可能影响实际最优策略。

### 十二、可观测性与故障定位

#### 核心问题

**功能出错时，能否根据现有记录还原发生了什么，而不是依赖猜测？**

#### 审查要点

**追踪身份**

- 是否可以通过 `run_id` 定位完整执行？
- 工具调用是否有稳定的 `tool_call_id`？
- 重试是否能区分逻辑请求 ID 和具体执行尝试 ID？
- 事件、状态、工具调用之间能否建立关联？
- 是否能追踪关键资源的版本变化？

**状态变化**

- 是否记录重要状态转换及失败原因？
- 是否能判断错误发生在模型调用、工具执行、持久化还是事件发送阶段？
- 是否记录 GC、摘要、恢复、重试等重要管理操作的触发原因？
- 是否能区分正常拒绝、业务冲突和系统异常？

**诊断能力**

- 异常日志是否保留必要的上下文和调用链？
- 是否需要记录内容 Hash、版本号和资源引用，而不是完整敏感正文？
- 是否能够识别工具循环、连续失败和长时间无进展？
- 是否能查看某一次优化实际释放了多少 Token 或增加了多少延迟？

#### 重要原则

日志和 Trace 应服务于实际故障定位，而不是无差别记录所有内容。

优先收集具有明确诊断用途、成本可控且符合数据安全要求的指标。

### 十三、测试、契约验证与故障注入

#### 核心问题

**当前测试只是证明正常路径能运行，还是也验证了关键失败路径不会破坏系统？**

#### 测试分层

**单元测试**

验证条件判断、状态转换、参数校验、Token 计算、消息配对、版本检查等确定性逻辑。

**契约测试**

验证工具输入输出、模型消息协议、SSE 事件格式、业务扩展接口和持久化结构。

**集成测试**

验证真实数据库、队列、Worker、资源服务之间的行为，尤其是事务边界与状态重载。

**真实模型链路测试**

验证实际 Agent 能否正确使用功能，包括工具调用、任务结果、上下文变化和恢复行为。

**故障注入测试**

在关键状态变化前后制造中断、重复、超时、冲突和错误，检查系统是否符合预期。

#### 建议重点检查的故障窗口

1. 外部调用尚未发出之前。
2. 外部调用已经发出，但未收到结果。
3. 工具已成功，但结果尚未持久化。
4. 数据库提交成功，但响应尚未返回。
5. 事件持久化成功，但 SSE 尚未发送。
6. 新 Context 候选生成后，最终模型调用之前。
7. 用户取消与工具成功同时发生。
8. 两个执行单元同时写入同一个资源。
9. 服务重启后加载历史状态。
10. 功能开关关闭后重新读取已有状态。

并非每个功能都需要测试以上全部窗口。应根据功能实际经过的执行边界选择。

#### 测试数据安全

- 集成测试优先使用隔离数据库、用户、资源和会话。
- 复制历史消息时重新生成必要的身份标识。
- 不能通过破坏真实业务数据来证明隔离能力。
- 涉及数据库操作时，需要验证失败不会留下部分错误修改。
- 测试结束后应明确哪些资源被创建、修改和保留。

#### 重要原则

**测试不仅要证明操作成功，还应验证关键失败不会破坏系统不变量。**

### 十四、统一审查输出规范

在新增功能或者修改 Harness 核心链路之后，要求审查者结合实际代码进行检查。

#### 第一步：确定变更影响面

先识别当前变更涉及哪些模块，例如：

- Agent Loop / Worker
- Tool Execution
- Context Management
- Conversation Persistence
- SSE / Event Stream
- Document / File / Business Resource
- Authentication / Authorization
- Model Provider / Routing

只对实际涉及或存在明确间接影响的领域深入审查。

#### 第二步：追踪完整链路

不能只查看新增函数。

需要理解：

- 功能从哪里进入？
- 谁负责调用？
- 哪个模块持有状态真源？
- 哪些地方存在副作用？
- 哪个时刻提交状态？
- 失败时谁负责处理？
- 重启后从哪里恢复？
- 最终结果通过什么协议返回用户？

#### 第三步：按风险输出结论

每个发现的问题至少应提供：

| 字段 | 说明 |
| --- | --- |
| 风险描述 | 具体可能发生什么 |
| 触发条件 | 什么情况下会发生 |
| 实际影响 | 数据损坏、状态错误、任务失败或性能问题等 |
| 代码依据 | 涉及的文件、函数和执行路径 |
| 现有保障 | 目前代码已经处理了什么 |
| 建议措施 | 能够解决问题的最小改动 |
| 验证方式 | 如何证明问题存在以及改动有效 |
| 优先级 | P0 / P1 / P2 / 可接受 |

推荐的优先级原则：

- **P0**：可能导致越权、跨用户数据污染、严重数据损坏、不可接受的重复副作用。
- **P1**：能够在合理条件下导致任务失败、错误状态、不可恢复的执行异常。
- **P2**：低频边缘故障、可观测性不足、非关键性能问题或工程改进项。
- **可接受**：风险存在，但当前业务约束与成本评估支持暂不处理。

优先级应结合实际业务影响，不应只根据理论严重性判断。

#### 第四步：给出最小实现方案

对于需要修复的问题：

1. 优先使用现有代码和基础设施。
2. 尽可能不改变外部 API 与已有业务契约。
3. 说明增加了哪些状态和复杂度。
4. 明确是否产生新的恢复或兼容性负担。
5. 提供必要的测试和故障注入方案。

对不建议修复的风险，也应说明理由。

#### 第五步：验证并复审

功能修改完成后，检查：

- 原风险是否确实消除？
- 是否出现新的竞争条件或失败窗口？
- 是否破坏既有测试和协议？
- 是否有需要补充的回归测试？
- 是否引入明显的性能或 Token 成本？

### 十五、给 Codex 的可复用审查指令

每次新功能开发完成后，可以使用以下指令：

> 请阅读项目中的 Harness 稳定性设计文档，并结合本次功能变更和真实代码执行链路，开展一次有针对性的可靠性审查。
>
> 要求：
>
> 1. 先理解功能目标、业务约束、执行路径、状态真源及持久化方式。
> 2. 根据实际涉及的模块，选择适用的稳定性审查领域，不要机械套用所有检查项。
> 3. 不要假设现有代码缺少保障。先寻找已经实现的机制，避免重复设计。
> 4. 对每个风险，提供真实代码依据、触发条件、实际后果和建议的最小修复方案。
> 5. 区分必须修复、建议优化、风险可接受和不适用，不得将理论可能性一律认定为缺陷。
> 6. 特别审查中断、重试、并发、重复提交、持久化恢复和协议兼容等与本次功能直接相关的边界。
> 7. 对建议修改的部分，给出相应的单元测试、契约测试或故障注入方案。
> 8. 优先复用现有 Runtime、队列、数据库及错误处理能力，避免不必要的抽象或新基础设施。
> 9. 评估新增保障是否引入状态复杂度、额外模型调用、缓存损失或其他性能开销。
> 10. 先输出审查结论与建议方案，不要擅自进行大范围架构重构。

### 十六、最终设计原则

Harness 的工程可靠性，不是靠无限增加保护逻辑获得的。

真正重要的是：

- 知道系统在哪些边界可能失败。
- 知道失败之后哪些状态已经发生变化。
- 知道哪些操作可以安全重试。
- 知道哪些状态必须保护、验证或恢复。
- 知道哪些风险值得投入工程成本解决。
- 知道如何用测试证明保障措施确实有效。

**设计原则应随着真实工程问题持续演进，而不是为了追求理论上的完整性不断增加复杂度。**

这份规范应作为风险识别和设计复盘的参考，而不是强制要求所有功能具备所有机制的开发标准。
