# Text-to-SQL 上下文设计：清晰 Schema 与少量关键业务规则

> 做好 Text-to-SQL，不一定需要给模型灌输完整业务背景。对于边界明确的查询场景，清晰的表名、字段名和关系，加上少量消除歧义的业务规则，就可能构成高性价比的上下文。
>
> 目标是提高上下文的语义密度，而不是一味增加描述，也不是不计代价地压缩 Token。

记录来源：2026-09-15 对装备维保 Text-to-SQL Lab 的讨论、源码核对，以及 2026-09-09 的历史实验报告。

## 1. 这次最值得记住的发现

直觉上，业务系统复杂，就应该先让模型充分了解业务，补很多背景、流程、术语和字段解释。

但这次实验表明：很多查询只要求模型理解当前问题涉及的局部数据关系，并不要求它理解整个业务系统的运转过程。

例如，查询“当前谁手头还压着最多活”，不一定需要解释工单如何审批、如何派发、如何结算。只要模型知道人员、工单、人员与工单的关系，以及“未完成”的状态定义，就具备生成查询的必要信息。

因此，业务复杂度不应该直接转换成 Prompt 长度。

## 2. 简洁的 Schema，本身就是业务描述

下面这几行已经表达了一部分业务结构：

```text
person(id, name, ...)
workorder(id, name, status_code, ...)
workorder_person(workorder_id, person_id)

工单状态：0 新建，1 维修中，2 已完成。
未完成工单：status_code 为 0 或 1。
关联后统计工单，按 workorder.id 去重计数。
```

模型可以据此完成如下对应：

```text
“谁”       → person
“活”       → workorder
“手头”     → workorder_person 关联
“还压着”   → 未完成状态
“最多”     → 分组计数、降序、取第一
```

我们没有为每一种自然语言问法写转换模板。理解问法、选择关联、组合 SQL，仍然是模型完成的工作。

很多看起来复杂的业务查询，本质上是在组合筛选、JOIN、去重、分组、HAVING、排序和 Top-N。Schema 与关键口径明确后，模型可以调用已有的 SQL 能力，不必重新学习一套项目自定义查询语言。

清晰命名对人和模型都有帮助，关键不在于代码是否由 AI 编写，也不在于必须使用英文。像 `f001`、`sy_sm` 这样的名字需要可靠映射或解释；即使是 `remaining_life_value`，也仍然需要说明单位。

## 3. 我们并不是只把原始 DDL 删短了

原始业务系统主要用通用对象内核存储：

```text
object_type_meta：对象类型目录
object_resource：通用对象记录，专属业务字段存在 payload JSONB 中
link_object：通用对象关系
```

只看原始 DDL，模型只能知道存在 `payload`，不知道其中的字段和业务含义。Lab 用确定性代码把它展开为查询导向的语义结构：

| 原始存储 | 提供给模型的查询接口 |
|---|---|
| `type_code='equipment'` 的对象记录 | `equipment(...)` |
| 装备的 `payload->>'model'` | `equipment.model` |
| 装备的 `payload->>'status'`，转成整数 | `equipment.status_code` |
| 状态码映射中文 | `equipment.status_label` |
| `payload->>'remaining_life'`，校验并转成数值 | `equipment.remaining_life_value` |
| 工单与人员的通用关系记录，处理方向并去重 | `workorder_person(workorder_id, person_id)` |

真实 PostgreSQL Demo 使用固定 CTE，也就是查询中的临时命名视图。底层存储没有因此拆成几十张物理业务表。

模型只看简短的语义表说明，不看背后的固定展开 SQL。生成查询后，由后端把映射代码和模型 SQL 组合起来交给数据库执行。

```text
清晰的语义 Schema + 少量关键规则 + 当前问题
                    ↓
             模型生成 SQL
                    ↓
        后端映射、校验、数据库执行
```

这里的优化是重新组织接口、明确类型与关系、补足关键含义，不是单纯删除文字。

## 4. 哪些描述值得保留？

优先保留会改变查询结果、但无法从名字可靠推断的内容：

- 状态枚举：什么叫“未完成”“有效”“待审核”。
- 单位与时间：寿命是年还是小时；“本月”按哪个时间字段计算。
- 计数根：统计工单还是人员；多对多 JOIN 后如何去重。
- 关系范围：只算直接关联，还是包含经部件关联的故障。
- 空值与边界：未知寿命怎么处理；是否包含已超期对象；是否显示零计数组。
- 输出身份：对象结果保留 ID 和名称，不能只返回可能重名的文字。

与当前查询无关的业务历史、完整操作流程、重复解释，可以不进入这次模型上下文。

需要背景信息时再提供，而不是为了让模型“了解业务”预先堆叠所有文档。

## 5. 这次实验提供了什么证据？

### 历史 SQLite fixture 测试

2026-09-09，使用同一套 29 道标准题、语义 Schema 和提示词，全量 Schema、关闭思考：

| 指标 | qwen35 | qwen38 |
|---|---:|---:|
| 业务结果完整正确 | 28/29，96.6% | 29/29，100% |
| SQL 可执行率 | 100% | 100% |
| 平均单题耗时 | 0.63 秒 | 1.45 秒 |
| 平均输入 Token | 1590.3 | 1590.3 |
| 平均输出 Token | 65.9 | 69.6 |

`qwen35`、`qwen38` 是当时的服务标识；不把服务别名直接当成官方模型版本名。qwen35 在全量模式下那道未通过的题，主要是人员结果缺少身份 ID，而不是统计数值错误。

另外 8 道隐晦表达题，最终规则下两个模型的业务正确率都是 100%。这组题开启 medium 思考没有提升最终业务正确率，但增加了耗时。

29 道标准题改为渐进披露后，两个模型的平均输入都降到约 1052 Token，但平均耗时分别升至 1.17 秒、2.10 秒，业务正确率没有提高。多一次 Schema 选择调用，并不一定能用节省的输入换来更低延迟。

### 真实 PostgreSQL Demo 的上下文规模

2026-09-15 核对的 8765 Demo：

- 使用全量语义手册，没有先选 Schema 的步骤。
- 24 个可查询入口：13 个实体、9 个关系、2 个通用兜底入口。
- 174 个列项，其中大量是重复的身份列和通用字段。
- Schema 手册及规则共 3058 个字符，系统提示词另有 261 个字符。
- 当天一次查询“当前一共有多少装备？”的模型输入为 1134 Token。

这说明字段列表看起来不少，并不必然意味着很大的输入负担。

两类证据不能混淆：前者是固定测试数据上的准确性与单题延迟评估，后者是实际 Demo 的上下文统计和单次调用记录，不是完整真实业务准确率评测。正式聊天还可能包含外层 Agent 调用和结果总结，Token 不等于 Lab 内层调用的 Token。

## 6. 可以复用的做法，以及边界

可以优先尝试：

1. 确定当前业务域和实际查询范围，而不是默认暴露整个公司的所有业务。
2. 提供清晰的表名、字段、类型和必要关系。
3. 把底层 JSON 提取、类型转换和关系规范化放进确定性实现。
4. 仅为歧义点补业务规则，不以描述长度衡量上下文质量。
5. 在 Schema 可控时，建立“全量语义 Schema + 单次 SQL 生成”的基线。
6. 用真实失败决定是否补注释、增加示例、开启思考或做渐进披露，并测试补充后的效果。

不要把这次经验扩展成以下结论：

- 描述越少越好，或者字段名可以替代所有业务定义。
- 所有业务系统的对象和字段都不会多。物理表少，可能只是把大量业务结构藏进了 JSON。
- SQL 能执行、结果看起来合理，就等于口径正确。
- 不开思考一定最好，或者少量测试全部通过就证明可以覆盖任意复杂查询。
- 好的上下文可以替代权限隔离和 SQL 执行安全。

当前 Lab 的装备—故障关系只展开直接关联，而正式业务读取还考虑经部件或告警关联的故障。这类差异即使 SQL 成功执行，也可能造成漏数，必须通过业务口径对齐和测试发现。

本次没有做“只给名字”“名字加注释”“长篇业务描述”等完整消融对照，因此不能证明某种上下文在所有任务上最优，也不能精确量化每项设计的贡献。

## 7. 后续故障：图谱名称与 SQL 执行名称、修复校验的边界

2026-10-29 的装备图谱 SQL 会话暴露了两个相连的问题。图谱关系的内部 ID 是 `equipment_faults_all`，但本体的 `query_mapping.semantic_table` 指向可执行语义表 `equipment_fault`。映射已经送给模型；当时的上下文又同时出现两个名称，模型把内部 ID 用作 SQL 表名。第一版 SQL 因表名不在语义 Schema 中被正常拒绝。第二版尝试改用 `equipment_fault`，却被当时的 `validate_repair_scope` 认定为修复超出范围，仍无法执行。

这项旧校验只比较前后 SQL AST 中 `FROM`、`JOIN`、`WHERE`、`HAVING`、`LIMIT`、`OFFSET` 的结构签名；它不调用 LLM，也没有拿到用户问题、业务定义或生成时的 `reason`。因此，它能发现某些结构变化，却不能判断变化是否偏离用户意图。**第一次 SQL 可能本来就是错的，不能把它的表名或关联结构冻结成用户意图的真值。**反过来，仅改变 `SELECT` 中的 `COUNT(DISTINCT ...)` 为 `COUNT(...)` 等输出表达式，也不被这层比较完整覆盖，结构未变不等于业务口径未变。

本机已按这次决策实现：装备模块新增 SQL 送模渲染器，向模型展示实际可执行的表、列名称；图谱稳定 ID 留在内部检索与追踪，冻结本体和向量索引不改。多种概念共用的 `business_relation` 保留必选过滤，没有独立表的口径用中文说明和批准路径表达；不对模型生成的 SQL 偷做名称替换。生成结果保留简短 `reason`，用于说明口径和能力缺口。共享 Workflow 停止发送 `repair_scope_sql`，后端删除 `validate_repair_scope` 及其调用；旧请求字段仅兼容解析，不再触发该检查。

SQL 的只读、语义 Schema 与字段准入、对象权限、可信身份检查及有界重试继续各自负责其明确边界。本机定向回归为 AI-Human 209 项、后端 65 项、隔离 PostgreSQL 54 项通过；后端全量 1066 通过、22 失败、48 跳过，22 项失败与同环境修改前基线相同。真实接口验证了非法图谱表名仍被拒绝、改用 `equipment_fault` 能成功，以及物理表、写操作、未知列仍被拒绝。定向关联 Run `run_b287cff8531e` 一次生成并执行成功，SQL 实际使用 `fault → equipment_fault → equipment`。

这些是**本机实施与验收**，不等于已提交、推送或证明所有业务问题正确。原问法 Run `run_730d47612f2e` 的两次 SQL 都成功，但主 Agent 自行把列表限为“前 10 条”，全量范围问题仍未解决。执行检查能约束可访问和可执行范围，**不能单独证明生成 SQL 的业务语义正确**；业务口径仍须对照用户问题和结果验证。

项目接入背景见 [[开发经验/AI-Human 业务本体与图谱检索技术选型|AI-Human 业务本体与图谱检索技术选型]]。故障排查、实施与本机验收记录在 `ai-human/labs/equipment_ontology/integration/root_cause_20261029/README.md` 和同目录 `EXECUTION_ACCEPTANCE.json`；故障时的旧函数位于 `ai-business-system/app/services/ai_sql_validation.py`，现已从本机代码移除。

## 8. 多模型查询链路：主 Agent 与 SQL 模型共享业务认知

2026-11-02，装备维保正式问答的后续讨论补充了一个关键经验：**在“主 Agent 理解、拆解任务 → 内部模型生成 SQL”的架构下，两者需要共享一致的业务认知。**此前关于简洁 Schema 的经验主要面向内层 SQL 查询；加入外层主 Agent 后，还需要给它完整的业务资源概览，以及当前任务涉及资源的必要详情。

主 Agent 会先决定调用什么能力、查询哪些资源、如何表达条件和解释结果。如果这一层不知道存在“判别规则”，或混淆了维修报告的“审核结果”和“编写进度”，传入 SQL Workflow 的任务就可能已经偏离用户问题。SQL 模型掌握更多字段，也无法保证纠正外层已经引入的错误条件。

### 对齐哪些信息

| 共同认知 | 要保持一致的内容 |
|---|---|
| 资源与可查内容 | 当前业务域有哪些资源、各资源能查询什么；目录覆盖完整，详情按任务提供 |
| 字段与取值含义 | 状态、时间、单位、空值的业务口径，名称/别名与实际字段值的区别 |
| 关系与统计范围 | 直接关联、批准的派生关联、历史登记文本各自含义，以及计数粒度 |
| 当前对象与任务 | 用户原话、可信选中对象、追问引用、本次关注的对象及条件 |

这里既有静态业务知识，也有每轮变化的查询事实。静态 info 对齐后，仍要让对象引用和任务范围在调用链中正确传递。

### 同源定义，按职责提供不同详细程度

可复用的设计是从同一份受控业务声明派生不同投影，并校验版本：

```text
受控业务语义声明
├─ 主 Agent：完整资源概览、相关资源的可查内容、少量声明取值和简短示例
├─ SQL 模型：同口径业务说明、批准的逻辑字段、类型、关联路径及必要依赖
└─ 业务服务：字段与操作准入、权限检查、执行映射和结果投影
```

主 Agent 要能正确定位和组织业务任务；SQL 模型需要进一步知道如何将任务落实为查询。上下文详细程度按职责分层，公共业务含义保持一致。底层存储、未知 JSON 键和未批准的内部字段继续留在能力边界之外。

控制 Token 时，优先压缩重复表述，按任务提供资源详情；保留完整资源目录和影响结果的业务定义。资源卡片用完整的可查业务内容加简短示例，避免每遇到一种失败问法就堆一条特例提示。示例应标明为虚构，只帮助理解字段，不作为实际结果或新枚举。

### 装备试点中的落实方式（v1.4.1）

- 先读取全局 `info` 了解13类业务资源；查询相关资源前，再用 `info(resources=[...])` 一次读取一个或多个资源详情。同版本完整说明已经可见时复用。
- Harness 检查概览与声明资源的完整说明是否真实可见，缺少时拒绝 query。这个检查证明模型读过说明，不证明它已经理解业务，也不能从自然语言证明所声明的资源集合完整。
- 内部 SQL 模型收到同版本、同正文的资源业务说明；声明资源的完整已开放字段映射先作为必要知识装配，再由原 Top-12 补充关系等知识。必要知识整体放不下时回退完整手册，避免主 Agent 认为“可以查”，内层却因裁剪缺少必要字段。

这项对齐沿用既有 SQL 组合能力，没有为50个问题新增固定查询接口。装备内部 SQL 继续关闭思考；思考模式、错误恢复和数据边界各自独立验证。

### 复测支持这个方向，但仍有适用边界

2026-11-02 对原50道正常业务题完整复测，沿用独立预期、真实选中对象和多轮历史：

| 指标 | 原 v1.3 完整50题 | 当前 v1.4.1 完整50题 |
|---|---:|---:|
| 必答业务事实正确 | 44/50 | 49/50 |
| 整段最终答复正确，保守口径 | 38/50 | 45/50 |
| 时延中位数 | 18.478秒 | 21.010秒 |
| P95，最近秩 | 49.153秒 | 38.857秒 |

当前50个 Run 均正常结束，没有整轮失败或模型超时；测试前后55条独立只读参考查询全部稳定。45/50包含一题中等置信度的跨人员合计口径歧义，其余四题为明确错误。运行成功、工具结果正确、最终答复正确需要分别评价。

这批沿用了此前完成的字段投影、错误恢复等改动，并非只改变 info 的消融实验，不能把全部提升归因于“业务认知对齐”。共享推理服务负载和缓存未控制，每题只有一次样本，也不能据此宣称稳定提速。

唯一必答结果错误的N39，用户同时选中两台装备，故障数应为7和0，却回答7和7：首次查询漏掉零匹配对象，补查没有明确保留第二个对象的查询焦点，又返回第一台；主 Agent 随后错误归属结果。另有几题主结果正确，追加统计却算错或口径不清。**业务认知对齐是这类架构的重要基础；零结果保留、对象焦点传递和最终结果核对仍需单独处理。**

## 一句话记住

> 查询链路中的模型共享业务口径，按职责取得不同详细程度的知识。清晰结构负责表达，少量规则负责消歧，模型负责组合，数据库负责计算。
