# 知识图谱检索单元的组织与分阶段横评

> 同一份图谱知识可以按不同粒度建立检索索引。先比较能否在预算内选齐必要定义，再用下游任务验证这些定义有没有被正确使用；两层结果不能互相代替。

## 先分清比较的是什么

图谱实验里，“构建方式”至少可能指三件事：

1. **事实从哪里来**：人工建模、规则抽取、模型从文档抽取，以及来源核验。
2. **知识怎么表示**：哪些是实体、字段、关系、规则，依赖和批准路径怎样记录。
3. **检索单元怎么组织**：哪些定义合成一条索引文档，哪些上下文一起送入 Embedding，命中后怎样补齐依赖。

如果四组都来自同一份已冻结的本体，只改变第三层，就应称为**知识组织或索引视图横评**。它不能证明哪种自动构图方法更好，也不能证明某种图数据库更好。检索文档只是派生视图：稳定定义 ID、原始定义、来源和关系仍需单独保留，命中后回到原定义装配上下文。

## 四种值得比较的检索单元

| 方案 | 一条索引文档包含什么 | 主要检验的取舍 |
| --- | --- | --- |
| 整实体分组 | 一个实体及其全部字段；关系、规则等另成单元 | 容易带全字段，但可能挤占上下文预算 |
| 原子定义 | 实体、字段、关系、规则各自独立 | 可精确选取，但短描述可能缺少消歧线索 |
| 带上下文的原子定义 | 原子定义加所属实体、关系两端、依赖名称等 | 能否改善短定义的召回，同时保留细粒度 |
| 依赖预分组 | 建索引时把明确需要一起理解的定义组成单元 | 能否提前带上条件，代价是重复编码与候选聚集 |

预分组与“检索后图补全”发生在不同阶段：前者把整组文字一起向量化，后者先检索单条定义，再按显式依赖把相关定义加入最终上下文。即使最后包含的定义 ID 相同，索引向量和候选排序也可能不同。

分组只沿有依据的依赖、关系路径和规则引用进行。不要为了让某道测试题命中而加入题目专属别名或凭空补事实。一个分组若超出预算，应整体拒绝并记录，不能截掉半条关系路径后仍当作已覆盖。

## 横评顺序：先检索，再看任务结果

### 1. 冻结知识和题目

固定同一份规范定义、Embedding 模型、排序方式、图补全规则、最终知识 Token 预算和下游渲染方式。先写好问题与必要定义 ID，再构建索引；构建器和排序器不读答案。保留旧题作为回归，新增组合题检查跨实体、状态、单位、时间及关系路径，并标清新增题是否由方案设计者编写。缺定义题单列：最近邻返回候选，不等于系统已经有该指标定义。

不同粒度的单元不能仅凭相同 Top-K 声称信息量相同。可以预设一个主 K 和少数诊断 K，同时按**相同最终知识预算**比较；不要事后为每组挑最有利的 K 拼成主排名。查询向量可在同一次展示比较中共享，但独立执行的时延对照要把查询编码成本记清楚。

### 2. 在检索层记录选取过程

至少分开记录：原始 Top-K 是否命中、图依赖补全新增了什么、预算淘汰了什么、最终是否选齐必要定义。再记录最终知识 Token、文档构建 Token、索引大小、查询编码和本地装配耗时。失败不能静默换成另一种检索方式。

必要定义覆盖率只是**预标注定义是否被选中**，不是业务回答正确率；额外定义也不自动等于噪声。更少的知识 Token 可能是因为漏选了定义。严格按 ID 的评分可以用于诊断，但同一业务结果有时还能由其他合法路径得到，需留到下游核查。

### 3. 选分歧题做下游验证

保留覆盖领先、成本较低和失败机制不同的候选，继续在同一任务、模型、数据快照与执行限制下比较。只替换所选知识，核对模型实际收到的请求。下游至少区分三层：

1. **严格交付**：列名、逐行结构、NULL、范围及事实是否都符合任务契约。
2. **事实已返回**：即使结构不符，已有回执中是否能明确提取全部所需事实。
3. **最终回答**：主 Agent 能否正确理解回执、必要时拆分任务并向用户回答。

第二层是事后内容诊断，不能回填严格分数，更不能冒充第三层。若缺字段导致不必要的澄清、返回了嵌套数组而非指定逐行结果，或仅列名不同但事实相同，也应分开归因。

## 一次冻结本体实验带来的提醒

2026-10-29 的装备维保实验使用同一份 332 条定义，对四种**索引视图**做检索横评；36 道正例、2 道缺定义负例，主工作点为 K=12、2500 知识 Token。三次重复用于观察稳定性，不当作新的独立问题。

| 方案 | 36 道正例中选齐必要定义 | 最终知识 Token 中位数 |
| --- | ---: | ---: |
| 整实体分组 | 32/36 | 2455 |
| 原子定义 | 26/36 | 2290 |
| 带上下文的原子定义 | 30/36 | 1788 |
| 依赖预分组 | 26/36 | 1371 |

在这个题集上，整实体组覆盖最多，却带入更多知识；带上下文的原子定义比原子定义覆盖更高，但模板文字也一并变化，不能断定具体是哪一项上下文起作用。预分组的低 Token 有一部分来自漏选定义；它的文档编码输入约为带上下文原子组的 4.79 倍，因为依赖内容被反复写入各组。增加带上下文原子组的候选数到预设 K=24，覆盖也达到 32/36，但成功题与整实体 K=12 不完全相同。

随后只挑整实体 K=12、带上下文原子 K=12/K=24 做固定 SQL 子任务验证：17 题、每组两次，共 102 次。三组严格交付均为 **28/34**；只看 30 个正例中“回执已包含全部所需事实”，事后诊断分别为 **27/30、26/30、30/30**。K=24 相比当前 K=12 的累计模型总 Token 增加约 **20.6%**，严格交付却没有提高。部分事实位于嵌套数组或 `details` 中，尚未验证主 Agent 能否正确提取并回答。这个结果支持继续把 K=12 作为成本基线、把 K=24 留作最终回答测试候选；不支持仅凭检索分数或内容完整性立即切换默认方案。

这些是**同一本体、特定模型、特定题集**上的观察。组合题由实验设计者编写，不是独立盲测；固定 SQL 子任务也不包含主 Agent 的自主规划和最终回答。不能推广成通用准确率。

## 复盘时先问这些问题

1. 漏项发生在原始召回、依赖补全，还是预算淘汰？
2. 命中的定义是否来自有依据的源内容？规则、关系方向和单位有没有被完整保留？
3. Top-K 和最终 Token 预算是否同时记录？低 Token 是否只是漏选？
4. 文档重复编码、索引维护和查询耗时是否分开计费？缓存冷热状态是否一致？
5. 评分是否区分定义覆盖、事实已返回、严格结构和最终回答？
6. 负例、失败题、预检、异常批次是否保留并与正式样本分开？

本次实验就发现，多 K 顺序运行时共享 Token 计数缓存会让装配耗时偏热；后续对原记录逐条清缓存重放，确认上下文不变后才重报冷缓存计时。性能比较要检查测量路径本身。
