# 工具结果的确定性结构压缩：表格化、去重与模型投影

> **重复字段名只写一次，相同长值按规则复用，已知的等价包装合并。程序就能让送给模型的数据更紧凑，不需要先调用另一个模型生成摘要。**

记录来源：2026-10-20 关于“SQL 结果从 JSON 对象数组改成表头＋行数据”的讨论。已对照 ai-human 本地源码，读取时 HEAD 为 `0274ab6dde5b20a0333b2c35318ca8a0ff129789`。以下实现说明针对这份本地源码；没有据此推断线上各业务的启用情况和调用频率。

## 1. 图里的方式叫什么

可以称为**确定性结构压缩**，也可以说是**表示压缩**。具体到截图，是把对象数组改成表头与行数据的**表格化编码**：

```json
[
  {"id": 1, "status": "OK", "type": "设备"},
  {"id": 2, "status": "OK", "type": "设备"},
  {"id": 3, "status": "OK", "type": "设备"}
]
```

可以改写成：

```text
columns: id, status, type
1, OK, 设备
2, OK, 设备
3, OK, 设备
```

这里没有要求模型判断“哪几条重要”，也没有把三条记录总结成一句话。变化发生在表示上：原来每行都写一遍 `id/status/type`，现在表头只声明一次，后面按列的位置对应值。

ai-human 中同类实现保留 JSON 外壳，使用如下格式：

```json
{
  "format": "columnar-v1",
  "columns": ["id", "status", "type"],
  "rows": [
    [1, "OK", "设备"],
    [2, "OK", "设备"],
    [3, "OK", "设备"]
  ]
}
```

按列名把每行重新组装成对象，就能恢复原来的数据。`columnar-v1` 是项目内的格式标记；这里讨论的是工具文本的编码，不是在改变数据库的物理存储方式。

这是一类方法，没有必要把截图认作某一个特定压缩库或标准协议。

## 2. 为什么它可以不依赖模型

程序知道两件事，就可以完成转换：

1. 各条记录使用哪些字段。
2. 每条记录中，各字段的值是什么。

转换过程是固定规则：

```text
检查是否为同构对象数组
   ↓
确定统一列顺序
   ↓
把每条对象转换成按列排列的值数组
   ↓
附带格式说明，输出紧凑表示
```

恢复过程同样不需要模型：

```text
columns = [id, status, type]
row     = [1,  OK,     设备]
   ↓
{id: 1, status: OK, type: 设备}
```

它节省的是字段名、结构符号和等价重复内容的开销。可以先用一句话理解：**事实保留，表达事实时的重复开销减少。**

使用 LLM 生成摘要，是另一种处理：模型需要选择和概括信息，通常无法由程序把摘要还原成全部原始记录。二者可以在同一系统中配合，但需要分别验收。

## 3. 这类方法可以分成几层

| 方法 | 做什么 | 例子 |
| --- | --- | --- |
| 紧凑序列化 | 去掉排版空白 | `json.dumps(..., separators=(",", ":"))` |
| 表头复用 | 同构记录只声明一份字段名 | 对象数组 → `columns + rows` |
| 公共字段上提 | 同一批数据的公共值放到批次层 | 每个对象相同的资源类型、资源标题只写一次 |
| 已知等价字段合并 | 相同事实保留一个明确位置 | `content` 与 `text` 完全相同时，正文保留一份 |
| 局部值字典与引用 | 同一回执的重复长值只保存一次 | 多行相同报告正文 → 值字典＋局部引用 |

前两层几乎不涉及业务判断。后面几层需要明确数据契约：哪些字段互为别名，哪些值真的相同，引用怎样解释。

例如，“状态都叫正常”并不足以证明两条对象相同；去重的是可复用的表示，不能因此删掉对象、合并重复行或改写对象身份。

同样，业务对象的 `ref` 用来指代真实对象，压缩编码中的 `$ref` 用来指向局部值字典。二者含义不同。

## 4. ai-human 里确实多处采用了这个思路

从当前源码看，这不是只用在某个实验脚本里的技巧：共享业务读取、共享 RAG，以及显式启用的装备 SQL 工具都有相关实现。不过，不同路径做的事情并不完全相同。

### 4.1 业务读取：表格化、公共字段与别名复用

主要实现位于：

```text
app/capabilities/business_integration/services/business_read_projection.py
```

`columnarize_homogeneous_records()` 递归查找同构对象数组，转换成 `columnar-v1`。基本条件包括：至少两条记录、每条都是对象、字段集合一致、字段集合非空。列顺序取第一条记录，各行依照这个顺序取值。

字段不一致时不强行补齐：`{"x": null}` 与 `{}` 的含义可能不同，不能随便补一个 null 就声称保留了原结构。

`render_lossless_business_payload()` 还包含两类专门优化：

- **info 资源目录**：使用 `manual-resources-v1`，处理已知结构中某些资源有 `statuses`、某些资源缺省的情况；不能表达的形状保持原路径。
- **list 结果**：使用 `list-flat-v1`，复用 `data.columns` 的字段顺序，将共同的 `resource/resource_title` 提到批次层；只有顶层 `title/status/object_code` 与对应 `fields` 值确实相同时，才用别名表示。

它还保留了一个实际调用所需的边界：**手册示例 `data.manual.examples` 和续页 `request` 保持可直接调用的普通 JSON 参数。** 事实表可以编码，工具参数示例则要能照着构造合法调用。

展开函数 `expand_columnar_records()` 用于恢复这些受支持的格式。完整手册可见性校验也会先展开再核对内容，不能因为回包压短了，就放松对规则、示例是否仍然可见的检查。

### 4.2 RAG：合并等价包装，保留正文和来源

主要实现位于：

```text
app/capabilities/retrieval/model_projection.py
```

`_compact_chunk()` 处理已知的重复表示，例如：

- 非空 `content` 与 `text/snippet` 完全相同，省略重复正文副本。
- `associated_images` 与 `image_urls` 或 `metadata.anchor_images` 完全相同，省略重复图片列表。
- 顶层与 metadata 中的已知来源字段完全相同，保留一份。
- 已知的位置字段重复时，保留完整的定位表示。
- 相同的图片使用说明放在本次回包的公共位置，不在每个 chunk 重复附加。

比较会递归区分类型，不把 `false` 与 `0` 当成相同值。不同正文、不同图片顺序、不同评分和未知字段，不能只因为占空间就删掉。

这里应称为**事实层面的等价去重**。它保留正文、全部 chunk、顺序及已知来源信息，但没有提供把输出逐字段还原成任意 raw 回包的通用解码器。不要把“没有删正文”进一步说成“整个原始 JSON 逐字节可逆”。

### 4.3 SQL 查询：表格化＋重复长值字典

主要实现位于：

```text
app/capabilities/business_integration/services/business_result_compaction.py
```

`render_compact_business_result()` 对受控模型 payload 选择几种候选表示：

1. 紧凑的原 JSON。
2. 使用 `$table` 的表格化表示。
3. 再加上局部值字典，用 `$ref` 复用相同长值。

编码说明放在 `_compact` 中。遇到原业务本身使用 `$table/$ref/$literal` 等保留键时，通过 `$literal` 保留原值，避免把业务数据错认成编码。

实现会比较包含说明开销在内的最终字符串长度，选择最短候选；很小的结果可能直接保留紧凑原结构。`expand_compact_business_result()` 用于还原受支持的编码。

当前 `query_business_by_sql` 的 projector 使用这个函数。这个 SQL 工具在装备模块里仍属于显式启用的实验能力，不能因此说所有业务查询都走这条链路。

还有一个范围区别：SQL projector 先选取适合交给主 Agent 的结果字段，再调用结构编码函数。**编码可以相对于选出的模型 payload 无损，但整个投影未必能还原原始工具回包中的 SQL、内部诊断等字段。**

### 4.4 SQL Workflow：选择更直接的行式表示

当前 `query_business_by_sql_workflow` 使用另一份投影：

```text
app/business_modules/equipment_maintenance/sql_workflow_result_text.py
```

它直接输出状态、范围、列名与行数据，单元格内联，不要求模型追踪压缩值字典。数据行使用制表符分格，每个单元格独立编码成 JSON 值，并对换行、制表符及 Unicode 行分隔符作确定性转义。

这种方式仍会复用表头、提高表示密度，只是减少了局部引用的解码步骤。源码里的“无压缩编码”指的是不使用那套 `$table/$ref` 结构引用，不等于每一行重新重复全部字段名。

10 月 10 日的工程记录提到，结构引用增加了解码负担，因此 Workflow 采用更直接的表示。该记录也发现，高重复长正文下，直接内联的输入 Token 会增加。这里存在一个真实取舍：**表示长度与模型读取负担，要放在一起评估。**

## 5. “模型结果投影”比“结构压缩”范围更大

ai-human 的模型投影入口会按工具贡献选择 projector，并把原始 payload 的深拷贝交给它。工具执行结果与模型接收到的文本因此可以分别维护。

可以把关系理解成：

```text
工具执行，得到原始结果
   ├─ 原始回执 / UI 等消费者
   └─ 模型结果投影
        ├─ 选择模型需要的协议与事实
        ├─ 按需要做结构压缩或等价去重
        └─ 得到待接纳的模型文本
             ↓
        完整请求预算检查
             ↓
        保存、重放已接纳的模型表示
```

这解释了为什么原始接口可以继续返回完整业务 JSON，模型收到的却是更紧凑的表格或文本。

但 projector 这个名字本身不保证无损。例如写作工具的 proposal 投影只给模型元数据与“尚未应用”的说明，候选正文保留给前端和服务端应用流程。这是**按用途选择可见信息**，不能把它归为完整内容的可逆压缩。

判断一个实现是否无损，要问清楚相对于哪份输入：原始工具结果、已经筛选的模型 payload，还是约定要保留的事实集合。

## 6. 怎样才算保住了数据

对于声称可逆的结构编码，最直接的标准是：

```text
decode(encode(payload)) == payload
```

这里相等的目标是约定的数据结构和值，不要求恢复 JSON 原文的缩进、空白或对象键的排版顺序。

至少需要关注：

| 边界 | 需要保留什么 |
| --- | --- |
| JSON 类型 | `false`、`0`、`"0"` 等不能混成一个值 |
| 缺失与空值 | 字段不存在，与字段值是 null 分开处理 |
| 空集合 | `[]`、`{}` 和无字段不是同一回事 |
| 顺序与重复行 | 数据顺序、重复行及对象身份不因去重而改变 |
| 字符转义 | 逗号、引号、换行、制表符不破坏单元格边界 |
| 引用与分页 | 业务 ref、cursor、has_more、完整性标记仍然明确 |
| 编码标记 | 原业务的同名键不会被误解成编码 |
| 调用参数 | 示例和续页参数仍能用于原工具 schema |

截图里的简单纯文本适合说明原理，但“随便拿逗号拼字符串”不能覆盖通用 JSON。例如字符串 `"001"` 不能变成数字 `1`，字符串里有逗号和换行时也需要明确转义规则。

对于 RAG 这类事实去重，验收目标则应具体到正文、条数、顺序、来源、图片关联及差异值保留，不能只检查字符串变短。

## 7. 字符少了，不代表 Token 一定少了

表格化通常能减少大量重复字段名，但还有三个因素：

1. **编码说明也占空间。** 少量短记录可能不够抵消 `format/columns/rows` 等外壳。
2. **Tokenizer 按自己的规则切分。** 字符长度、UTF-8 字节长度、Token 数不是同一指标。
3. **模型还要读取和使用结果。** 过多局部引用可能增加查找、推理或出错的成本。

当前 `business_result_compaction.py` 按字符串长度挑最短候选；这能限制字符开销，不能自动证明对当前模型的 Token 数也是最优。业务读取的部分形状转换也不是每一步都在原 JSON 与新编码间做全局最短选择。

所以截图里的“Token 已经减少了”应以对应 tokenizer 的实测为准，不能作为所有形状、所有模型下的必然结论。

这种压缩依然让模型直接读取文本。gzip、zstd 等字节压缩适合存储或传输；把压缩字节换成 Base64 文本，并不会自动得到模型可理解的更短上下文。数据怎样交给模型读取，是另一层问题。

## 9. 可以沉淀下来的设计经验

**先减少可证明的表示冗余，再决定是否需要丢弃或概括信息。** 同构表格、重复别名、重复说明往往适合程序处理；自然语言摘要负责另一个层面的任务交接。

实现时，需要让编码、解码和适用形状明确对应。数据形状不满足条件时保留原表示，格式标记与原业务字段冲突时有明确处理，完整性与失败状态始终可读。

选择格式时，直接表格通常更容易查看；值字典适合重复的长正文，但需要检查模型能否正确追踪引用。可以用输入 Token、读取正确性、推理与输出用量、耗时一起评估，而不是只追求字符串最短。

原始结果、模型副本和已接纳历史也应分清。新回执采用什么表示，与以后是否改写旧历史，是不同决策。ai-human 当前的首次投影和稳定重放边界，值得继续保留。
